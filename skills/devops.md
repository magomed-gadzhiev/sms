## Режим: deploy

### Pre-deploy checklist
Перед деплоем проверь **каждый пункт**. Если хоть один FAIL — не деплой.

**1. Код:**
- [ ] Текущая ветка — та, что нужна (`master` или указанная в `DEPLOY_BRANCH`)
- [ ] Все изменения закоммичены и запушены в GitHub
- [ ] `go build ./...` — компиляция без ошибок
- [ ] `go vet ./...` — нет очевидных проблем
- [ ] Нет конфликтов с remote (git pull --dry-run)

**2. Миграции:**
- [ ] Есть ли новые файлы в `migrations/`?
- [ ] Если да — миграции идемпотентны? (можно запустить повторно без ошибки)
- [ ] Есть ли rollback/down-миграция?
- [ ] Миграция не содержит destructive операций (DROP TABLE, DROP COLUMN) без подтверждения

**3. Конфигурация:**
- [ ] Новые env-переменные? Добавлены ли на сервере?
- [ ] Нет захардкоженных секретов в коммите (grep по паттернам: password, secret, token, apikey)
- [ ] `docker-compose.yml` — валидный, нет синтаксических ошибок
- [ ] Порты не конфликтуют с существующими сервисами

**4. Зависимости:**
- [ ] `go.mod` / `go.sum` — изменились? Новые зависимости — безопасны?
- [ ] `package.json` / `package-lock.json` — изменились? npm audit?
- [ ] Docker-образы — указаны конкретные версии (не `latest`)?

### Deploy execution

**Стандартный деплой:**
1. `scripts/server.sh sync` — git pull без перезапуска
2. `scripts/server.sh migrate` — применить миграции (если есть новые)
3. `scripts/server.sh deploy` — пересборка и перезапуск контейнеров
4. Перейти к post-deploy verification

**Деплой одного сервиса:**
1. `scripts/server.sh deploy <service>` — обновить только указанный
2. Перейти к post-deploy verification (scope: только этот сервис)

**При ошибке деплоя:**
1. Прочитать лог ошибки
2. Если ошибка сборки — не перезапускать, старые контейнеры продолжают работать
3. Если контейнер не поднимается — `scripts/server.sh logs <service>` для диагностики
4. При необходимости: `scripts/server.sh restart <service>` с предыдущей версией

### Post-deploy verification

**Немедленно (0-1 мин):**
- [ ] `scripts/server.sh status` — все контейнеры Running
- [ ] Health-эндпоинты отвечают 200 (если есть)
- [ ] Логи без panic/fatal/error (первые 30 секунд)

**Короткий smoke test (1-3 мин):**
- [ ] Portal доступен (HTTP 200 на `/portal`)
- [ ] Login работает (если есть тестовый аккаунт)
- [ ] API отвечает (GET на основной эндпоинт)
- [ ] gRPC-сервисы отвечают (если есть health check)

**Мониторинг (3-10 мин):**
- [ ] Логи: нет роста error rate
- [ ] Метрики: request latency в норме (если есть Prometheus)
- [ ] Delivery rate: не просел (если есть данные)
- [ ] Kafka: consumer lag не растёт

### В режиме interactive
- Показывай pre-deploy checklist и жди подтверждения перед каждым этапом.
- При ошибке — предлагай варианты (fix / rollback / skip).
- После деплоя — показывай результаты каждой проверки.

### В режиме auto
- Выполняй pre-deploy. При FAIL — останавливайся и пиши отчёт, не деплой.
- Деплой только если все проверки пройдены.
- Post-deploy: при ошибке — пытайся диагностировать, не откатывай автоматически.
- Результат — отчёт с полным логом деплоя.

## Режим: health

Проверка состояния сервера и сервисов. Запускать по расписанию (ежедневно или чаще).

### 1. Контейнеры
- Все контейнеры Running? Uptime каждого.
- Есть ли перезапуски (restart count > 0)?
- Потребление ресурсов: CPU, memory каждого контейнера.

### 2. Диск
- Свободное место на `/` и `/opt` (порог: <20% свободного = WARNING, <10% = CRITICAL).
- Размер Docker volumes (особенно PostgreSQL data).
- Размер логов (`/var/log`, Docker logs) — нужна ли ротация?
- Неиспользуемые Docker images/volumes — можно ли почистить?

### 3. Базы данных
- **PostgreSQL:**
  - Размер БД и крупнейших таблиц.
  - Активные connections vs pool size.
  - Dead tuples — нужен ли VACUUM?
  - Долгие запросы (>5 сек) — есть ли прямо сейчас?
  - Репликация (если есть) — lag.
  - Последний бэкап — когда? Размер?
- **Redis:**
  - Используемая память vs maxmemory.
  - Количество ключей.
  - Eviction policy — срабатывает ли?
  - Persistence (RDB/AOF) — последний snapshot.

### 4. Kafka
- Broker доступен?
- Consumer lag по group'ам — есть ли отстающие?
- Размер топиков — настроена ли retention?

### 5. Сеть и сертификаты
- Внешние порты (HTTP, SMPP) — доступны?
- SSL-сертификат — дней до истечения (порог: <30 = WARNING, <7 = CRITICAL).
- DNS — резолвится ли домен (если есть)?

### 6. Безопасность
- Обновления ОС — есть ли security updates?
- SSH: вход только по ключу? Root login отключен?
- Firewall: только нужные порты открыты?

## Режим: incident

Диагностика при проблеме. Параметр `Цель` описывает симптом.

### Алгоритм
1. **Симптом:** что именно не работает? (из параметра `Цель`)
2. **Scope:** один сервис или вся платформа?
3. **Timeline:** когда началось? Что изменилось перед этим? (git log, deploy history)
4. **Логи:** `scripts/server.sh logs <service>` — ищи первую ошибку, не последнюю
5. **Ресурсы:** CPU/memory/disk — не упёрлись ли в лимит?
6. **Зависимости:** БД, Redis, Kafka — живы ли? Отвечают ли?
7. **Гипотеза:** что сломалось и почему
8. **Действие:** restart / rollback / fix config / scale up / hotfix

### Приоритет действий
1. **Восстановить сервис** — restart, если помогает
2. **Понять причину** — не маскировать проблему рестартом
3. **Предотвратить повторение** — что изменить, чтобы не повторилось

### В режиме interactive
- Задавай уточняющие вопросы ("Когда началось?", "Что деплоили?").
- Показывай гипотезы и проси подтверждение перед действиями.
- Не перезапускай сервисы без подтверждения.

### В режиме auto
- Собирай диагностику, формируй гипотезу.
- Не предпринимай деструктивных действий (restart, rollback) автоматически.
- Результат — отчёт с диагностикой и рекомендованными действиями.

## Режим: maintenance

Регулярное обслуживание. Запускать раз в неделю.

### 1. Очистка
- Неиспользуемые Docker images: `docker image prune`
- Неиспользуемые Docker volumes (осторожно!): только если точно не используются
- Старые логи: ротация, сжатие
- Временные файлы

### 2. Бэкапы
- Последний бэкап PostgreSQL — когда? Проверить целостность.
- Если нет автоматических бэкапов — предложить настройку (pg_dump + cron + retention).
- Redis RDB/AOF — актуален ли?

### 3. Обновления
- Docker images — есть ли новые версии для base images?
- ОС пакеты — security updates?
- PostgreSQL, Redis, Kafka — minor version updates?

### 4. Оптимизация
- PostgreSQL: `VACUUM ANALYZE` на крупных таблицах.
- PostgreSQL: проверка размера индексов, bloat.
- Redis: проверка TTL политик, memory fragmentation.
- Docker: пересборка images (если давно не обновлялись).

### В режиме auto
- Выполняй безопасные операции: очистка Docker images, VACUUM, проверка бэкапов.
- Не удаляй volumes, не обновляй пакеты, не перезапускай сервисы.
- Результат — отчёт с выполненным и рекомендациями.
