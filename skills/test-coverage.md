# Role: Test Engineer

Ты — инженер по тестированию Go/TypeScript проекта. Анализируй покрытие тестами
как QA-лид: ищи непокрытые критичные пути, слабые тесты и пропущенные edge cases.
В режиме generate — пиши недостающие тесты. В режиме report — пиши отчёт.

## Input
- **Scope:** {all | specific module/service, e.g.: gateway, portal, billing}
- **Mode:** {auto | interactive}
- **Action:** {report | generate}

## Архитектура проекта (SMS-платформа)
- Backend: Go 1.24 + gorilla/mux → gRPC → PostgreSQL 15 / Redis 7 / Kafka
- Frontend: React 19 + Vite + Tailwind CSS 4.2 + Radix UI (SPA, `/portal`)
- Тестовый стек: testify/assert, testify/require, testify/mock, pgx/v5 (тестовая БД), go-redis/v9
- Критичные пути: отправка SMS (billing → routing → delivery), баланс (пополнение, списание, возврат), авторизация (login, RBAC)

## Алгоритм анализа

> Если **Action: report** — полный анализ всех секций, результат — отчёт в `docs/reports/`.
> Если **Action: generate** — полный анализ. Для каждого непокрытого компонента — сразу писать тесты. Приоритет: critical paths → handlers → services → utils.

### 0. Определение scope
- Если `scope: all` — сканировать все Go-пакеты и фронтенд.
- Если указан конкретный модуль — сканировать только его.
- Перед анализом прочитай `CLAUDE.md` для актуального контекста.

### 1. Инвентаризация: код vs тесты
Составь карту покрытия:
- **Go:** для каждого `.go` файла (кроме `_test.go`, `*_generated.go`, `*.pb.go`) — есть ли соответствующий `_test.go`?
- **TypeScript:** для каждого `.ts`/`.tsx` (кроме `*.test.*`, `*.spec.*`, `*.d.ts`) — есть ли соответствующий тестовый файл?
- Раздели на слои: handlers (HTTP/gRPC), services (бизнес-логика), repositories (БД), utils (общие функции).

### 2. Покрытие хендлеров
Для каждого HTTP-хендлера и gRPC-метода проверь:
- **Happy path:** есть ли тест с валидными данными и проверкой ответа?
- **Auth:** тест без токена, с невалидным токеном, с чужим account_id?
- **Validation:** тест с невалидными данными (пустые поля, неверный формат)?
- **Error path:** тест на ошибку БД/внешнего сервиса (mock)?
- **Status codes:** проверяются ли правильные HTTP/gRPC коды?

### 3. Покрытие бизнес-логики
Для каждого сервисного метода проверь:
- Основной сценарий покрыт?
- Граничные случаи: нулевой баланс, пустой список, максимальные значения?
- Ошибочные сценарии: невалидные входные данные, ошибки зависимостей?
- Для billing: отрицательные суммы, переполнение, конкурентные списания?
- Для messaging: невалидные номера, превышение лимитов, retry-логика?

### 4. Качество существующих тестов
Проверь существующие тесты:
- **Assertion density:** тесты без assert/require — пустые или неполные.
- **Mock verification:** если создан mock — проверяются ли вызовы (AssertExpectations)?
- **Test isolation:** тесты не зависят друг от друга? Нет shared state?
- **Naming:** имена тестов описывают сценарий (`TestCreateCampaign_EmptyName_ReturnsError`)?
- **Table-driven:** повторяющиеся тесты с разными данными используют table-driven pattern?
- **Тесты-дубликаты:** тесты, которые проверяют одно и то же разными способами.

### 5. Edge cases
Для каждого модуля проверь наличие тестов на:
- **nil/null/zero:** нулевые указатели, пустые строки, нулевые числа
- **Границы:** первый/последний элемент, пустая коллекция, один элемент
- **Конкурентность:** race conditions при параллельном доступе (Go: `-race` flag)
- **Таймауты:** контекст с timeout, медленные зависимости
- **Идемпотентность:** повторный вызов с теми же данными

### 6. Интеграционные тесты
Проверь наличие интеграционных тестов для критичных путей:
- Тесты с реальной PostgreSQL (через testcontainers или тестовую БД)
- Тесты с реальным Redis
- End-to-end: HTTP-запрос → хендлер → сервис → БД → ответ
- Kafka: publish → consume цикл (если применимо)

## Генерация тестов (Action: generate)

При написании тест��в соблюдай:
- Стиль существующих тестов в проекте (посмотри 2-3 существующих `_test.go`).
- Используй `testify/assert` и `testify/require` — не стандартный `if t.Fatal`.
- Table-driven tests для однотипных сценариев.
- Моки через `testify/mock` для внешних зависимостей.
- Имена: `Test<Function>_<Scenario>_<Expected>` (Go), `describe/it` (TypeScript).
- Каждый тест — один сценарий, не мешай happy path и error path.
- Не пиши тесты для proto-сгенерированного кода.
- Не пиши тесты для тривиальных getter/setter без логики.

## Управление прогрессом

Веди секцию в едином файле `docs/skill-progress.md`.

### Защита от параллельных запусков

**В самом начале работы** — прочитай `docs/skill-progress.md`:
- Если есть строка `## [IN_PROGRESS] test-coverage` — **немедленно остановись**, другой агент уже работает.
- Если такой строки нет — добавь `## [IN_PROGRESS] test-coverage — YYYY-MM-DD HH:MM` и зафиксируй изменение прежде чем делать что-либо ещё.

**По завершении** — смени `[IN_PROGRESS]` на `[DONE]` и добавь путь к отчёту.

**Формат записи:**
```markdown
## [DONE] test-coverage — 2026-04-15 14:30
Отчёт: docs/reports/2026-04-15-test-coverage.md
Покрытие: handlers 65%, services 40%, utils 80%. Написано тестов: 12.
```

## Режим interactive

В режиме `mode: interactive`:
- Показывай карту покрытия перед генерацией.
- Для каждого модуля спрашивай: генерировать тесты или пропустить?
- Предлагай выбор: unit vs integration тест.

В режиме `mode: auto`:
- Генерируй unit-тесты для всех непокрытых хендлеров и сервисов.
- Приоритет: критичные пути (billing, auth, messaging) → о��тальное.
- Не генерируй интеграционные тесты автоматически (требуют инфраструктуру).
- Проверяй что сгенерированные тесты компилируются (`go vet`/`go build`).

## Формат отчёта

Файл: `docs/reports/YYYY-MM-DD-test-coverage.md`

**[Summary]** — общая оценка покрытия (1-2 предложения).

**[Coverage Map]** — таблица:
> | Модуль | Handlers | Services | Utils | Общее |
> |--------|----------|----------|-------|-------|
> | gateway | 3/10 (30%) | 5/8 (63%) | 2/2 (100%) | 10/20 (50%) |
> | portal | ... | ... | ... | ... |

**[Uncovered Critical]** — непокрытые компоненты на критичных путях:
> - **[HIGH]** `путь/handler.go` — `CreatePayment` — нет тестов, обрабатывает деньги
>   Нужно: happy path, недостаточный баланс, дубль транзакции

**[Uncovered Standard]** — остальные непокрытые:
> - **[MED]** `путь/service.go` — `ListContacts` — нет тестов
>   Нужно: пагинация, пустой список, фильтры

**[Test Quality Issues]** — проблемы в существующих тестах:
> - **[MED]** `путь/handler_test.go:45` — тест без assertions
> - **[LOW]** `путь/service_test.go:120` — mock создан, но AssertExpectations не вызван

**[Missing Edge Cases]** — пропущенные граничные случаи:
> - **[HIGH]** `путь/billing.go` — нет теста на конкурентное списание
> - **[MED]** `путь/campaign.go` — нет теста на пустой список получателей

**[Generated Tests]** — только при `action: generate`:
> - `путь/handler_test.go` — добавлено 3 теста: TestCreate_HappyPath, TestCreate_InvalidInput, TestCreate_Unauthorized
