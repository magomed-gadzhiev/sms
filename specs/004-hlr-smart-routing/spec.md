# Feature Specification: Number Lookup (HLR/MNP) + Smart Routing

**Feature Branch**: `004-hlr-smart-routing`
**Created**: 2026-03-21
**Status**: Draft
**Input**: User description: "Number Lookup (HLR/MNP) + Smart Routing — интеграция HLR-lookup для определения реального оператора, smart routing, кеширование, API валидации номеров"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - HLR-обогащённая маршрутизация SMS (Priority: P1)

Платформа перед отправкой каждого SMS выполняет HLR-запрос для определения реального оператора получателя. На основе полученных данных система выбирает оптимального провайдера для доставки — того, у которого наилучшее соотношение стоимости и качества для данного оператора. Если номер перенесён (MNP), сообщение уходит реальному оператору, а не тому, что определяется по префиксу.

**Why this priority**: Это ядро фичи — без этого остальные сценарии не имеют смысла. Прямое влияние на deliverability (+10%) и снижение затрат (15-30%).

**Independent Test**: Можно протестировать отправкой SMS на перенесённый номер — система должна определить реального оператора и выбрать правильного провайдера.

**Acceptance Scenarios**:

1. **Given** номер перенесён от оператора A к оператору B, **When** система отправляет SMS на этот номер, **Then** HLR-запрос определяет оператора B и сообщение маршрутизируется через провайдера, обслуживающего оператора B.
2. **Given** HLR-провайдер недоступен, **When** система отправляет SMS, **Then** маршрутизация выполняется по префиксу (fallback), и событие логируется для мониторинга.
3. **Given** номер имеет статус "invalid" по данным HLR, **When** система обрабатывает запрос на отправку, **Then** отправка не выполняется, клиент получает статус "invalid", и стоимость доставки не списывается.
4. **Given** номер имеет статус "absent" по данным HLR, **When** система обрабатывает запрос на отправку, **Then** SMS отправляется с пометкой "absent" в статусе доставки, клиент информируется о временной недоступности получателя.

### User Story 2 - Кеширование HLR-результатов (Priority: P1)

Результаты HLR-запросов кешируются с TTL 24 часа. При повторной отправке на тот же номер в пределах TTL система использует кешированные данные без повторного HLR-запроса. Это снижает затраты на HLR-lookup и ускоряет маршрутизацию.

**Why this priority**: Без кеширования каждое SMS потребует отдельный HLR-запрос — это дорого и медленно. Критично для экономической эффективности.

**Independent Test**: Отправить два SMS на один номер в течение 24 часов — второе должно использовать кешированный результат без HLR-запроса.

**Acceptance Scenarios**:

1. **Given** HLR-запрос для номера выполнен менее 24 часов назад, **When** поступает новый запрос на отправку на тот же номер, **Then** система использует кешированный результат без обращения к HLR-провайдеру.
2. **Given** TTL кешированного результата истёк, **When** поступает запрос на отправку, **Then** система выполняет новый HLR-запрос и обновляет кеш.
3. **Given** номер помечен как "invalid" в кеше, **When** клиент запрашивает повторную валидацию до истечения TTL, **Then** система позволяет принудительный HLR-запрос с обновлением кеша.

### User Story 3 - API валидации номеров (Standalone Number Lookup) (Priority: P2)

Клиенты платформы могут использовать отдельный API для проверки номеров без отправки SMS. API возвращает информацию: реальный оператор, статус номера (active/absent/invalid), страна, тип номера (mobile/fixed). Это отдельный тарифицируемый продукт.

**Why this priority**: Дополнительная линия дохода, но не блокирует основную функциональность маршрутизации.

**Independent Test**: Вызвать API с номером — получить структурированный ответ о статусе и операторе без побочных эффектов (отправки SMS).

**Acceptance Scenarios**:

1. **Given** клиент авторизован и имеет активный аккаунт, **When** он отправляет запрос на валидацию номера, **Then** система возвращает: реальный оператор, статус номера, страна, тип номера.
2. **Given** клиент отправляет запрос на валидацию пакета номеров (bulk), **When** пакет содержит до 1000 номеров, **Then** система обрабатывает все номера и возвращает результаты для каждого.
3. **Given** клиент превысил лимит запросов, **When** он отправляет новый запрос, **Then** система возвращает ошибку с указанием оставшегося времени до сброса лимита.

### User Story 4 - Выбор оптимального провайдера (Smart Routing) (Priority: P2)

После определения реального оператора система выбирает провайдера на основе: стоимости маршрута для данного оператора, текущей доступности провайдера, исторического качества доставки (delivery rate). Если основной провайдер недоступен, система переключается на следующий по приоритету.

**Why this priority**: Улучшает экономику маршрутизации поверх базового HLR-обогащения.

**Independent Test**: Настроить два провайдера для одного оператора с разной стоимостью — система должна выбрать более дешёвого при равном качестве.

**Acceptance Scenarios**:

1. **Given** для оператора B доступны провайдеры X (дешевле, delivery rate 95%) и Y (дороже, delivery rate 97%) и настроены веса по умолчанию, **When** система выбирает провайдера, **Then** выбирается провайдер с лучшим взвешенным score по настроенным весам (cost weight, quality weight).
2. **Given** провайдер X недоступен (health check failed), **When** система маршрутизирует SMS для оператора B, **Then** выбирается следующий по приоритету провайдер Y.
3. **Given** администратор обновил тарифы провайдера, **When** новые тарифы вступают в силу, **Then** smart routing учитывает обновлённые тарифы для новых сообщений.

---

### Edge Cases

- Что происходит, если HLR возвращает противоречивую информацию (например, номер active, но оператор не определён)? Система должна выполнить fallback на маршрутизацию по префиксу.
- Как обрабатывается ситуация, когда все HLR-провайдеры недоступны? Система должна переключиться на prefix-based routing и отправить алерт операционной команде.
- Что если номер перенесён повторно в течение TTL кеша? Используется кешированный (потенциально устаревший) результат, но при ошибке доставки инвалидируется кеш и выполняется повторный HLR-запрос.
- Как обрабатываются номера формата, не поддерживаемого HLR (короткие номера, служебные)? Система пропускает HLR-lookup и маршрутизирует по префиксу.
- Что происходит при массовой рассылке (100k+ номеров)? Система выполняет HLR-запросы пакетами с rate-limiting, используя кеш для уже проверенных номеров.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Система MUST выполнять синхронный HLR-запрос (или использовать кешированный результат) перед отправкой SMS для определения реального оператора-получателя. Отправка блокируется до получения результата lookup.
- **FR-002**: Система MUST поддерживать fallback на маршрутизацию по префиксу, если HLR-запрос невозможен (провайдер недоступен, timeout, неподдерживаемый формат номера).
- **FR-003**: Система MUST кешировать результаты HLR-запросов с настраиваемым TTL (по умолчанию 24 часа).
- **FR-004**: Система MUST предоставлять клиентам API для валидации номеров (single и bulk до 1000 номеров за запрос).
- **FR-005**: Система MUST возвращать в результате lookup: реальный оператор (MCC+MNC), статус номера (active/absent/invalid/unknown), страна, тип номера (mobile/fixed/voip).
- **FR-006**: Система MUST выбирать оптимального провайдера для маршрутизации на основе: реального оператора, стоимости маршрута, доступности провайдера и исторического delivery rate. Веса факторов (cost weight, quality weight) MUST быть настраиваемыми per-operator и per-region с разумными значениями по умолчанию.
- **FR-007**: Система MUST поддерживать подключение нескольких HLR-провайдеров с настраиваемым приоритетом и failover.
- **FR-008**: Система MUST не отправлять SMS и не списывать стоимость доставки, если номер определён как invalid. Номера со статусом absent MUST обрабатываться как доступные для отправки с пометкой статуса "absent" в результате доставки.
- **FR-009**: Система MUST тарифицировать lookup-запросы как отдельный продукт с per-number тарификацией (каждый номер в bulk-запросе оплачивается отдельно).
- **FR-010**: Система MUST обеспечивать rate-limiting для API валидации номеров (настраиваемые лимиты per-client).
- **FR-011**: Система MUST инвалидировать кеш для номера при неудачной доставке, связанной с ошибкой маршрутизации (wrong operator).
- **FR-012**: Система MUST логировать все HLR-запросы и их результаты для аудита и аналитики. Срок хранения логов — 90 дней, после чего данные автоматически удаляются (PII — номера телефонов).
- **FR-013**: Система MUST позволять клиентам принудительно запрашивать свежий HLR-lookup (bypass cache) через параметр API.

### Key Entities

- **NumberLookupResult**: Результат HLR-запроса — содержит MSISDN, реальный оператор (MCC+MNC, название), статус номера, страна, тип номера, время запроса, источник (HLR-провайдер), флаг portability (перенесён ли номер).
- **HLRProvider**: Внешний HLR-провайдер — название, приоритет, статус доступности, стоимость запроса, поддерживаемые регионы.
- **SmartRoute**: Правило маршрутизации — связка реального оператора с провайдером доставки, стоимость, приоритет, delivery rate, статус активности.
- **LookupRequest**: Запрос клиента на валидацию — клиент, список номеров, тип (single/bulk), результаты, стоимость, timestamp.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Deliverability SMS на рынках с высоким MNP повышается с ~85% до ~95%.
- **SC-002**: Средняя стоимость доставки одного SMS снижается на 15-30% за счёт выбора оптимального провайдера.
- **SC-003**: Время обработки одного SMS (включая HLR-lookup с кешем) не превышает прежнее время обработки более чем на 200мс в 95-м перцентиле.
- **SC-004**: Коэффициент использования кеша (cache hit rate) при стабильной нагрузке составляет не менее 70% после первых 24 часов работы.
- **SC-005**: Bulk-запрос на валидацию 1000 номеров обрабатывается менее чем за 30 секунд.
- **SC-006**: При недоступности всех HLR-провайдеров система продолжает отправку SMS через prefix-based routing без потери сообщений.
- **SC-007**: Lookup как отдельный продукт генерирует дополнительный доход — отслеживается количество платных lookup-запросов в месяц.

## Clarifications

### Session 2026-03-21

- Q: Как обрабатывать номера со статусом "absent" — блокировать отправку или отправлять? → A: Отправлять на absent (с пометкой в статусе), блокировать только invalid.
- Q: Режим HLR-lookup в pipeline отправки — синхронный или асинхронный? → A: Синхронный: HLR-запрос (или кеш-хит) блокирует отправку, гарантирует актуальность перед каждым SMS.
- Q: Модель тарификации bulk-lookup — per-number или per-batch? → A: Per-number: каждый номер в batch тарифицируется отдельно.
- Q: Настраиваемость весов smart routing — фиксированная формула или конфигурируемая? → A: Настраиваемые веса per-operator/per-region с разумными defaults (cost weight, quality weight).
- Q: Срок хранения логов HLR-lookup (содержат PII — номера телефонов)? → A: 90 дней — баланс между аудитом, биллинговой сверкой и минимизацией PII.

## Assumptions

- Существуют коммерчески доступные HLR-провайдеры с API-доступом для целевых регионов (Европа, СНГ).
- Текущая архитектура маршрутизации (routing-service) допускает расширение для интеграции HLR-данных без полного переписывания.
- TTL кеша 24 часа является разумным балансом между актуальностью данных и стоимостью HLR-запросов (MNP в среднем происходит значительно реже).
- Клиенты платформы готовы оплачивать lookup-запросы как отдельную услугу.
- Rate-limiting для API валидации настраивается per-client через существующую тарифную систему.
