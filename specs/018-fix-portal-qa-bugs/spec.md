# Feature Specification: Исправление багов портала по результатам QA

**Created**: 2026-04-01  
**Status**: Draft  
**Input**: QA-отчёт `/test-screenshots/server-full-qa-1775019984296` — автоматизированное тестирование продакшн-сервера

## User Scenarios & Testing *(mandatory)*

### User Story 1 — Дашборд загружается после входа (Priority: P1)

Новый или вернувшийся пользователь входит в личный кабинет и видит дашборд с актуальной сводкой. Сейчас дашборд застревает в состоянии «Загрузка дашборда…» и никогда не показывает контент — страница пустая на неопределённый срок.

**Why this priority**: Дашборд — первая страница после входа. Если он не загружается, пользователь не может работать с порталом.

**Independent Test**: Войти в ЛК → убедиться, что дашборд отображает реальные данные или корректный пустой экран в течение 5 секунд.

**Acceptance Scenarios**:

1. **Given** пользователь только что вошёл в систему, **When** открывается страница `/dashboard`, **Then** в течение 5 секунд отображается содержимое дашборда (статистика или пустой экран с подсказкой) — текст «Загрузка дашборда…» исчезает.
2. **Given** у нового пользователя нет данных, **When** открывается дашборд, **Then** отображается пустой экран с поясняющим сообщением, а не бесконечный спиннер.
3. **Given** запрос на профиль возвращает 401 до завершения авторизации, **When** пользователь успешно входит, **Then** портал получает профиль и завершает загрузку дашборда, не подвешивая страницу.

---

### User Story 2 — Страницы с пустыми данными отображаются корректно (Priority: P1)

Пользователь переходит на разделы портала (Сообщения, Рассылки, Шаблоны, Контакт-листы, Биллинг), в которых ещё нет данных. Сейчас эти страницы падают или не рендерятся. Пользователь должен видеть информативный пустой экран с призывом к действию.

**Why this priority**: Все новые пользователи начинают именно в этом состоянии. Падающие страницы делают продукт неиспользуемым с первых минут.

**Independent Test**: Зайти с новым аккаунтом и последовательно открыть `/messages`, `/campaigns`, `/templates`, `/contact-lists`, `/billing` — каждая должна отрендериться без ошибок.

**Acceptance Scenarios**:

1. **Given** у пользователя нет сообщений, **When** он открывает раздел Сообщения, **Then** отображается пустой экран с поясняющим текстом, страница не падает.
2. **Given** у пользователя нет рассылок, **When** он открывает раздел Рассылки, **Then** отображается пустой экран с призывом создать первую рассылку.
3. **Given** у пользователя нет шаблонов, **When** он открывает раздел Шаблоны, **Then** отображается пустой экран.
4. **Given** у пользователя нет контакт-листов, **When** он открывает раздел Контакт-листы, **Then** отображается пустой экран.
5. **Given** у пользователя нет транзакций биллинга, **When** он открывает раздел Биллинг, **Then** отображается пустой экран с информацией о балансе (или нулевым балансом).

### User Story 3 — Валидация имени API-ключа с понятной ошибкой (Priority: P2)

Пользователь создаёт API-ключ и вводит слишком длинное имя. Сейчас сервер возвращает HTTP 400 без пользовательской обратной связи — пользователь не понимает, что пошло не так и что нужно исправить.

**Why this priority**: Молчащий сбой дезориентирует пользователя; без UX-обратной связи задача не решается.

**Independent Test**: Попытаться создать API-ключ с именем длиннее допустимого лимита → увидеть сообщение об ошибке с указанием лимита символов.

**Acceptance Scenarios**:

1. **Given** пользователь вводит имя API-ключа длиннее допустимого лимита, **When** он нажимает «Создать», **Then** отображается сообщение «Имя не должно превышать N символов» (клиентская валидация, без отправки запроса).
2. **Given** клиентская валидация пропущена и сервер вернул 400, **When** форма получает ответ, **Then** рядом с полем «Название» показывается читаемое сообщение об ошибке, кнопка «Создать» снова становится активной.
3. **Given** пользователь вводит корректное имя, **When** он нажимает «Создать», **Then** ключ создаётся успешно.

---

### Edge Cases

- Что происходит, когда `/dashboard` открывается при нестабильном соединении — показывается ли кнопка «Повторить» или только ошибка?
- Если у пользователя есть баланс биллинга, но нет истории транзакций — отображается ли баланс при пустой таблице транзакций?
- Что происходит при попытке создать API-ключ с пустым именем?

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Дашборд ДОЛЖЕН завершать загрузку и показывать контент (или пустой экран) в течение 5 секунд после успешной авторизации пользователя.
- **FR-002**: Дашборд ДОЛЖЕН корректно отображаться при нулевом количестве данных (новый аккаунт) — без бесконечного спиннера.
- **FR-003**: Страницы Сообщения, Рассылки, Шаблоны, Контакт-листы и Биллинг ДОЛЖНЫ рендериться без ошибок, когда в них нет записей.
- **FR-004**: Каждая из указанных страниц ДОЛЖНА показывать информативный пустой экран с поясняющим текстом и/или призывом к действию вместо сбоя.
- **FR-005**: Форма создания API-ключа ДОЛЖНА валидировать длину имени на стороне клиента до отправки запроса.
- **FR-006**: При получении ответа об ошибке от сервера во время создания API-ключа портал ДОЛЖЕН отображать читаемое сообщение об ошибке рядом с соответствующим полем формы.
- **FR-007**: Запросы на получение профиля пользователя ДОЛЖНЫ выполняться только после успешного завершения авторизации, исключая появление повторяющихся ошибок «Не авторизован» в консоли.

### Key Entities

- **Дашборд**: сводный виджет с ключевыми метриками аккаунта; должен корректно отображаться при любом количестве данных (0..N).
- **Пустой экран (Empty State)**: компонент, показываемый вместо таблицы/списка, когда у пользователя нет записей; содержит поясняющий текст и ссылку/кнопку для начала работы.
- **API-ключ**: сущность с обязательным полем «Название»; поле имеет максимальную длину, которую нужно валидировать на стороне клиента.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Дашборд отображает контент для 100% вошедших пользователей в течение 5 секунд (в нормальных условиях сети) — состояние «Загрузка дашборда…» никогда не остаётся единственным содержимым страницы.
- **SC-002**: Все 5 ранее падавших страниц (Сообщения, Рассылки, Шаблоны, Контакт-листы, Биллинг) отображаются без ошибок при пустых данных — автоматизированный QA-тест переходит с 4/11 неуспехов в стрессовых тестах на 0 неуспехов по этим страницам.
- **SC-003**: Попытка создать API-ключ с невалидным именем приводит к отображению сообщения об ошибке в течение 1 секунды — QA-тест «Long API key name» переходит из `false` в `true`.
- **SC-004**: В консоли браузера нет необработанных ошибок при навигации по перечисленным страницам с пустыми данными после завершения авторизации.

---

## Assumptions

- Баги воспроизводятся на продакшн-сервере; локальное воспроизведение предполагается возможным с теми же данными.
- Максимальная длина имени API-ключа задана серверной логикой; если она явно не задокументирована, принимаем 100 символов как разумный лимит для клиентской валидации.
- Страницы Сегменты и Провайдеры уже корректно обрабатывают пустые данные (прошли QA) — они вне скоупа данного фикса.
- Повторяющиеся 401-ошибки в консоли — следствие race condition при старте приложения (запросы уходят до получения токена), а не проблема серверной авторизации.
- Мобильная адаптация (responsive) — вне скоупа данного фикса (блок `responsive` в QA-отчёте пуст).
- Регистрационная форма использует метку «Email» вместо «Электронная почта» — это отдельная проблема локализации, не входит в данный скоуп.
