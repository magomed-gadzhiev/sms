# Feature Specification: Multi-tenant Self-Service Portal + Sub-accounts

**Feature Branch**: `003-self-service-portal`
**Created**: 2026-03-21
**Status**: Draft
**Input**: User description: "Multi-tenant Self-Service Portal + Sub-accounts"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Авторизация и управление профилем (Priority: P1)

Клиент входит в портал по email и паролю, может сбросить пароль, включить двухфакторную аутентификацию (TOTP), обновить контактные данные. Каждый пользователь видит только данные своего tenant'а.

**Why this priority**: Авторизация — обязательная основа для любого самообслуживания. Без безопасного входа портал невозможен.

**Independent Test**: Можно протестировать, выполнив вход, сброс пароля и включение 2FA.

**Acceptance Scenarios**:

1. **Given** зарегистрированный клиент, **When** он вводит корректный email и пароль, **Then** он авторизуется и видит данные своего аккаунта
2. **Given** клиент забыл пароль, **When** он запрашивает сброс, **Then** на email приходит ссылка для установки нового пароля (действительна 1 час)
3. **Given** клиент с включенной 2FA, **When** он входит с корректным паролем, **Then** система запрашивает TOTP-код перед предоставлением доступа
4. **Given** пользователь tenant A, **When** он пытается получить данные tenant B, **Then** система возвращает ошибку доступа

---

### User Story 2 - Просмотр баланса и истории сообщений (Priority: P1)

Клиент входит в личный кабинет и видит текущий баланс, историю отправленных SMS с детализацией (получатель, статус доставки, стоимость, дата/время). Клиент может фильтровать и искать сообщения по дате, статусу и номеру получателя.

**Why this priority**: Базовая функциональность, закрывающая основной запрос клиентов — понимание текущего состояния аккаунта и отслеживание отправок.

**Independent Test**: Авторизоваться в портале и проверить отображение баланса и списка сообщений с корректной фильтрацией.

**Acceptance Scenarios**:

1. **Given** авторизованный клиент с балансом 1500 руб., **When** он открывает главную страницу портала, **Then** отображается текущий баланс 1500 руб. и последние 50 сообщений
2. **Given** клиент с историей 500 сообщений, **When** он применяет фильтр по дате "01.03.2026 - 15.03.2026", **Then** отображаются только сообщения за указанный период
3. **Given** клиент просматривает историю, **When** он фильтрует по статусу "Доставлено", **Then** отображаются только успешно доставленные сообщения

---

### User Story 3 - Управление API-ключами (Priority: P1)

Клиент самостоятельно создает, просматривает и отзывает API-ключи для интеграции. При создании ключа секрет отображается один раз. Клиент может задать описание ключа и ограничить его по IP-адресам.

**Why this priority**: API-ключи — основной инструмент интеграции. Самостоятельное управление ключами устраняет зависимость от администратора.

**Independent Test**: Создать новый ключ, проверить его в списке, затем отозвать и убедиться, что ключ перестал работать.

**Acceptance Scenarios**:

1. **Given** авторизованный клиент, **When** он создает новый API-ключ с описанием "Production", **Then** система генерирует ключ, отображает секрет один раз и добавляет ключ в список активных
2. **Given** клиент с тремя активными ключами, **When** он отзывает один из них, **Then** ключ помечается как отозванный и перестает приниматься системой
3. **Given** клиент создает ключ, **When** он указывает разрешенные IP-адреса "192.168.1.0/24", **Then** ключ принимается только с запросов из указанной подсети

---

### User Story 4 - Аналитика по отправкам (Priority: P2)

Клиент просматривает агрегированную аналитику по SMS-отправкам: количество отправленных/доставленных/недоставленных, конверсия доставки, расходы за период. Данные в виде графиков и таблиц с выбором периода.

**Why this priority**: Аналитика помогает клиентам оптимизировать отправки, но не блокирует основную работу с платформой.

**Independent Test**: Выбрать период и проверить корректность агрегированных данных и отображения графиков.

**Acceptance Scenarios**:

1. **Given** клиент с историей отправок за месяц, **When** он открывает раздел аналитики, **Then** отображаются графики доставляемости и расходов за последние 30 дней
2. **Given** клиент выбирает период "Последняя неделя", **When** данные загружаются, **Then** все метрики пересчитываются для выбранного периода
3. **Given** клиент с отправками в разные страны, **When** он просматривает аналитику, **Then** данные можно группировать по стране назначения

---

### User Story 5 - Настройка Webhook'ов (Priority: P2)

Клиент настраивает URL для получения уведомлений о статусах доставки (DLR) и входящих сообщениях. Можно добавлять, редактировать и удалять webhook-эндпоинты, просматривать историю доставки уведомлений.

**Why this priority**: Webhook'и важны для интеграции, но это вторичная функциональность после базового управления аккаунтом.

**Independent Test**: Добавить webhook URL, отправить тестовое сообщение и проверить получение уведомления.

**Acceptance Scenarios**:

1. **Given** авторизованный клиент, **When** он добавляет webhook URL "https://example.com/dlr" для событий доставки, **Then** URL сохраняется и отображается в списке активных webhook'ов
2. **Given** клиент с настроенным webhook'ом, **When** он нажимает "Отправить тест", **Then** система отправляет тестовое событие и показывает результат доставки
3. **Given** webhook не отвечает 10 раз подряд, **When** система фиксирует сбой, **Then** webhook деактивируется и клиент получает уведомление по email

---

### User Story 6 - Создание и управление Sub-accounts (Priority: P2)

Клиент-реселлер создает дочерние аккаунты (sub-accounts) для своих клиентов. Каждый sub-account имеет отдельный баланс, лимиты на отправку и собственные API-ключи. Пользователи sub-accounts получают собственный логин в портал и видят свои данные (баланс, историю сообщений, API-ключи, webhook'и). Реселлер просматривает статистику по всем sub-accounts, пополняет их балансы из своего основного баланса и устанавливает ограничения.

**Why this priority**: Sub-accounts открывают реселлерский канал монетизации, но требуют базовую функциональность портала (P1) как фундамент.

**Independent Test**: Создать sub-account, пополнить его баланс, отправить сообщение от его имени и проверить корректность списания.

**Acceptance Scenarios**:

1. **Given** клиент с балансом 10000 руб., **When** он создает sub-account "Компания А" с начальным балансом 1000 руб., **Then** sub-account создается, 1000 руб. переводится с баланса реселлера
2. **Given** реселлер с 5 sub-accounts, **When** он открывает сводку по sub-accounts, **Then** отображается таблица с балансами, количеством отправок и статусом каждого
3. **Given** sub-account с балансом 0 руб., **When** sub-account пытается отправить сообщение, **Then** отправка блокируется с сообщением о недостаточном балансе
4. **Given** реселлер, **When** он устанавливает дневной лимит 500 сообщений для sub-account, **Then** после достижения лимита отправки блокируются до следующего дня

---

### Edge Cases

- Что происходит, когда реселлер удаляет sub-account с ненулевым балансом? Остаток возвращается на баланс реселлера.
- Что происходит при попытке создать sub-account, когда у реселлера недостаточно средств? Операция отклоняется с сообщением о недостаточном балансе.
- Что происходит при одновременном отзыве API-ключа и входящем запросе с этим ключом? Запрос отклоняется — отзыв вступает в силу немедленно.
- Что происходит при превышении лимита запросов к аналитике? Применяется rate limiting с информативным сообщением.
- Что происходит, если webhook-эндпоинт клиента недоступен длительное время? После 10 неудачных попыток webhook деактивируется, клиент уведомляется по email.
- Что происходит при попытке входа с неверным паролем более 5 раз? Аккаунт временно блокируется на 15 минут.
- Что происходит при удалении реселлерского аккаунта, у которого есть активные sub-accounts? Удаление блокируется — сначала необходимо удалить или перенести все sub-accounts.
- Что происходит при попытке создать sub-account сверх лимита? Операция отклоняется с сообщением о достижении максимального количества sub-accounts.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Система ДОЛЖНА предоставлять клиентам веб-интерфейс для просмотра текущего баланса в реальном времени
- **FR-002**: Система ДОЛЖНА отображать историю отправленных сообщений с детализацией (получатель, статус, стоимость, время отправки/доставки)
- **FR-003**: Система ДОЛЖНА поддерживать фильтрацию и поиск по истории сообщений (по дате, статусу, номеру получателя)
- **FR-004**: Система ДОЛЖНА позволять клиентам создавать, просматривать и отзывать API-ключи
- **FR-005**: Система ДОЛЖНА отображать секрет API-ключа только один раз при создании
- **FR-006**: Система ДОЛЖНА поддерживать ограничение API-ключей по IP-адресам (whitelist)
- **FR-007**: Система ДОЛЖНА предоставлять агрегированную аналитику: количество сообщений по статусам, конверсия доставки, расходы за период
- **FR-008**: Система ДОЛЖНА отображать аналитику в виде графиков и таблиц с выбором произвольного периода
- **FR-009**: Система ДОЛЖНА позволять клиентам настраивать webhook-эндпоинты для получения уведомлений о доставке
- **FR-010**: Система ДОЛЖНА поддерживать отправку тестовых webhook-событий для проверки настройки
- **FR-011**: Система ДОЛЖНА автоматически деактивировать webhook'и после 10 последовательных сбоев доставки и уведомлять клиента
- **FR-012**: Система ДОЛЖНА позволять клиентам-реселлерам (статус активируется администратором) создавать sub-accounts с отдельными балансами, лимитами и собственными учетными данными для входа в портал
- **FR-013**: Система ДОЛЖНА поддерживать перевод средств с баланса реселлера на баланс sub-account
- **FR-014**: Система ДОЛЖНА позволять реселлерам устанавливать дневные и месячные лимиты на количество сообщений для каждого sub-account
- **FR-015**: Система ДОЛЖНА блокировать отправки sub-account при исчерпании баланса или достижении лимита
- **FR-016**: Система ДОЛЖНА обеспечивать полную изоляцию данных между tenant'ами (мультитенантность)
- **FR-017**: Система ДОЛЖНА поддерживать аутентификацию по email/паролю с опциональной двухфакторной аутентификацией (TOTP)
- **FR-018**: Система ДОЛЖНА поддерживать сброс пароля через email со ссылкой, действительной 1 час
- **FR-019**: Система ДОЛЖНА блокировать аккаунт на 15 минут после 5 неудачных попыток входа
- **FR-020**: Система ДОЛЖНА предоставлять реселлерам полный доступ к данным sub-accounts (история сообщений, API-ключи, webhook'и, баланс, аналитика)
- **FR-021**: Система ДОЛЖНА возвращать остаток баланса на счет реселлера при удалении sub-account
- **FR-022**: Система ДОЛЖНА поддерживать пагинацию для всех списковых представлений
- **FR-023**: Система ДОЛЖНА вести полный журнал аудита всех критичных действий пользователей (создание/отзыв API-ключей, настройка webhook'ов, операции с sub-accounts, финансовые операции, изменения профиля и настроек безопасности)
- **FR-024**: Система ДОЛЖНА отображать журнал аудита tenant'у с возможностью фильтрации по типу действия, дате и пользователю

### Key Entities

- **Tenant (Клиент)**: Основная учетная запись клиента. Содержит профиль, баланс, настройки. Может иметь реселлерский статус (активируется администратором) с заданным лимитом на количество sub-accounts. Связан с API-ключами, webhook'ами и sub-accounts.
- **Sub-account**: Дочерняя учетная запись, принадлежащая tenant'у-реселлеру. Имеет собственный баланс, лимиты на отправку и API-ключи. Максимальная глубина — один уровень.
- **API Key**: Ключ доступа для программной интеграции. Принадлежит tenant'у или sub-account'у. Имеет описание, статус (активен/отозван), опциональный IP-whitelist.
- **Webhook Endpoint**: Настроенный URL для получения уведомлений. Принадлежит tenant'у или sub-account'у. Имеет тип событий, статус, счетчик ошибок.
- **Message History**: Запись об отправленном сообщении с детализацией. Принадлежит tenant'у или sub-account'у.
- **Balance Transaction**: Запись о движении средств (пополнение, списание, перевод на sub-account, возврат). Обеспечивает аудит финансовых операций.
- **Audit Log Entry**: Запись о действии пользователя в портале. Содержит: кто (пользователь/tenant), что (тип действия), когда (временная метка), детали (параметры действия), IP-адрес. Неизменяемые записи для расследования инцидентов.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Клиенты выполняют 90% рутинных операций (просмотр баланса, управление ключами, аналитика) самостоятельно, без обращения в поддержку
- **SC-002**: Количество обращений в поддержку по операционным вопросам снижается на 80% в течение 3 месяцев после запуска
- **SC-003**: Клиент может создать API-ключ и начать интеграцию менее чем за 5 минут
- **SC-004**: Реселлер может создать и настроить sub-account менее чем за 3 минуты
- **SC-005**: Данные аналитики загружаются и отображаются менее чем за 3 секунды для периодов до 30 дней
- **SC-006**: Портал поддерживает одновременную работу не менее 500 активных пользователей без деградации
- **SC-007**: 100% данных изолированы между tenant'ами — ни один клиент не может получить доступ к данным другого
- **SC-008**: Не менее 10% клиентов активируют реселлерскую модель (sub-accounts) в течение 6 месяцев после запуска

## Clarifications

### Session 2026-03-21

- Q: Могут ли пользователи sub-accounts самостоятельно входить в портал? → A: Да, sub-accounts получают собственный логин и видят свои данные (баланс, сообщения, ключи, webhook'и).
- Q: Как tenant становится реселлером? → A: Администратор активирует реселлерский статус для конкретного tenant'а.
- Q: Есть ли лимит на количество sub-accounts у реселлера? → A: Да, администратор задает максимальное количество при активации реселлерского статуса.
- Q: Какой уровень доступа реселлера к данным sub-accounts? → A: Полный доступ — реселлер видит все данные sub-accounts (сообщения, ключи, webhook'и, баланс).
- Q: Требуется ли аудит действий в портале? → A: Да, полный аудит — все действия с ключами, webhook'ами, sub-accounts и балансом логируются.

## Assumptions

- Клиенты уже зарегистрированы в системе через администратора; портал предоставляет самообслуживание для существующих клиентов.
- Пополнение баланса происходит через администратора или внешнюю платежную систему — портал отображает баланс, но не принимает платежи напрямую.
- Максимальная глубина иерархии sub-accounts — один уровень (реселлер -> sub-account, без вложенности).
- Хранение истории сообщений ограничено 90 днями для оперативного доступа; более старые данные доступны через экспорт.
- Webhook-уведомления используют формат JSON с HMAC-подписью для верификации.
- Портал поддерживает русский и английский языки интерфейса.
- Автоматическая деактивация webhook после 10 сбоев реализована в существующем webhook-service. Email-уведомление клиента при деактивации — отложено до реализации email-инфраструктуры (отдельная фича).
