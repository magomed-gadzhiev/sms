# Feature Specification: Portal UX Improvements for Managers

**Feature Branch**: `019-portal-ux-improvements`  
**Created**: 2026-04-01  
**Status**: Draft  
**Input**: User description: "На основе анализа кода предложи 5 новых фич, которые закроют текущие пробелы в функциональности, и 3 изменения в существующих модулях для улучшения масштабируемости. Изучи реализацию ui/ux панели клиента, предложи 5 улучшений в интерфейсе. Цель - сделать удобным для менеджеров, чтобы процесс был простым и наглядным."

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Визуальный дашборд с графиками и трендами (Priority: P1)

Менеджер открывает дашборд и видит наглядные графики: динамику отправок за неделю/месяц, распределение статусов доставки (кольцевая диаграмма), топ-5 стран по трафику (горизонтальная гистограмма), а также карточки метрик с индикаторами трендов (стрелки вверх/вниз с процентом изменения по сравнению с предыдущим периодом). На странице аналитики доступны интерактивные графики временных рядов с возможностью выбора метрик и периода.

**Why this priority**: Менеджеры принимают решения на основе данных. Сейчас дашборд показывает только статичные числа без контекста и динамики, что заставляет вручную сравнивать показатели. Визуализация - самый высокий ROI для удобства работы.

**Independent Test**: Можно протестировать, открыв дашборд и аналитику - графики отображаются с реальными данными, при наведении показываются детали, переключение периодов обновляет данные.

**Acceptance Scenarios**:

1. **Given** менеджер авторизован, **When** открывает дашборд, **Then** видит карточки метрик с трендами (сравнение с предыдущим периодом) и 3 графика: временной ряд отправок, распределение статусов, топ стран
2. **Given** менеджер на странице аналитики, **When** выбирает период "30 дней" и метрику "Доставлено", **Then** график обновляется и показывает данные за выбранный период с подписями осей
3. **Given** данные за выбранный период отсутствуют, **When** менеджер открывает график, **Then** отображается пустое состояние с понятным сообщением "Нет данных за выбранный период"
4. **Given** менеджер навел курсор на точку графика, **When** появляется тултип, **Then** в нем отображаются точные значения метрик на эту дату

### User Story 2 - Массовые действия над элементами списков (Priority: P1)

Менеджер работает со списками сообщений, шаблонов, контактных листов и имен отправителей. Он может выбрать несколько элементов чекбоксами (или выбрать все на странице) и применить массовое действие: удалить, экспортировать в CSV, изменить статус (для шаблонов - отправить на проверку, для имен отправителей - активировать/деактивировать).

**Why this priority**: Менеджеры ежедневно работают с десятками/сотнями записей. Поштучное удаление или экспорт занимает непропорционально много времени. Массовые действия - критичная функция для эффективной работы.

**Independent Test**: Открыть список сообщений, выбрать 5 элементов чекбоксами, нажать "Экспорт" - скачивается CSV с выбранными записями. Выбрать 3 шаблона, нажать "Удалить" - появляется подтверждение, после согласия элементы удаляются.

**Acceptance Scenarios**:

1. **Given** менеджер на странице списка сообщений, **When** отмечает чекбокс у 3 записей, **Then** появляется панель массовых действий с кнопками "Экспорт" и "Удалить" и счетчиком выбранных
2. **Given** выбрано 5 шаблонов в статусе "Черновик", **When** менеджер нажимает "Отправить на проверку", **Then** все 5 шаблонов переходят в статус "На проверке" и показывается уведомление об успехе
3. **Given** менеджер нажал "Выбрать все на странице", **When** затем снимает чекбокс с одного элемента, **Then** счетчик уменьшается на 1 и "Выбрать все" становится в промежуточном состоянии (indeterminate)
4. **Given** менеджер выбрал записи и нажал "Удалить", **When** появляется диалог подтверждения, **Then** диалог показывает количество удаляемых элементов и требует явного подтверждения

### User Story 3 - Улучшенный мастер создания рассылки с навигацией по шагам (Priority: P2)

Менеджер создает рассылку через мастер, где каждый шаг визуально отмечен в верхней панели прогресса. Можно свободно переходить между уже заполненными шагами кликом по индикатору, видеть сводку ошибок валидации на каждом шаге (красная точка на незаполненном шаге), а на последнем шаге - компактный preview всех параметров рассылки перед отправкой.

**Why this priority**: Текущий мастер позволяет двигаться только вперед/назад линейно. Менеджеры часто хотят вернуться к конкретному шагу, чтобы исправить параметр, не проходя все промежуточные. Это критично для сложных рассылок.

**Independent Test**: Создать рассылку, заполнить шаги 1-3, кликнуть на шаг 1 в индикаторе прогресса - происходит переход на шаг 1 с сохраненными данными. Оставить шаг 2 невалидным - на индикаторе видна красная точка.

**Acceptance Scenarios**:

1. **Given** менеджер заполнил шаги 1 и 2 мастера, **When** кликает на индикатор шага 1, **Then** происходит переход на шаг 1 с сохраненными данными шагов 1 и 2
2. **Given** шаг 3 содержит ошибку валидации, **When** менеджер находится на шаге 5, **Then** индикатор шага 3 отображает красную точку-маркер ошибки
3. **Given** менеджер на финальном шаге "Подтверждение", **When** просматривает сводку, **Then** видит все параметры рассылки: имя, список получателей (кол-во), текст сообщения, расписание, настройки повторов - компактно и наглядно
4. **Given** менеджер перешел на уже заполненный шаг и изменил данные, **When** данные на этом шаге теперь невалидны для последующих шагов, **Then** зависимые шаги помечаются как требующие проверки

### User Story 4 - Экспорт данных в CSV (Priority: P2)

Менеджер может экспортировать данные из любой таблицы портала (сообщения, транзакции, аналитика, контакты, аудит-лог) в CSV-файл. Экспорт учитывает текущие фильтры - выгружаются только отфильтрованные данные. Доступна кнопка "Экспорт" рядом с фильтрами на каждой странице со списком.

**Why this priority**: Менеджерам необходимо выгружать данные для отчетов, анализа в Excel, передачи коллегам. Сейчас единственный способ - копировать вручную из таблиц в браузере.

**Independent Test**: Отфильтровать сообщения по статусу "Доставлено" за последние 7 дней, нажать "Экспорт CSV" - скачивается файл с корректными данными, соответствующими фильтрам.

**Acceptance Scenarios**:

1. **Given** менеджер на странице сообщений с активными фильтрами, **When** нажимает кнопку "Экспорт CSV", **Then** скачивается CSV-файл с данными, соответствующими текущим фильтрам
2. **Given** в таблице более 10 000 записей, **When** менеджер запускает экспорт, **Then** показывается индикатор прогресса и файл скачивается по готовности
3. **Given** применены фильтры, отсекающие все записи, **When** менеджер нажимает "Экспорт", **Then** кнопка неактивна или отображается сообщение "Нет данных для экспорта"
4. **Given** менеджер экспортирует таблицу транзакций, **When** файл скачан, **Then** CSV содержит все видимые колонки таблицы с корректными заголовками на русском языке

### User Story 5 - Быстрый поиск и навигация (Command Palette) (Priority: P2)

Менеджер нажимает Ctrl+K (или Cmd+K на Mac) и видит палитру команд - поле поиска, позволяющее быстро найти любую страницу портала, действие (создать рассылку, добавить шаблон) или конкретную запись (имя отправителя, контактный лист). Результаты фильтруются по мере набора текста, переход происходит по Enter или клику.

**Why this priority**: При большом количестве страниц и функций навигация через сайдбар становится медленной. Палитра команд - стандартный паттерн для продвинутых пользователей, значительно ускоряющий работу.

**Independent Test**: Нажать Ctrl+K, набрать "рассыл" - в результатах видны "Рассылки" и "Создать рассылку". Выбрать "Создать рассылку" - переход на страницу создания.

**Acceptance Scenarios**:

1. **Given** менеджер на любой странице портала, **When** нажимает Ctrl+K, **Then** появляется модальное окно с полем поиска и фокусом на нем
2. **Given** палитра открыта, **When** менеджер вводит "шабло", **Then** в результатах отображаются "Шаблоны", "Создать шаблон" с иконками соответствующих разделов
3. **Given** палитра открыта, **When** менеджер нажимает Escape или кликает за пределами, **Then** палитра закрывается без побочных эффектов
4. **Given** палитра открыта с результатами, **When** менеджер нажимает стрелки вверх/вниз и Enter, **Then** навигация по результатам работает с клавиатуры и выбранный пункт активируется

### User Story 6 - Inline-валидация форм с визуальной обратной связью (Priority: P3)

При заполнении любой формы в портале (создание шаблона, настройка вебхука, добавление API-ключа, профиль) менеджер видит моментальную обратную связь: ошибки валидации появляются под полем сразу при вводе (не после отправки), обязательные поля отмечены визуально, счетчик символов показывается для текстовых полей с ограничениями (SMS-сообщение, имя отправителя).

**Why this priority**: Текущая валидация работает только при отправке формы. Менеджеры тратят время на исправление ошибок, обнаруженных постфактум. Real-time валидация снижает фрустрацию и количество ошибок.

**Independent Test**: Открыть форму создания шаблона, ввести в поле "Имя" один символ - под полем появляется подсказка "Минимум 3 символа". Удалить текст из обязательного поля - поле подсвечивается красным.

**Acceptance Scenarios**:

1. **Given** менеджер заполняет форму создания шаблона, **When** вводит слишком короткое имя, **Then** под полем появляется сообщение об ошибке и рамка поля становится красной
2. **Given** менеджер пишет текст SMS-сообщения, **When** длина приближается к лимиту, **Then** счетчик символов меняет цвет (зеленый -> желтый -> красный) и показывает оставшееся количество
3. **Given** форма содержит обязательные поля, **When** менеджер пытается отправить форму с пустыми обязательными полями, **Then** все пустые обязательные поля подсвечиваются одновременно с прокруткой к первой ошибке
4. **Given** менеджер исправил ошибку в поле, **When** значение становится валидным, **Then** индикатор ошибки исчезает немедленно и рамка возвращается к нормальному состоянию

### User Story 7 - Центр уведомлений (Priority: P3)

Менеджер видит в хедере портала иконку колокольчика с бейджем количества непрочитанных уведомлений. При клике открывается выпадающая панель с историей уведомлений: завершение рассылки, одобрение/отклонение шаблона или имени отправителя, низкий баланс, изменения статуса провайдеров. Уведомления можно отметить прочитанными по одному или все сразу.

**Why this priority**: Сейчас уведомления существуют только как toast-сообщения, которые исчезают через несколько секунд. Менеджер может пропустить важное событие, если не находился на портале в момент его возникновения.

**Independent Test**: Завершить рассылку, открыть портал - на колокольчике показывается "1", при клике видно уведомление "Рассылка X завершена: 950/1000 доставлено".

**Acceptance Scenarios**:

1. **Given** завершилась рассылка, **When** менеджер открывает портал, **Then** бейдж на колокольчике показывает количество непрочитанных уведомлений
2. **Given** менеджер кликает на колокольчик, **When** открывается панель уведомлений, **Then** уведомления отсортированы по времени (новые сверху) с иконками типов событий
3. **Given** панель уведомлений открыта, **When** менеджер нажимает "Отметить все прочитанными", **Then** бейдж исчезает и все уведомления визуально помечаются как прочитанные
4. **Given** менеджер кликает на уведомление о рассылке, **When** происходит переход, **Then** открывается страница соответствующей рассылки

### User Story 8 - Улучшенная аналитика с разбивками и сравнениями (Priority: P3)

Менеджер на странице аналитики может сравнить два периода (этот месяц vs прошлый), увидеть разбивку по операторам/странам в виде таблицы с сортировкой и процентами, а также отдельный блок "Стоимость" с расходами по дням/неделям и прогнозом расходов до конца периода.

**Why this priority**: Текущая аналитика показывает только абсолютные числа за один период. Менеджерам нужны сравнения для оценки динамики и прогнозирование расходов для бюджетирования.

**Independent Test**: Выбрать "Сравнить с предыдущим периодом" на странице аналитики - графики показывают два наложенных ряда данных. Открыть вкладку "Стоимость" - видны расходы по дням и прогноз.

**Acceptance Scenarios**:

1. **Given** менеджер на странице аналитики, **When** включает "Сравнение с предыдущим периодом", **Then** на графике отображаются два ряда данных (текущий и предыдущий) с легендой
2. **Given** менеджер переходит на вкладку "По странам", **When** данные загружены, **Then** отображается таблица с колонками: страна, количество, доля (%), стоимость - с сортировкой по любой колонке
3. **Given** менеджер на вкладке "Стоимость", **When** данные загружены, **Then** видны расходы по дням в виде графика и текстовый блок "Прогноз до конца месяца: X руб." — рассчитывается как скользящее среднее за последние 7 дней × оставшиеся дни периода

---

### Edge Cases

- Что происходит при экспорте таблицы с более чем 100 000 записей? Экспорт выполняется асинхронно на сервере с уведомлением о готовности через центр уведомлений.
- Как работает палитра команд, если у менеджера нет прав на некоторые страницы? В результатах отображаются только доступные страницы и действия согласно роли пользователя.
- Что происходит при попытке массового удаления элементов, используемых в активных рассылках? Отображается предупреждение с перечислением зависимых рассылок, удаление блокируется.
- Как ведет себя дашборд, если данные за период не загрузились? Графики показывают skeleton-заглушки, затем сообщение об ошибке с кнопкой "Повторить".
- Что происходит с уведомлениями при потере интернет-соединения? Уведомления загружаются при следующем открытии панели, локальный кеш не используется для критичных данных.

## Requirements *(mandatory)*

### Functional Requirements

**Визуализация данных (Дашборд и Аналитика)**

- **FR-001**: Система ДОЛЖНА отображать на дашборде карточки метрик с индикаторами тренда (процент изменения по сравнению с предыдущим аналогичным периодом)
- **FR-002**: Система ДОЛЖНА отображать на дашборде графики: временной ряд отправок (линейный график), распределение статусов доставки (кольцевая диаграмма), топ стран по трафику (горизонтальная гистограмма)
- **FR-003**: Система ДОЛЖНА поддерживать на странице аналитики интерактивные графики с выбором метрики, периода и возможностью сравнения двух периодов
- **FR-004**: Система ДОЛЖНА показывать тултипы с точными значениями при наведении на элементы графиков
- **FR-005**: Система ДОЛЖНА отображать на вкладке аналитики "Стоимость" расходы по дням и прогноз до конца текущего периода

**Массовые действия**

- **FR-006**: Система ДОЛЖНА предоставлять чекбоксы для выбора элементов в каждой таблице (индивидуально и "Выбрать все на странице")
- **FR-007**: Система ДОЛЖНА отображать контекстную панель массовых действий при выборе хотя бы одного элемента
- **FR-008**: Система ДОЛЖНА поддерживать массовые действия: удаление, экспорт, смена статуса (в зависимости от типа сущности)
- **FR-009**: Система ДОЛЖНА запрашивать подтверждение перед выполнением деструктивных массовых действий с указанием количества затронутых элементов

**Улучшенный мастер рассылки**

- **FR-010**: Система ДОЛЖНА отображать визуальный индикатор прогресса по шагам мастера с возможностью клика по уже заполненным шагам для навигации
- **FR-011**: Система ДОЛЖНА показывать маркеры ошибок валидации на индикаторах незаполненных/невалидных шагов
- **FR-012**: Система ДОЛЖНА сохранять данные всех шагов при навигации между ними без потерь
- **FR-013**: Система ДОЛЖНА отображать на финальном шаге компактную сводку всех параметров рассылки

**Экспорт данных**

- **FR-014**: Система ДОЛЖНА предоставлять кнопку "Экспорт CSV" на каждой странице с таблицей данных
- **FR-015**: Система ДОЛЖНА экспортировать данные с учетом текущих активных фильтров
- **FR-016**: Система ДОЛЖНА поддерживать асинхронный экспорт для больших объемов данных (более 10 000 записей) с индикатором прогресса
- **FR-017**: Система ДОЛЖНА формировать CSV с заголовками колонок на русском языке, соответствующими отображаемым в таблице; кодировка файла — UTF-8 без BOM

**Быстрый поиск (Command Palette)**

- **FR-018**: Система ДОЛЖНА открывать палитру команд по сочетанию Ctrl+K / Cmd+K
- **FR-019**: Система ДОЛЖНА отображать результаты поиска в реальном времени: страницы и действия (статический реестр) + записи из БД (шаблоны, контактные листы, имена отправителей) через API с debounce 300 мс
- **FR-020**: Система ДОЛЖНА поддерживать навигацию по результатам с клавиатуры (стрелки, Enter, Escape)
- **FR-021**: Система ДОЛЖНА показывать только доступные пользователю страницы и действия с учетом его роли и прав

**Inline-валидация форм**

- **FR-022**: Система ДОЛЖНА показывать ошибки валидации в реальном времени при вводе данных в поля форм
- **FR-023**: Система ДОЛЖНА отображать счетчик символов для полей с ограничениями (SMS-сообщение, имя отправителя) с цветовой индикацией приближения к лимиту
- **FR-024**: Система ДОЛЖНА визуально отмечать обязательные поля и подсвечивать все невалидные поля при попытке отправки формы с прокруткой к первой ошибке

**Центр уведомлений**

- **FR-025**: Система ДОЛЖНА отображать иконку уведомлений в хедере с бейджем количества непрочитанных
- **FR-026**: Система ДОЛЖНА показывать выпадающую панель с историей уведомлений, отсортированных по времени
- **FR-027**: Система ДОЛЖНА поддерживать отметку уведомлений как прочитанных (по одному и все сразу)
- **FR-028**: Система ДОЛЖНА позволять переход к связанному объекту по клику на уведомление
- **FR-029**: Фронтенд ДОЛЖЕН опрашивать эндпоинт `GET /notifications` каждые 30–60 секунд для обновления бейджа и списка уведомлений (REST polling; WebSocket/SSE не используются)

### Key Entities

- **Уведомление**: событие в системе, адресованное пользователю (тип события, текст, ссылка на связанный объект, статус прочитанности, время создания); хранится в новой таблице PostgreSQL `notifications` (поля: `id`, `user_id`, `type`, `body`, `object_type`, `object_id`, `is_read`, `created_at`)
- **Задача экспорта**: запрос на формирование файла выгрузки (формат, применённые фильтры, статус готовности, ссылка на сформированный файл, время создания)

## Assumptions

- Библиотека Recharts уже установлена в проекте и используется для графиков в админ-панели - будет переиспользована для клиентского дашборда
- Radix UI уже используется для модалей и дропдаунов - палитра команд и панель уведомлений будут построены на этих же компонентах
- Backend API уже предоставляет данные для аналитики (метрики, статусы) - потребуется добавить эндпоинты для сравнения периодов, уведомлений и асинхронного экспорта
- Существующий компонент DataTable будет расширен чекбоксами и массовыми действиями без нарушения обратной совместимости
- Интерфейс портала используется преимущественно с десктопа; мобильная адаптация новых компонентов выполняется, но не является приоритетом
- Текущая система авторизации и ролей будет использована для фильтрации результатов палитры команд
- Экспорт больших объемов данных потребует серверного эндпоинта для генерации файлов; клиентская генерация CSV используется для объемов до 10 000 записей
