# Feature Specification: Sender Names and Message Templates Registration

**Feature Branch**: `010-sender-names-templates`  
**Created**: 2026-03-31  
**Status**: Draft  
**Input**: User description: "необходимо реализовать механизм регистрации имен отправителей и шаблоны сообщений для них"

## User Scenarios & Testing *(mandatory)*

### User Story 1 — Регистрация имени отправителя (Priority: P1)

Оператор хочет зарегистрировать имя отправителя (Sender ID), которое будет отображаться получателям вместо номера телефона при получении SMS от этого оператора.

**Why this priority**: Без зарегистрированного имени отправителя все SMS будут приходить с обезличенного номера. Это базовая функция, без которой остальные сценарии лишены смысла.

**Independent Test**: Оператор может полностью пройти цикл регистрации (создать заявку → увидеть статус «На рассмотрении») без каких-либо других функций системы.

**Acceptance Scenarios**:

1. **Given** оператор авторизован в личном кабинете, **When** он вводит имя отправителя и нажимает «Зарегистрировать», **Then** система создаёт заявку со статусом «На рассмотрении» и отображает её в списке.
2. **Given** оператор пытается зарегистрировать имя длиннее 11 символов, **When** он подтверждает форму, **Then** система отклоняет запрос с понятным сообщением об ошибке.
3. **Given** оператор пытается зарегистрировать имя, уже зарегистрированное им же, **When** он подтверждает форму, **Then** система отклоняет дублирование с пояснением.
4. **Given** оператор пытается зарегистрировать имя, содержащее специальные символы (кроме пробела), **When** он подтверждает форму, **Then** система отклоняет запрос с указанием допустимого формата.

---

### User Story 2 — Рассмотрение заявок администратором (Priority: P2)

Администратор просматривает поступившие заявки на регистрацию имён отправителей и принимает решение: одобрить или отклонить каждую из них.

**Why this priority**: Без процедуры одобрения нельзя предотвратить злоупотребления (например, использование имён брендов, которым оператор не принадлежит). Одобрение является обязательным шагом перед активацией имени.

**Independent Test**: Администратор может видеть список заявок и одобрять/отклонять их независимо от остальных функций системы.

**Acceptance Scenarios**:

1. **Given** есть заявка на имя отправителя в статусе «На рассмотрении», **When** администратор одобряет её, **Then** имя переходит в статус «Активно» и становится доступным для отправки SMS.
2. **Given** есть заявка на имя отправителя в статусе «На рассмотрении», **When** администратор отклоняет её с указанием причины, **Then** статус меняется на «Отклонено» и оператор видит причину отказа.
3. **Given** администратор смотрит список заявок, **When** он фильтрует по статусу «На рассмотрении», **Then** отображаются только заявки, ожидающие решения.

---

### User Story 3 — Управление шаблонами сообщений (Priority: P3)

Оператор создаёт и управляет шаблонами сообщений, привязанными к зарегистрированному имени отправителя. Шаблон содержит типовой текст с переменными-заполнителями.

**Why this priority**: Шаблоны ускоряют создание рассылок и снижают вероятность ошибок в тексте. Полезная функция, но не блокирует базовую отправку.

**Independent Test**: Оператор может создать шаблон для одобренного имени отправителя, просмотреть его и использовать при составлении рассылки, независимо от других функций.

**Acceptance Scenarios**:

1. **Given** у оператора есть одобренное имя отправителя, **When** он создаёт шаблон с текстом и переменными-заполнителями (например, `{имя}`), **Then** шаблон сохраняется со статусом «На рассмотрении» и недоступен для отправки до одобрения администратором.
2. **Given** оператор выбирает шаблон при создании рассылки, **When** он указывает значения переменных, **Then** система подставляет значения в текст и показывает предпросмотр итогового сообщения.
3. **Given** оператор хочет изменить текст шаблона, **When** он редактирует и сохраняет шаблон, **Then** изменения применяются только к новым рассылкам (ранее отправленные не затрагиваются).
4. **Given** оператор удаляет шаблон, **When** он подтверждает удаление, **Then** шаблон помечается как архивный и недоступен для новых рассылок, но сохраняется в истории.

---

### User Story 4 — Просмотр статусов и истории (Priority: P4)

Оператор может отслеживать статус своих имён отправителей и просматривать историю изменений.

**Why this priority**: Прозрачность состояния заявок снижает нагрузку на поддержку и повышает доверие к системе.

**Independent Test**: Оператор видит полный список своих имён отправителей с текущими статусами и может просмотреть историю изменений каждого.

**Acceptance Scenarios**:

1. **Given** у оператора несколько имён отправителей в разных статусах, **When** он открывает раздел «Имена отправителей», **Then** видит список с чёткими статусами и датами последнего изменения.
2. **Given** имя отправителя было отклонено администратором, **When** оператор просматривает детали, **Then** он видит причину отказа и может отредактировать имя и повторно отправить на рассмотрение.

---

### Edge Cases

- Если два оператора зарегистрировали одинаковое имя отправителя — конфликт не блокируется автоматически; администратор проверяет конфликт при одобрении и может отклонить заявку с пояснением о занятости имени.
- Как система обрабатывает попытку использовать деактивированное имя отправителя для новой рассылки?
- Если шаблон содержит переменную, значение которой не передано при отправке — система блокирует отправку и возвращает явную ошибку с указанием имени пропущенной переменной.
- Как обрабатываются имена отправителей, состоящие только из цифр (числовые Sender ID)?
- Что произойдёт, если оператор удалён из системы — что случится с его именами отправителей?

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Система ДОЛЖНА позволять оператору регистрировать имена отправителей через личный кабинет.
- **FR-002**: Система ДОЛЖНА валидировать формат имени отправителя: допустимы латинские буквы, цифры и пробелы; длина — от 1 до 11 символов; числовые имена — не более 15 цифр (стандарт GSM).
- **FR-003**: Система ДОЛЖНА хранить статус каждого имени отправителя: «На рассмотрении», «Активно», «Отклонено», «Деактивировано». Оператор ДОЛЖЕН иметь возможность отредактировать отклонённое имя и повторно отправить на рассмотрение — статус при этом возвращается в «На рассмотрении».
- **FR-003a**: Аналогичный цикл редактирования и повторной подачи ДОЛЖЕН быть доступен для отклонённых шаблонов сообщений.
- **FR-004**: Администраторы ДОЛЖНЫ иметь возможность одобрять или отклонять заявки на регистрацию с указанием причины.
- **FR-005**: Система ДОЛЖНА запрещать использование имени отправителя для отправки SMS до его одобрения.
- **FR-006**: Система ДОЛЖНА позволять оператору создавать шаблоны сообщений, привязанные к одобренному имени отправителя. Созданный шаблон получает статус «На рассмотрении» и требует одобрения администратора перед использованием.
- **FR-006a**: Администраторы ДОЛЖНЫ иметь возможность одобрять или отклонять шаблоны сообщений с указанием причины отказа (аналогично именам отправителей).
- **FR-007**: Шаблоны ДОЛЖНЫ поддерживать переменные-заполнители в формате `{имя_переменной}`, подставляемые при отправке. Система ДОЛЖНА блокировать отправку и возвращать явную ошибку, если значение хотя бы одной переменной шаблона не передано.
- **FR-008**: Система ДОЛЖНА показывать предпросмотр шаблона с подставленными значениями переменных перед отправкой.
- **FR-009**: Система ДОЛЖНА запрещать регистрацию дублирующего имени от одного оператора.
- **FR-010**: При отклонении заявки администратор ДОЛЖЕН иметь возможность указать причину, которая будет доступна оператору.
- **FR-011**: Система ДОЛЖНА сохранять историю изменений статуса каждого имени отправителя.
- **FR-012**: Удалённые шаблоны ДОЛЖНЫ архивироваться, а не удаляться физически, для сохранения истории рассылок.

### Key Entities

- **SenderName (Имя отправителя)**: Зарегистрированный идентификатор отправителя для SMS. Атрибуты: уникальное значение, владелец-оператор, статус, дата создания, дата изменения статуса, причина отказа (если применимо).
- **MessageTemplate (Шаблон сообщения)**: Типовой текст сообщения с поддержкой переменных. Атрибуты: название, тело шаблона, список переменных, привязка к имени отправителя, статус (активен/архив), дата создания/изменения.
- **SenderNameStatusHistory (История статусов)**: Журнал изменений статуса имени отправителя. Атрибуты: имя отправителя, предыдущий статус, новый статус, дата, инициатор изменения, комментарий.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Оператор может подать заявку на регистрацию имени отправителя менее чем за 2 минуты с момента входа в раздел.
- **SC-002**: Администратор может рассмотреть и обработать заявку менее чем за 1 минуту.
- **SC-003**: 100% заявок с некорректным форматом имени отклоняются системой автоматически до отправки администратору.
- **SC-004**: Оператор видит актуальный статус всех своих имён отправителей без ручного обновления страницы.
- **SC-005**: Оператор может создать шаблон с переменными и получить предпросмотр менее чем за 3 минуты.
- **SC-006**: Имена отправителей, не прошедшие проверку, не могут быть использованы для отправки ни одного SMS.

## Clarifications

### Session 2026-03-31

- Q: Как обрабатывается ситуация, когда два оператора регистрируют одинаковое имя отправителя? → A: Дублирование допускается; администратор при одобрении обязан проверить конфликт и может отклонить заявку с пояснением.
- Q: Требуется ли одобрение администратора для шаблонов сообщений? → A: Да, шаблоны требуют одобрения администратора перед использованием (аналогично именам отправителей).
- Q: Что происходит при отправке, если значение переменной шаблона не передано? → A: Система блокирует отправку и возвращает явную ошибку с указанием пропущенной переменной.
- Q: Могут ли операторы повторно подать заявку после отказа? → A: Да — оператор редактирует отклонённый объект и повторно отправляет на рассмотрение; статус возвращается в «На рассмотрении».
- Q: Есть ли лимит на количество имён отправителей и шаблонов на одного оператора? → A: Нет лимитов — любое количество имён и шаблонов.

## Assumptions

- Пользователи системы — операторы (клиенты SMS-шлюза) и администраторы платформы; конечные получатели SMS не взаимодействуют с этим разделом.
- Каждый оператор может иметь неограниченное количество имён отправителей.
- Каждое имя отправителя может иметь неограниченное количество шаблонов.
- Числовые Sender ID (до 15 цифр) и буквенно-числовые (до 11 символов) обрабатываются по единой логике, но с разными правилами валидации.
- Уведомления оператора об изменении статуса (email/push) выходят за рамки данной функции; достаточно отображения статуса в личном кабинете.
- Шаблоны могут использоваться только с именем отправителя, к которому они привязаны.
- Механизм деактивации имени отправителя администратором (после одобрения) предусматривается, но детали управления жизненным циклом уточняются при планировании.
- Имя отправителя является уникальным в рамках одного оператора; разные операторы могут иметь одинаковые имена — конфликт разрешается администратором при одобрении заявки (не автоматически).
