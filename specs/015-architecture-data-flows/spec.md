# Feature Specification: Архитектура и потоки данных SMS-платформы

**Feature Branch**: `015-architecture-data-flows`  
**Created**: 2026-04-01  
**Status**: Draft  
**Input**: Описание топологии сервисов, gateway-уровня, service mesh, Kafka pipeline и двух изолированных потоков — Campaign и Cascade.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Отправка SMS через кампанию (Priority: P1)

Клиент создаёт рассылку по списку контактов. Система запускает кампанию, материализует сообщения по списку контактов, направляет их через конвейер обработки (batch → router → sender) и доставляет через SMS-провайдера. Клиент видит статус по каждому получателю и итоговый статус кампании.

**Why this priority**: Это основной способ массовой рассылки SMS. Без работающего campaign-потока платформа не выполняет своё главное назначение.

**Independent Test**: Можно протестировать полностью: запустить кампанию с тестовым списком контактов и убедиться, что все сообщения доставлены, а статус кампании стал `completed`.

**Acceptance Scenarios**:

1. **Given** активная кампания с непустым списком контактов, **When** клиент вызывает запуск кампании, **Then** система создаёт записи сообщений со статусом `queued` и начинает их обработку
2. **Given** сообщение успешно доставлено провайдером, **When** приходит статусное уведомление, **Then** статус получателя в кампании обновляется, счётчики кампании инкрементируются
3. **Given** все получатели обработаны, **When** последний статус получен, **Then** кампания переходит в статус `completed`

---

### User Story 2 - Мультиканальная доставка через каскад (Priority: P2)

Клиент инициирует доставку сообщения с каскадной стратегией. Система проверяет доступность получателя по каналам (SMS → Max Messenger → Flash Call) и пытается доставить через первый доступный канал. При неуспехе переходит к следующему каналу стратегии.

**Why this priority**: Каскад повышает процент доставки для абонентов мессенджеров и обеспечивает резервирование по каналам.

**Independent Test**: Можно протестировать отдельно от campaign-потока: создать доставку с каскадной стратегией и проверить переключение между каналами.

**Acceptance Scenarios**:

1. **Given** получатель доступен в первом канале стратегии, **When** создаётся доставка, **Then** сообщение отправляется через первый канал без попытки следующих
2. **Given** первый канал недоступен или доставка не удалась, **When** истекает таймаут канала, **Then** система переходит к следующему каналу в стратегии
3. **Given** webhook-уведомление от Max Messenger, **When** получен статус доставки, **Then** статус попытки доставки обновляется

---

### User Story 3 - Просмотр статуса сообщений через портал (Priority: P3)

Клиент входит в портал и видит историю отправленных сообщений с актуальными статусами. Оператор через Admin Portal видит все сообщения по всем клиентам.

**Why this priority**: Наблюдаемость необходима для управления платформой, но это read-only функциональность поверх уже работающих потоков.

**Independent Test**: Можно протестировать независимо: запросить список сообщений через Portal/Admin Gateway и убедиться в корректности возвращаемых статусов.

**Acceptance Scenarios**:

1. **Given** клиент авторизован в Portal, **When** открывает раздел сообщений, **Then** видит свои сообщения с текущими статусами
2. **Given** администратор авторизован в Admin Portal, **When** запрашивает список сообщений, **Then** видит сообщения всех клиентов

---

### Edge Cases

- Что происходит, если список контактов кампании пустой при запуске?
- Как система ведёт себя при недоступности всех каналов каскада?
- Что происходит при дублировании webhook-уведомления от провайдера?
- Как обрабатывается недоступность очереди сообщений в момент постановки?
- Что происходит при сбое routing-сервиса в середине обработки batch?

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Система ДОЛЖНА принимать запросы на запуск кампании и материализовать сообщения для каждого контакта из списка
- **FR-002**: Система ДОЛЖНА обрабатывать сообщения через конвейер: батчинг → маршрутизация → отправка провайдеру
- **FR-003**: Система ДОЛЖНА обновлять статусы сообщений и счётчики кампании при получении уведомлений о доставке
- **FR-004**: Система ДОЛЖНА поддерживать каскадную доставку с последовательным перебором каналов по стратегии
- **FR-005**: Система ДОЛЖНА проверять доступность получателя в каждом канале перед попыткой отправки, с кешированием результата
- **FR-006**: Система ДОЛЖНА принимать webhook-уведомления от внешних каналов (Max Messenger) и обновлять статусы попыток доставки
- **FR-007**: Campaign-поток и Cascade-поток ДОЛЖНЫ быть полностью изолированы — рассылки не используют каскад
- **FR-008**: Система ДОЛЖНА маршрутизировать входящие запросы через соответствующий gateway в зависимости от типа клиента (Admin / Portal / Client)
- **FR-009**: Взаимодействие между внутренними сервисами ДОЛЖНО происходить через единый внутренний протокол обмена сообщениями
- **FR-010**: Система ДОЛЖНА обеспечивать наблюдаемость: метрики по каждому потоку, статусы сообщений доступны через API

### Key Entities

- **Message**: Отдельное SMS-сообщение; содержит получателя, текст, статус, провайдера
- **Campaign**: Рассылка по списку контактов; содержит счётчики (queued/sent/delivered/failed) и общий статус
- **CampaignRecipient**: Связь кампании с конкретным контактом; содержит индивидуальный статус доставки
- **Delivery**: Запрос на мультиканальную доставку через каскадную стратегию
- **DeliveryAttempt**: Одна попытка доставки в рамках конкретного канала; содержит канал, статус, временные метки
- **DeliveryStrategy**: Описание порядка каналов и условий переключения между ними
- **ContactList**: Список контактов, используемый кампанией для материализации получателей

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Кампания с 10 000 получателей запускается и начинает обработку в течение 30 секунд после вызова launch
- **SC-002**: Статус доставки каждого сообщения обновляется в течение 5 секунд после получения уведомления от провайдера
- **SC-003**: При каскадной доставке переключение на следующий канал происходит в течение настроенного таймаута без ручного вмешательства
- **SC-004**: Система корректно обрабатывает дублирующиеся статусные уведомления — итоговый статус не меняется при повторном получении того же события
- **SC-005**: Все запросы к Admin/Portal/Client API аутентифицированы — неавторизованные запросы отклоняются на уровне gateway
- **SC-006**: Изоляция потоков подтверждена: запуск кампании не создаёт записей в разделе каскада и наоборот

## Assumptions

- Кампания предполагает отправку только через SMS-канал; мультиканальность реализуется исключительно через Cascade
- Кеш доступности получателя имеет TTL 1 час; свежесть данных в этом интервале считается приемлемой
- Webhook-уведомления от провайдеров защищены подписью; неподписанные запросы отклоняются
- Масштабирование воркеров конвейера выходит за рамки данной спецификации
- Порядок каналов в каскадной стратегии фиксирован при создании и не меняется в процессе доставки
- Admin Portal имеет доступ ко всем данным всех клиентов; Portal и Client API видят только свои данные
