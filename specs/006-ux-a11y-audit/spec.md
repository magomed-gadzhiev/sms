# Feature Specification: UX/UI and Accessibility Audit

**Feature Branch**: `006-ux-a11y-audit`
**Created**: 2026-03-21
**Status**: Draft
**Input**: User description: "UX/UI and Accessibility audit of the SMS gateway web application portal"

---

## Обзор

Аудит охватывает `portal-frontend` — React 19 + Vite SPA (16 файлов). Страницы: Login, PasswordReset, Dashboard, Messages, API Keys, Webhooks, Analytics, Sub-accounts, Profile, Audit Log, Layout/Navigation.

---

## User Scenarios & Testing *(mandatory)*

### User Story 1 — Вход и навигация (Priority: P1)

Пользователь открывает портал, вводит email/пароль, при необходимости проходит 2FA, попадает на Dashboard и перемещается по боковой навигации.

**Why this priority**: Аутентификация и первичная навигация — точка входа. Нарушения здесь блокируют доступ ко всему продукту.

**Independent Test**: Открыть `/login`, войти, убедиться что навигация доступна с клавиатуры и ведёт на правильные страницы.

**Acceptance Scenarios**:

1. **Given** форма логина открыта, **When** сервер вернул ошибку аутентификации, **Then** сообщение об ошибке программно связано с формой через `aria-live="polite"` и читается скринридером без ручного перемещения фокуса.
2. **Given** 2FA включён и показана форма TOTP, **When** пользователь нажимает Tab, **Then** поле кода TOTP получает фокус и его label отображается.
3. **Given** пользователь вошёл, **When** он нажимает Tab в навигационной панели, **Then** все 8 пунктов меню доступны в логичном порядке, а активный пункт помечен `aria-current="page"`.
4. **Given** пользователь в навигации, **When** он нажимает Enter на пункте меню, **Then** происходит переход на соответствующую страницу.

---

### User Story 2 — Просмотр и фильтрация сообщений (Priority: P2)

Пользователь заходит на Messages, применяет фильтры по статусу/дате/получателю и листает страницы.

**Why this priority**: Messages — основная рабочая область оператора, наиболее часто используемая страница.

**Independent Test**: Открыть `/messages`, применить фильтр, убедиться что таблица обновилась и пагинация работает.

**Acceptance Scenarios**:

1. **Given** таблица с длинными текстами сообщений, **When** пользователь фокусируется на ячейке с обрезанным текстом, **Then** доступен способ прочитать полный текст (tooltip, title или отдельная ссылка).
2. **Given** фильтр применён без результатов, **When** пустое состояние отображается, **Then** оно визуально отличимо не только цветом текста.
3. **Given** пользователь на последней странице, **When** кнопка "Next" отключена, **Then** она имеет `aria-disabled="true"` и смысловой `aria-label="Next page"`.

---

### User Story 3 — Создание API Key (Priority: P2)

Пользователь нажимает "Create API Key", заполняет форму, получает ключ и копирует его.

**Why this priority**: Критический сценарий — ключ показывается только один раз.

**Independent Test**: Открыть `/api-keys`, создать ключ, убедиться что банер озвучивается скринридером и ключ можно скопировать.

**Acceptance Scenarios**:

1. **Given** ключ создан и банер появился, **When** скринридер активен, **Then** банер имеет `role="alert"` и его содержимое автоматически зачитывается.
2. **Given** форма создания открыта, **When** пользователь нажимает Escape, **Then** форма закрывается и фокус возвращается на кнопку "Create API Key".
3. **Given** форма создания открыта, **When** пользователь нажимает Tab внутри формы, **Then** фокус не уходит за пределы формы (focus trap).

---

### User Story 4 — Настройка 2FA в профиле (Priority: P3)

Пользователь открывает Profile, настраивает или отключает 2FA.

**Why this priority**: Важный security-flow, но менее частый.

**Independent Test**: Открыть `/profile`, пройти полный цикл включения и отключения 2FA.

**Acceptance Scenarios**:

1. **Given** секрет TOTP показан как `<code>` блок, **When** пользователь хочет скопировать вручную, **Then** рядом присутствует кнопка "Copy" (аналогично QR-коду).
2. **Given** 2FA успешно включён, **When** появляется сообщение "2FA enabled successfully", **Then** элемент имеет `role="status"` и озвучивается скринридером.
3. **Given** профиль загружается, **When** состояние `loading`, **Then** индикатор загрузки имеет `role="status"` или `aria-live`.

---

### Edge Cases

- Что происходит при потере сети во время отправки формы — нет offline-индикации.
- Как пользователь со скринридером понимает таблицу Sub-accounts с 8 столбцами без `<caption>`.
- Как работает редирект `/dashboard` без авторизации — `<div>Loading...</div>` без `aria-live` невидим для AT.

## Requirements *(mandatory)*

### Критические проблемы доступности (WCAG 2.1 AA)

- **FR-001**: Все сообщения об ошибках форм ДОЛЖНЫ программно связываться с соответствующими полями через `aria-describedby`. Текущее состояние: `<p style={{ color: 'red' }}>` над формой без связи — нарушение WCAG 1.3.1 и 3.3.1.
- **FR-002**: Динамически появляющийся контент (банеры API Key/Webhook Secret, уведомления, ошибки) ДОЛЖЕН иметь `role="alert"` или `aria-live`. Текущее состояние: все банеры рендерятся в DOM без объявления для AT.
- **FR-003**: Кнопки действий в таблицах ДОЛЖНЫ иметь контекстный `aria-label`. Текущее состояние: кнопки "Revoke" и "Delete" не указывают, к какому элементу относятся — нарушение WCAG 2.4.6.
- **FR-004**: Активный пункт навигации ДОЛЖЕН помечаться `aria-current="page"`. Текущее состояние: активность передаётся только через `fontWeight: 'bold'` — визуальный маркер без семантики.
- **FR-005**: Формы-в-потоке (Create API Key, Create Webhook, Edit Webhook) ДОЛЖНЫ реализовывать focus trap. Текущее состояние: при открытии формы фокус не перемещается внутрь неё.
- **FR-006**: Все таблицы ДОЛЖНЫ иметь `<caption>` или `aria-label`. Текущее состояние: ни одна таблица не имеет заголовка для скринридера.

### Проблемы семантики HTML

- **FR-007**: `<nav>` в Layout ДОЛЖЕН иметь `aria-label="Main navigation"`. Текущее состояние: `<nav>` без метки — при наличии нескольких landmarks скринридер не различает их.
- **FR-008**: Загрузочные состояния ДОЛЖНЫ использовать `role="status"` или `aria-live="polite"`. Текущее состояние: `<div>Loading...</div>`, `<div>Loading dashboard...</div>` и аналоги — нет объявления для AT.
- **FR-009**: Skip-link "Skip to main content" ДОЛЖЕН присутствовать как первый элемент страницы. Текущее состояние: отсутствует полностью — нарушение WCAG 2.4.1.
- **FR-010**: `<main>` в Layout ДОЛЖЕН иметь `id="main-content"` для target skip-link.

### Проблемы UX и User Flow

- **FR-011**: Карточки метрик на Dashboard ДОЛЖНЫ быть кликабельными ссылками на соответствующие разделы. Текущее состояние: `<div>` без ссылок, пользователь не может кликнуть на "Active API Keys: 3" чтобы перейти к ключам.
- **FR-012**: Активный пункт навигации ДОЛЖЕН иметь дополнительный визуальный маркер помимо жирного шрифта (цвет, фон, border-left). Текущее состояние: только `fontWeight: 'bold'` — недостаточный контраст визуального различия.
- **FR-013**: Кнопка "Logout" ДОЛЖНА быть визуально отделена от навигационных пунктов не менее чем на 16px отступа сверху. Текущее состояние: расположена сразу под `<hr>` вплотную к меню — риск случайного нажатия.
- **FR-014**: Текст сообщений в таблице Messages ДОЛЖЕН быть доступен полностью. Текущее состояние: `overflow: hidden; text-overflow: ellipsis` без `title` атрибута или tooltip — пользователь не может прочитать обрезанный текст.
- **FR-015**: Секция фильтров Analytics ДОЛЖНА быть обёрнута в `<fieldset>/<legend>` для группировки связанных элементов управления.
- **FR-016**: Статусные индикаторы (Active/Revoked, Active/Inactive, Yes/No) ДОЛЖНЫ передавать смысл не только цветом. Текущее состояние: только `color: #4caf50` и `color: #f44336` — нарушение WCAG 1.4.1 (Use of Color).
- **FR-017**: Кнопки пагинации ДОЛЖНЫ иметь `aria-label` ("Previous page", "Next page") и передавать текущую позицию. Текущее состояние: кнопки "Prev"/"Next" без контекста, информация о странице в тексте без `aria-live`.

### Проблемы размеров и touch targets

- **FR-018**: Все интерактивные элементы ДОЛЖНЫ иметь минимальный размер 44×44px. Текущее состояние: кнопки с `padding: '4px 12px'` дают ~28px высоты — нарушение WCAG 2.5.5 (AAA) и лучших практик мобильной доступности.

### Ключевые сущности

- **Layout/Navigation**: боковая панель с 8 пунктами меню, кнопкой Logout, email пользователя — центральный паттерн всего приложения.
- **Форма-в-потоке**: раскрываемая форма внутри страницы (без модального диалога) — используется в API Keys, Webhooks, Sub-accounts.
- **Однократный банер**: критический паттерн показа секретных данных (API Key, Webhook Secret) — показывается только один раз после создания.
- **Таблица с пагинацией**: используется в Messages и Audit Log.
- **Статусный индикатор**: цветовой маркер состояния активности — используется в API Keys, Webhooks, Sub-accounts.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 0 нарушений категорий "critical" и "serious" при автоматической проверке axe DevTools по всем 10 страницам.
- **SC-002**: 100% интерактивных элементов имеют видимый focus indicator при навигации Tab по всем страницам.
- **SC-003**: Все сообщения об ошибках, уведомления и банеры корректно озвучиваются NVDA/VoiceOver без ручного перемещения фокуса пользователем.
- **SC-004**: Пользователь может выполнить полный сценарий "Вход → просмотр Messages → создание API Key" используя только клавиатуру.
- **SC-005**: Ни один визуальный статус-индикатор не передаёт информацию исключительно через цвет — все статусы имеют текстовый или иконочный дублёр.
- **SC-006**: Контраст текст/фон для всех элементов ≥ 4.5:1 (нормальный текст) и ≥ 3:1 (крупный текст и UI-компоненты) по WCAG 2.1 AA.
- **SC-007**: Skip-link "Skip to main content" присутствует и корректно переносит фокус в основной контент при нажатии.

---

## Assumptions

- Аудит охватывает только `portal-frontend/src` — бэкенд и API не рассматриваются.
- Целевая аудитория — технические пользователи (разработчики, операторы), но WCAG 2.1 AA применяется в полном объёме.
- Тёмная тема и мобильная адаптация — вне области данного аудита.
- Отсутствие Design System / CSS-фреймворка является намеренным; рекомендации будут в виде конкретных точечных изменений в существующий код.
- Приоритет исправлений: WCAG-нарушения > UX-улучшения > визуальные улучшения.
