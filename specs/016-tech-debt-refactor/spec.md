# Feature Specification: Technical Debt Reduction and Refactoring

**Feature Branch**: `016-tech-debt-refactor`  
**Created**: 2026-04-01  
**Status**: Draft  
**Input**: User description: "Технический долг и план рефакторинга"

## User Scenarios & Testing *(mandatory)*

### User Story 1 — Единое место для исправления бизнес-логики баланса (Priority: P1)

Инженер обнаруживает ошибку в логике списания или пополнения баланса. Сейчас он вынужден найти и исправить идентичный код в четырёх местах, рискуя пропустить одно из них. После рефакторинга исправление делается в одном месте и автоматически применяется ко всем операциям с балансом.

**Why this priority**: Дублированная бизнес-логика — основной источник трудноуловимых расхождений: исправление в одном месте не распространяется на копии, создавая скрытые баги в производственной среде.

**Independent Test**: Вносим изменение в централизованную функцию изменения баланса и убеждаемся, что все четыре сценария (пополнение/списание с транзакцией и без) ведут себя одинаково — без дополнительных правок.

**Acceptance Scenarios**:

1. **Given** логика изменения баланса централизована в единой функции, **When** инженер исправляет ошибку округления в расчёте, **Then** исправление автоматически применяется ко всем операциям (пополнение/списание, с транзакцией/без) без дополнительных изменений.
2. **Given** существующие тесты покрывают операции с балансом, **When** рефакторинг завершён, **Then** все тесты проходят без изменений в тестовом коде.

### User Story 2 — Единый механизм авторизации для всех шлюзов (Priority: P2)

Инженер добавляет новый шлюз или вносит изменение в правила проверки доступа. Сейчас идентичный код проверки прав скопирован в трёх шлюзах, и обновление требует правок в каждом из них. После рефакторинга достаточно изменить один общий компонент; специфичное поведение отдельных шлюзов остаётся изолированным.

**Why this priority**: Расхождение в реализации авторизации между шлюзами создаёт уязвимости: патч безопасности, применённый к одному шлюзу, не попадает в остальные.

**Independent Test**: Все три шлюза (admin, client, portal) корректно определяют пользователя, роль и проверяют права доступа через одну кодовую базу; специфичный режим нагрузочного тестирования клиентского шлюза при этом сохраняется.

**Acceptance Scenarios**:

1. **Given** функции авторизации централизованы, **When** вносится изменение в правила проверки прав, **Then** изменение вступает в силу во всех трёх шлюзах одновременно без дополнительных правок.
2. **Given** клиентский шлюз поддерживает специальный режим тестирования нагрузки, **When** используется общий компонент авторизации, **Then** специфичное поведение клиентского шлюза сохраняется и не влияет на admin и portal шлюзы.

### User Story 3 — Надёжный failover маршрутизации без скрытых расхождений (Priority: P2)

Оператор наблюдает за доставкой сообщений при отказе провайдера. Сейчас логика переключения на резервный провайдер продублирована в трёх ветках маршрутизатора, и расхождение между копиями приводит к тому, что часть сообщений не переключается корректно. После рефакторинга переключение происходит одинаково при любом способе выбора провайдера.

**Why this priority**: Расхождение в failover-логике между ветками напрямую влияет на доставляемость сообщений — часть трафика может не переключаться на резервный провайдер при сбое.

**Independent Test**: При имитации недоступности основного провайдера все три сценария выбора (по прямому указанию, по маршруту, по умолчанию) одинаково переключаются на резервный провайдер.

**Acceptance Scenarios**:

1. **Given** логика failover централизована, **When** основной провайдер недоступен, **Then** все три способа выбора провайдера одинаково переключаются на резервный и сообщения доставляются.
2. **Given** написаны тесты для failover-сценариев, **When** изменяется политика переключения, **Then** тесты однозначно подтверждают корректность поведения для всех трёх путей маршрутизации.

---

### User Story 4 — Унифицированное поведение пагинации во всём API (Priority: P3)

Клиент интегрируется с API и ожидает предсказуемого поведения при переборе страниц. Сейчас разные части API могут по-разному обрабатывать граничные значения (отрицательный offset, нулевой или избыточно большой limit), создавая непредсказуемость. После рефакторинга все списки следуют одному правилу нормализации.

**Why this priority**: Непоследовательное поведение пагинации затрудняет интеграцию для клиентов API и создаёт скрытые риски при больших значениях limit.

**Independent Test**: Любой список в API при limit=0, limit=10000 и offset=-5 возвращает результат с одинаковыми дефолтными значениями (limit=100, offset=0).

**Acceptance Scenarios**:

1. **Given** параметры пагинации нормализуются в одном месте, **When** клиент передаёт некорректные значения (limit=0, limit>1000, offset<0), **Then** все списки возвращают результат с применёнными дефолтными значениями без ошибки.
2. **Given** добавлен новый список, **When** используется централизованная нормализация, **Then** поведение нового списка автоматически соответствует всем остальным без ручной настройки.

### User Story 5 — Централизованные утилиты для межсервисного взаимодействия (Priority: P3)

Инженер добавляет обработку нового идентификатора в сервисе. Сейчас каждый из 10+ сервисов содержит собственную копию парсинга идентификаторов с потенциально разным поведением при ошибках. После рефакторинга используется единый компонент с предсказуемой обработкой ошибок.

**Why this priority**: Дублирование утилит между 10+ сервисами создаёт техническую нагрузку без добавления ценности; разное поведение при ошибках приводит к трудноотлаживаемым расхождениям.

**Independent Test**: Все сервисы одинаково реагируют на некорректный формат идентификатора (возвращают понятную ошибку вместо паники или молчаливого игнорирования).

**Acceptance Scenarios**:

1. **Given** парсинг идентификаторов централизован, **When** сервис получает некорректный идентификатор, **Then** все сервисы возвращают одинаковую ошибку вместо паники или неопределённого поведения.
2. **Given** middleware восстановления после паник унифицирован, **When** происходит непредвиденная ошибка в любом шлюзе, **Then** система корректно восстанавливается и возвращает понятный ответ клиенту.

---

### Edge Cases

- Что происходит с in-flight транзакциями при поэтапном рефакторинге billing-логики — транзакции, начатые до деплоя, должны завершаться корректно.
- Как ведут себя сервисы в момент деплоя, когда часть инстанций уже использует централизованные утилиты, а часть — ещё нет (rolling update).
- Специфичный режим LOAD_TEST_MODE клиентского шлюза должен явно изолироваться при объединении auth-логики и не влиять на prod-трафик.
- Граничные значения пагинации: что происходит при limit=1 (минимальный допустимый), limit=1000 (максимальный допустимый).

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Система ДОЛЖНА обеспечить единое поведение всех операций изменения баланса (пополнение/списание) независимо от наличия внешней транзакции.
- **FR-002**: Все шлюзы ДОЛЖНЫ использовать общую реализацию определения пользователя, роли и проверки прав доступа.
- **FR-003**: Клиентский шлюз ДОЛЖЕН сохранить поддержку режима нагрузочного тестирования, изолированного от поведения остальных шлюзов.
- **FR-004**: Логика переключения на резервного провайдера ДОЛЖНА применяться одинаково при всех способах выбора провайдера.
- **FR-005**: Все списки в API ДОЛЖНЫ нормализовать параметры пагинации по единым правилам: limit от 1 до 1000 (по умолчанию 100), отрицательный offset приводится к 0.
- **FR-006**: Все сервисы ДОЛЖНЫ использовать общую реализацию парсинга идентификаторов с единым поведением при ошибке.
- **FR-007**: Все шлюзы ДОЛЖНЫ использовать единый механизм перехвата и обработки непредвиденных ошибок.
- **FR-008**: Все существующие автотесты ДОЛЖНЫ проходить после завершения каждого этапа рефакторинга без изменений в тестовом коде.
- **FR-009**: Публичные интерфейсы (REST endpoints, gRPC контракты) НЕ ДОЛЖНЫ изменяться в ходе рефакторинга.

### Key Entities

- **Shared Authorization Component**: Общий компонент проверки доступа, используемый всеми шлюзами; поддерживает расширение специфичным поведением для отдельных шлюзов.
- **Balance Operation**: Атомарное изменение баланса (пополнение или списание) с опциональной поддержкой внешней транзакции.
- **Provider Resolution**: Процесс выбора провайдера для доставки сообщения с единой логикой автоматического переключения на резервного при отказе.
- **Pagination Parameters**: Параметры запроса списка (limit, offset) с гарантированными граничными значениями, единообразными для всего API.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Объём дублированного кода в затронутых компонентах сокращается не менее чем на 80% от исходных ~900–1200 строк дублирования.
- **SC-002**: 100% существующих автотестов проходят после завершения каждого из этапов 1–3 рефакторинга.
- **SC-003**: Исправление в централизованном компоненте распространяется на всех потребителей без дополнительных правок — подтверждается ревью кода (0 мест с копированием логики).
- **SC-004**: При добавлении нового шлюза объём необходимого шаблонного кода авторизации сокращается на 60% по сравнению с текущим подходом.
- **SC-005**: Все API-ручки со списками демонстрируют идентичное поведение пагинации при граничных значениях — подтверждается единым набором параметризованных тестов.
- **SC-006**: Публичный API (REST и gRPC контракты) остаётся неизменным после завершения рефакторинга — подтверждается отсутствием breaking changes в diff.

## Assumptions

- Рефакторинг проводится поэтапно; каждый этап завершается и деплоится независимо, не блокируя следующий.
- Этапы 1–3 не изменяют публичный API и бизнес-логику — только внутреннюю структуру кода.
- Этапы 4 (campaign-функциональность) и 5 (proto-стандартизация) выходят за рамки данной спецификации: они добавляют новую ценность пользователям, а не устраняют дублирование, и будут описаны отдельными спецификациями.
- Команда имеет доступ ко всем затронутым компонентам для синхронного обновления зависимостей в рамках каждого этапа.
- Существующее покрытие автотестами достаточно для верификации корректности поведения после рефакторинга.
- Специфичное поведение LOAD_TEST_MODE в клиентском шлюзе документировано и может быть изолировано при объединении auth-компонента.
- Сервисы развёртываются атомарно в рамках одного этапа; частичный rollout (часть сервисов с новым кодом, часть со старым) не поддерживается.
