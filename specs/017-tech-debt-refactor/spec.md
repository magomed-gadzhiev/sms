## User Scenarios & Testing *(mandatory)*

### User Story 1 - Устранение дублирования кода в бэкенде (Priority: P1)

Разработчик вносит изменения в логику валидации клиента или обработки ошибок и хочет изменить это в одном месте, а не в 8+ методах. Повторяющийся код клиентской авторизации в gRPC-сервере и обработки ошибок БД консолидируется в переиспользуемые компоненты.

**Why this priority**: Дублирование кода — главный источник багов при изменениях, когда один из 8 копий обновляется, а остальные нет. Прямое влияние на скорость и качество разработки.

**Independent Test**: Можно протестировать, вызвав любой gRPC-метод клиентского API и убедившись, что авторизация работает через middleware, а не через inline-код.

**Acceptance Scenarios**:

1. **Given** gRPC-запрос без client ID в контексте, **When** вызывается любой метод API, **Then** возвращается ошибка Unauthenticated через единый middleware
2. **Given** gRPC-запрос с несовпадающим client ID, **When** вызывается метод API, **Then** возвращается PermissionDenied через единый middleware
3. **Given** ошибка БД "запись не найдена", **When** репозиторий обрабатывает ошибку, **Then** используется единая helper-функция для преобразования в domain-ошибку

### User Story 2 - Исправление проблем с производительностью и утечками памяти (Priority: P1)

Система работает стабильно под нагрузкой без утечек памяти и без N+1 запросов при маршрутизации сообщений. Round-robin индекс не растёт бесконечно, а health-check провайдеров загружается одним batch-запросом.

**Why this priority**: Утечки памяти и N+1 запросы приводят к деградации производительности и потенциальным падениям в продакшене.

**Independent Test**: Можно протестировать, запустив нагрузочный тест на маршрутизацию и убедившись, что потребление памяти стабильно, а количество SQL-запросов не растёт линейно с количеством провайдеров.

**Acceptance Scenarios**:

1. **Given** 10 активных провайдеров, **When** выполняется маршрутизация сообщения, **Then** health-check данные загружаются одним SQL-запросом
2. **Given** система работает 24 часа, **When** round-robin selector обрабатывает маршруты, **Then** карта индексов не превышает текущее количество активных маршрутов
3. **Given** провайдер удалён из конфигурации, **When** запускается очистка round-robin, **Then** его запись удаляется из индекса

---

### User Story 3 - Консолидация констант и устранение магических значений (Priority: P2)

Разработчик может найти все статусы сообщений, таймауты и конфигурационные значения в одном месте. Изменение таймаута или статуса требует правки одного файла, а не поиска по всему проекту.

**Why this priority**: Магические строки и числа усложняют поддержку и приводят к несогласованности при изменениях.

**Independent Test**: Можно протестировать grep-ом по проекту на наличие hardcoded строк типа "DELIVRD", "EXPIRED", убедившись что они используются только из центрального пакета констант.

**Acceptance Scenarios**:

1. **Given** DLR-статус "DELIVRD" приходит от провайдера, **When** DLR-сервис обрабатывает статус, **Then** используется константа из центрального пакета, а не строковый литерал
2. **Given** необходимо изменить таймаут подключения к SMSC, **When** разработчик обновляет конфигурацию, **Then** достаточно изменить одно значение в конфигурации сервиса

---

### User Story 4 - Удаление мёртвого кода и заглушек (Priority: P2)

Кодовая база не содержит неработающих заглушек, неиспользуемых адаптеров и TODO-комментариев без плана реализации. Каждый компонент либо полностью реализован, либо удалён.

**Why this priority**: Мёртвый код создаёт ложные ожидания, увеличивает когнитивную нагрузку и может маскировать реальные проблемы.

**Independent Test**: Можно протестировать статическим анализом кода — все экспортируемые функции должны иметь вызовы, все TODO должны иметь issue или быть удалены.

**Acceptance Scenarios**:

1. **Given** SMPPConnectionAdapter с методом "not implemented", **When** код ревью проверяет адаптер, **Then** адаптер либо полностью реализован, либо удалён
2. **Given** неиспользуемая конвертация в analytics_service, **When** анализируется код, **Then** неиспользуемые вычисления удалены

---

### User Story 5 - Улучшение обработки ошибок и устранение тихих сбоев (Priority: P2)

Система корректно логирует и обрабатывает все ошибки. Ни одна ошибка не проглатывается молча, все сбои приводят к информативным записям в логах и корректному восстановлению.

**Why this priority**: Тихие сбои — самые сложные для диагностики проблемы в продакшене.

**Independent Test**: Можно протестировать, имитируя сбои (Kafka недоступен, БД таймаут) и проверяя что все ошибки залогированы.

**Acceptance Scenarios**:

1. **Given** ошибка публикации события в Kafka, **When** DLR-сервис обрабатывает статус, **Then** ошибка логируется на уровне Error (не Warn) и включается в метрики
2. **Given** ошибка парсинга AllowedSourceAddresses, **When** репозиторий загружает клиента, **Then** ошибка логируется и возвращается вызывающему коду
3. **Given** race condition между Kafka publish и DB update в scheduler, **When** одна операция успешна, а вторая нет, **Then** выполняется корректный rollback или компенсация

---

### User Story 6 - Улучшение фронтенда: мемоизация и обработка ошибок (Priority: P3)

Фронтенд-компоненты работают эффективно с мемоизацией вычисляемых данных и корректно обрабатывают ошибки API-запросов, не допуская тихих сбоев и повторных действий пользователя.

**Why this priority**: Фронтенд-проблемы влияют на пользовательский опыт, но менее критичны чем бэкенд-стабильность.

**Independent Test**: Можно протестировать, проверив что React DevTools Profiler не показывает лишних ререндеров, и что ошибки API отображаются пользователю.

**Acceptance Scenarios**:

1. **Given** таблица кампаний с 50 записями, **When** компонент ререндерится, **Then** columns и обработчики создаются через useMemo/useCallback
2. **Given** ошибка при удалении кампании, **When** пользователь нажимает "Удалить", **Then** кнопка блокируется на время запроса и ошибка отображается
3. **Given** ошибка API в любом компоненте, **When** Promise отклоняется, **Then** ошибка обрабатывается и показывается пользователю, а не игнорируется

---

### Edge Cases

- Что происходит при одновременном обновлении health-check данных во время маршрутизации?
- Как round-robin selector ведёт себя при удалении/добавлении провайдеров во время работы?
- Как система восстанавливается при частичном сбое (Kafka доступен, БД нет)?
- Что происходит с мемоизированными данными при hot-reload фронтенда?

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Система ДОЛЖНА использовать единый gRPC middleware для валидации client ID вместо дублирования в каждом методе
- **FR-002**: Система ДОЛЖНА использовать единый helper для преобразования ошибок "запись не найдена" из БД в domain-ошибки
- **FR-003**: Система ДОЛЖНА загружать health-check данные всех провайдеров одним batch-запросом при маршрутизации
- **FR-004**: Система ДОЛЖНА ограничивать размер round-robin индекса и периодически очищать устаревшие записи
- **FR-005**: Система ДОЛЖНА определять все DLR-статусы и таймауты как именованные константы в центральном пакете
- **FR-006**: Система ДОЛЖНА логировать все ошибки с уровнем Error (не Warn) для ошибок влияющих на бизнес-логику
- **FR-007**: Система ДОЛЖНА удалить неиспользуемый SMPPConnectionAdapter или реализовать его полностью
- **FR-008**: Система ДОЛЖНА использовать useMemo/useCallback для вычисляемых данных и обработчиков событий в React-компонентах
- **FR-009**: Система ДОЛЖНА блокировать UI-элементы во время выполнения мутирующих API-запросов
- **FR-010**: Система ДОЛЖНА корректно обрабатывать все Promise rejection в фронтенд-компонентах

### Key Entities

- **GRPCMiddleware**: Компонент перехвата запросов для валидации клиентской авторизации, извлекает client ID из контекста и проверяет права доступа
- **DLRStatus**: Перечисление статусов доставки сообщений (DELIVRD, EXPIRED, REJECTD, UNDELIV и др.) с маппингом на внутренние состояния
- **ProviderHealth**: Агрегированные данные о состоянии провайдеров, загружаемые batch-запросом для маршрутизации
- **RoundRobinState**: Состояние round-robin селектора с ограниченным размером и механизмом очистки

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Количество дублированных блоков кода авторизации сокращается с 8+ до 1 (middleware)
- **SC-002**: Количество SQL-запросов при маршрутизации одного сообщения сокращается с N (количество провайдеров) до 1
- **SC-003**: Потребление памяти round-robin selector стабильно и не растёт со временем при постоянной нагрузке
- **SC-004**: 100% ошибок бизнес-логики логируются на уровне Error или выше
- **SC-005**: Все магические строки DLR-статусов заменены на именованные константы (0 hardcoded строк статусов в бизнес-логике)
- **SC-006**: Количество строк мёртвого кода (заглушки, TODO без issue) сокращается до 0
- **SC-007**: Все мутирующие операции на фронтенде блокируют UI во время выполнения

## Assumptions

- Существующие тесты продолжат проходить после рефакторинга — изменения не затрагивают внешнее поведение
- Проект компилируется и работает на текущей ветке master — рефакторинг базируется на рабочем состоянии
- gRPC interceptor/middleware поддерживается используемой версией google.golang.org/grpc
- Фронтенд использует React 19 с поддержкой хуков useMemo/useCallback
- Удаление мёртвого кода не сломает другие модули — проверяется через полную компиляцию и тесты
