# Feature Specification: Max Messenger Channel

**Feature Branch**: `013-max-messenger-channel`  
**Created**: 2026-04-01  
**Status**: Draft  
**Input**: User description: "Добавить новый канал отправлений — мессенджер Max (российский мессенджер) в систему мультиканальной каскадной доставки"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Отправка сообщения через Max Messenger в каскаде (Priority: P1)

Клиент системы создаёт каскадную доставку со стратегией, включающей канал Max Messenger. Система проверяет, зарегистрирован ли получатель в Max, и если да — отправляет сообщение через бота Max Messenger. Получатель видит сообщение в мессенджере. Если доставка успешна, каскад завершается; если нет — система переходит к следующему шагу.

**Why this priority**: Основная ценность фичи — возможность доставлять сообщения через Max Messenger. Без этого остальные истории не имеют смысла.

**Independent Test**: Можно протестировать, создав доставку с одношаговой стратегией (только Max Messenger) и проверив, что сообщение доставлено получателю в мессенджере.

**Acceptance Scenarios**:

1. **Given** получатель зарегистрирован в Max Messenger и стратегия включает шаг Max Messenger, **When** система выполняет этот шаг каскада, **Then** сообщение отправляется через Max Bot API и получатель видит его в мессенджере.
2. **Given** получатель зарегистрирован в Max Messenger, **When** Max API подтверждает доставку, **Then** попытка (attempt) получает статус «delivered», доставка завершается успешно.
3. **Given** получатель зарегистрирован в Max Messenger, **When** Max API возвращает ошибку отправки, **Then** попытка получает статус «failed», система переходит к следующему шагу каскада.

### User Story 2 - Проверка доступности получателя в Max Messenger (Priority: P1)

Перед попыткой отправки через Max Messenger система проверяет, зарегистрирован ли номер получателя (MSISDN) в мессенджере. Если получатель не зарегистрирован, шаг пропускается без потери времени и средств — каскад сразу переходит к следующему каналу.

**Why this priority**: Без проверки доступности система будет тратить время на таймауты и деньги на неуспешные попытки для пользователей, которых нет в Max.

**Independent Test**: Можно протестировать, отправив запрос проверки для номера, который заведомо не зарегистрирован в Max, и убедившись, что шаг получает статус «skipped».

**Acceptance Scenarios**:

1. **Given** номер получателя зарегистрирован в Max, **When** система проверяет доступность канала Max Messenger, **Then** проверка возвращает «доступен», шаг каскада выполняется.
2. **Given** номер получателя НЕ зарегистрирован в Max, **When** система проверяет доступность канала, **Then** проверка возвращает «недоступен», попытка получает статус «skipped», каскад переходит к следующему шагу без ожидания таймаута.
3. **Given** результат проверки доступности уже закеширован (менее 1 часа назад), **When** система проверяет доступность того же номера, **Then** используется кешированный результат без повторного обращения к Max API.
4. **Given** сервис проверки доступности Max недоступен, **When** система проверяет доступность, **Then** канал считается доступным (fail-open), попытка отправки выполняется.

### User Story 3 - Администрирование канала Max Messenger (Priority: P2)

Администратор платформы может управлять каналом Max Messenger: включать/выключать его, настраивать параметры подключения (URL провайдера, ключи API, идентификатор бота), а также включать канал Max Messenger в стратегии каскадной доставки с нужным порядком и таймаутом.

**Why this priority**: Администрирование необходимо для конфигурации и эксплуатации канала, но существующий интерфейс управления каналами уже есть — нужно лишь добавить в него новый канал.

**Independent Test**: Можно протестировать через админ-интерфейс: создать канал Max Messenger, задать конфигурацию, включить в стратегию, проверить что канал появился в списке доступных.

**Acceptance Scenarios**:

1. **Given** администратор авторизован в системе, **When** он создаёт новый канал с типом Max Messenger и указывает конфигурацию, **Then** канал сохраняется и отображается в списке каналов.
2. **Given** канал Max Messenger создан, **When** администратор добавляет его как шаг в стратегию каскадной доставки, **Then** стратегия сохраняется с шагом Max Messenger в указанном порядке и таймаутом.
3. **Given** канал Max Messenger активен и включён в стратегию, **When** администратор отключает канал, **Then** новые доставки пропускают шаг Max Messenger, но текущие активные попытки завершаются штатно.

---

### User Story 4 - Получение статуса доставки через webhook (Priority: P2)

Max Messenger присылает уведомления о статусе доставки сообщения (доставлено, прочитано, ошибка) через webhook-колбэк. Система принимает эти уведомления и обновляет статус попытки доставки, чтобы каскад мог принять решение о дальнейших действиях.

**Why this priority**: Без webhook-интеграции невозможно получить подтверждение доставки и корректно завершить каскад.

**Independent Test**: Можно протестировать, отправив имитированный webhook-запрос от Max API и проверив, что статус попытки обновился.

**Acceptance Scenarios**:

1. **Given** сообщение отправлено через Max Messenger и попытка в статусе «sent», **When** Max API присылает webhook с подтверждением доставки, **Then** попытка переходит в статус «delivered», доставка завершается успешно.
2. **Given** сообщение отправлено через Max Messenger, **When** Max API присылает webhook с ошибкой, **Then** попытка переходит в статус «failed», каскад переходит к следующему шагу.
3. **Given** доставка уже завершена успешно через другой канал, **When** приходит запоздалый webhook от Max, **Then** попытка получает статус «late_duplicate», повторное списание средств не происходит.

---

### User Story 5 - Тарификация доставки через Max Messenger (Priority: P3)

Попытки доставки через Max Messenger тарифицируются в соответствии с настройками стратегии. Если шаг отмечен как billable, клиенту выставляется стоимость попытки независимо от результата (успех или неудача). Пропущенные шаги (skipped) и запоздалые дубликаты (late_duplicate) не тарифицируются.

**Why this priority**: Тарификация важна для бизнеса, но базовый механизм биллинга уже реализован для других каналов — нужно лишь убедиться, что новый канал корректно в него интегрирован.

**Independent Test**: Можно протестировать, создав доставку с billable-шагом Max Messenger и проверив, что после завершения попытки формируется событие тарификации с корректными данными.

**Acceptance Scenarios**:

1. **Given** шаг Max Messenger в стратегии отмечен как billable, **When** попытка доставки завершается (успешно или с ошибкой), **Then** формируется событие тарификации для клиента.
2. **Given** шаг Max Messenger пропущен из-за недоступности получателя, **When** обрабатывается результат, **Then** тарификация НЕ выполняется.

---

### Edge Cases

- Что происходит, если Max Messenger API временно недоступен во время отправки? Попытка получает статус «failed», каскад переходит к следующему шагу.
- Что происходит, если получатель заблокировал бота в Max? Отправка не удастся — API вернёт ошибку, попытка получает статус «failed».
- Что происходит при одновременной отправке в параллельном режиме каскада через Max и другой канал? Первый успешный результат завершает доставку, остальные помечаются как «late_duplicate».
- Что происходит, если webhook от Max приходит после истечения таймаута шага? Если каскад уже перешёл к следующему шагу или завершился, webhook обрабатывается как запоздалый — попытка помечается «late_duplicate» или «timeout» (в зависимости от текущего статуса).
- Что происходит, если кеш доступности содержит устаревшие данные (пользователь удалил аккаунт Max)? Система попробует отправить, получит ошибку от API, попытка получит статус «failed» — каскад продолжится. Кеш обновится при следующей проверке после истечения TTL.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Система MUST поддерживать новый тип канала доставки — Max Messenger — наряду с существующими (SMS, Flash Call, Reverse Call, Messenger).
- **FR-002**: Система MUST отправлять сообщения получателям через Max Messenger Bot API по номеру телефона (MSISDN). Поддерживаемые типы контента: текст, изображения и кнопки (inline keyboard).
- **FR-003**: Система MUST проверять доступность получателя в Max Messenger перед попыткой отправки, используя API проверки регистрации.
- **FR-004**: Система MUST кешировать результаты проверки доступности с TTL 1 час для снижения нагрузки на внешний API.
- **FR-005**: Система MUST принимать webhook-уведомления от Max Messenger API о статусе доставки (доставлено, ошибка). Подлинность webhook проверяется через HMAC-SHA256 подпись в заголовке запроса; секрет хранится в конфигурации канала.
- **FR-006**: Система MUST корректно обрабатывать таймауты шага Max Messenger и переходить к следующему шагу каскада.
- **FR-013**: Система MUST выполнять экспоненциальный retry при получении HTTP 429 (rate-limit) от Max API — до 3 попыток с backoff 1s→2s→4s. При исчерпании retry попытка помечается как «failed».
- **FR-014**: Система MUST экспортировать Prometheus-метрики для канала Max Messenger: counter по статусам (sent/delivered/failed/skipped), histogram латентности отправки, counter входящих webhook-ов, gauge активных попыток.
- **FR-007**: Система MUST поддерживать конфигурирование канала Max Messenger администратором (URL провайдера, API-ключ, идентификатор бота, таймаут).
- **FR-008**: Система MUST позволять включать канал Max Messenger в стратегии каскадной доставки (как в последовательном, так и в параллельном режимах).
- **FR-009**: Система MUST тарифицировать попытки доставки через Max Messenger в соответствии с настройками billable в стратегии.
- **FR-010**: Система MUST пропускать шаг Max Messenger (статус «skipped»), если получатель не зарегистрирован в мессенджере, без ожидания таймаута.
- **FR-011**: Система MUST обрабатывать запоздалые webhook-уведомления, помечая их как «late_duplicate» без повторной тарификации.
- **FR-012**: Система MUST использовать стратегию fail-open при недоступности сервиса проверки регистрации в Max: считать получателя доступным и пытаться отправить.

### Key Entities

- **Канал Max Messenger**: Новый тип канала доставки. Характеризуется конфигурацией подключения к Max Bot API (URL, ключ, бот). Существует как запись в справочнике каналов.
- **Проверка доступности в Max**: Результат запроса к Max API о регистрации конкретного MSISDN. Кешируется на 1 час. Влияет на решение о пропуске шага каскада.
- **Webhook от Max**: Входящее уведомление от Max API о результате доставки сообщения. Содержит идентификатор попытки, статус и метаданные.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Сообщения через Max Messenger доставляются получателям, зарегистрированным в мессенджере, в течение 20 секунд с момента инициации шага каскада.
- **SC-002**: Шаг Max Messenger пропускается для незарегистрированных получателей менее чем за 1 секунду (благодаря проверке доступности).
- **SC-003**: Каскадные стратегии с участием Max Messenger (например, Max -> SMS) обеспечивают общий показатель доставки не ниже, чем стратегии без Max Messenger.
- **SC-004**: Стоимость доставки через Max Messenger ниже стоимости SMS-канала, что обеспечивает экономию для клиентов при использовании каскада Max -> SMS.
- **SC-005**: 100% запоздалых webhook-уведомлений корректно обрабатываются без двойной тарификации.
- **SC-006**: Администратор может добавить, настроить и включить канал Max Messenger в стратегию за одну сессию работы с интерфейсом.

## Clarifications

### Session 2026-04-01

- Q: Как система должна проверять подлинность входящих webhook-запросов от Max Messenger API? → A: Проверка HMAC-подписи (HMAC-SHA256) в заголовке запроса; секрет задаётся в конфигурации канала.
- Q: Какие типы контента система должна поддерживать при отправке через Max Messenger? → A: Текст + изображения + кнопки (inline keyboard).
- Q: Как система должна обрабатывать rate-limiting со стороны Max Messenger API? → A: Экспоненциальный retry (до 3 попыток, backoff 1s→2s→4s); если исчерпаны — «failed».
- Q: Должен ли получатель первым начать диалог с ботом (opt-in) для получения сообщений? → A: Нет, бот отправляет по MSISDN без предварительного opt-in.
- Q: Какие метрики необходимо экспортировать в Prometheus для канала Max Messenger? → A: Стандартный набор: counter по статусам (sent/delivered/failed/skipped), histogram латентности отправки, counter webhook-ов, gauge активных попыток.

## Assumptions

- Max Messenger предоставляет Bot API для отправки сообщений по номеру телефона (MSISDN) с возможностью проверки регистрации пользователя.
- Max Messenger поддерживает webhook-уведомления о статусе доставки сообщений.
- Max Messenger не зависит от мобильного оператора получателя — доступен через интернет.
- Существующая архитектура каскадной доставки (стратегии, шаги, адаптеры каналов, webhook-обработка, тарификация) полностью реализована и работает для других каналов.
- Бот в Max Messenger уже создан и зарегистрирован — система использует готовые учётные данные бота.
- Получатель должен не блокировать бота для успешной доставки сообщения. Предварительный opt-in (начало диалога с ботом) не требуется — бот отправляет сообщения по MSISDN напрямую.
- Тарифы на доставку через Max Messenger будут настроены администратором отдельно; система использует общий механизм тарификации каскада.
