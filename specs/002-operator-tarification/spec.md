# Feature Specification: Operator-Based SMS Tarification System

**Feature Branch**: `002-operator-tarification`
**Created**: 2026-03-20
**Status**: Draft
**Input**: User description: "Система тарификации SMS на основе операторов с 4 стратегиями биллинга, порогами, периодами и поддержкой зарегистрированных имён отправителей"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Настройка тарификации для оператора (Priority: P1)

Администратор платформы настраивает тарифный план для мобильного оператора. Он выбирает оператора, указывает категорию имени отправителя (общее / платное зарегистрированное / бесплатное зарегистрированное), выбирает стратегию тарификации и задаёт периоды с порогами и ценами.

**Why this priority**: Без настроенных тарифных планов ни одно сообщение не может быть тарифицировано. Это фундамент всей системы.

**Independent Test**: Можно полностью протестировать через админ-интерфейс — создание тарифного плана, периодов, порогов и проверка их корректного сохранения.

**Acceptance Scenarios**:

1. **Given** администратор открывает управление тарификацией, **When** он создаёт тарифный план с стратегией "фиксированная цена" для оператора МТС + категория "общее имя" и задаёт период с одним порогом, **Then** система сохраняет план и он становится активным
2. **Given** администратор создаёт тарифный план с стратегией "пороги", **When** он добавляет пороги (0-100 = 5₽, 101-500 = 4₽, 501+ = 3₽), **Then** система сохраняет все пороги и валидирует их непересечение
3. **Given** для оператора + категории уже существует активный план, **When** администратор пытается создать ещё один, **Then** система отклоняет создание с ошибкой уникальности

---

### User Story 2 - Тарификация сообщения при отправке (Priority: P1)

Клиент API отправляет SMS на номер, привязанный к определённому оператору. Система определяет оператора, находит подходящий тарифный план на основе типа имени отправителя, рассчитывает стоимость по текущему порогу с учётом количества сегментов и списывает средства с баланса.

**Why this priority**: Основной бизнес-процесс — каждое отправляемое сообщение должно быть корректно тарифицировано.

**Independent Test**: Отправка тестового SMS через API с проверкой корректности списания и обновления счётчика использования.

**Acceptance Scenarios**:

1. **Given** настроен тарифный план "фиксированная цена" (2₽ за сегмент) для оператора Билайн + "общее имя", **When** клиент отправляет SMS из 3 сегментов на номер Билайн без зарегистрированного имени, **Then** система списывает 6₽ с баланса клиента
2. **Given** настроен тарифный план "пороги" (0-100 = 5₽, 101+ = 3₽), клиент отправил 99 сегментов, **When** клиент отправляет SMS из 3 сегментов, **Then** система списывает: 1 сегмент × 5₽ + 2 сегмента × 3₽ = 11₽
3. **Given** на балансе клиента 5₽, **When** он отправляет SMS стоимостью 10₽, **Then** система отклоняет отправку с причиной "недостаточно средств"

---

### User Story 3 - Пересчёт при переходе порога (Priority: P1)

При стратегии "пороги с пересчётом", когда клиент пересекает границу порога, все ранее отправленные сообщения за период пересчитываются по новой цене. Разница возвращается на баланс (если новая цена ниже) или доначисляется.

**Why this priority**: Одна из ключевых стратегий тарификации, критична для корректности биллинга.

**Independent Test**: Отправка серии сообщений, доходящих до порога, и проверка автоматического пересчёта с корректировкой баланса.

**Acceptance Scenarios**:

1. **Given** стратегия "пороги с пересчётом" (0-100 = 10₽, 101+ = 8₽), клиент отправил 99 сегментов, **When** клиент отправляет SMS из 3 сегментов, **Then** система списывает стоимость текущего сообщения (1×10₽ + 2×8₽ = 26₽) и возвращает разницу за предыдущие 99 сегментов ((10-8)×99 = 198₽)
2. **Given** у клиента недостаточно средств для доначисления при переходе на более дорогой порог, **When** происходит переход порога, **Then** текущее сообщение отправляется, но создаётся запись о задолженности, и последующие отправки блокируются
3. **Given** пересчёт инициирован, но списание/возврат через billing-service не удался, **Then** система повторяет попытку с экспоненциальным backoff и уведомляет администратора после исчерпания попыток

---

### User Story 4 - Предоплата за период (Priority: P2)

При стратегии "предоплата с порогами" в начале тарифного периода с баланса клиента списывается фиксированная абонентская плата. Далее сообщения тарифицируются по порогам. Остаток предоплаты не возвращается.

**Why this priority**: Важная стратегия, но используется реже остальных.

**Independent Test**: Создание тарифного плана с предоплатой, запуск нового периода и проверка автоматического списания абонентской платы.

**Acceptance Scenarios**:

1. **Given** настроена стратегия "предоплата + пороги" с абонентской платой 5000₽, **When** наступает начало нового тарифного периода, **Then** система автоматически списывает 5000₽ с баланса клиента
2. **Given** у клиента недостаточно средств для абонентской платы, **When** наступает начало периода, **Then** списание откладывается, сообщения по этому плану блокируются, администратор получает уведомление
3. **Given** предоплата списана, **When** тарифный период завершается, **Then** неиспользованный остаток предоплаты не возвращается

---

### User Story 5 - Регистрация имени отправителя (Priority: P2)

Администратор регистрирует имя отправителя (Sender ID) для клиента у конкретного оператора, указывая тип регистрации — платная или бесплатная. Это определяет, какая стратегия тарификации будет применяться при отправке с этим именем.

**Why this priority**: Необходимо для дифференциации тарификации по типу имени.

**Independent Test**: Регистрация Sender ID через админ-панель и проверка, что при отправке с этим именем применяется корректный тарифный план.

**Acceptance Scenarios**:

1. **Given** оператор МТС поддерживает платную регистрацию, **When** администратор регистрирует имя "MYSHOP" для клиента X с типом "платная", **Then** система создаёт регистрацию со статусом "active"
2. **Given** оператор не поддерживает бесплатную регистрацию, **When** администратор пытается зарегистрировать бесплатное имя, **Then** система отклоняет запрос
3. **Given** клиент имеет зарегистрированное платное имя у оператора, **When** он отправляет SMS с этим именем, **Then** тарификация идёт по тарифному плану категории "paid_registered"

---

### User Story 6 - Управление странами и операторами (Priority: P2)

Администратор создаёт справочники стран и операторов с привязкой префиксов номеров. Это обеспечивает определение оператора по номеру получателя при маршрутизации.

**Why this priority**: Справочные данные, необходимые для работы тарификации, но создаются однократно.

**Independent Test**: Создание страны, оператора с префиксами и проверка корректного определения оператора по номеру.

**Acceptance Scenarios**:

1. **Given** администратор создаёт страну "Россия" (RU, +7, RUB) и оператора "МТС" с префиксами +7900, +7910, **When** система обрабатывает сообщение на +79001234567, **Then** определяется оператор МТС и страна Россия
2. **Given** существуют перекрывающиеся префиксы (+790 и +7900), **When** определяется оператор для +79001234567, **Then** выбирается более длинный/приоритетный префикс
3. **Given** для номера не найден ни один префикс, **When** система обрабатывает сообщение, **Then** оператор не определён, сообщение отклоняется с причиной "unknown_operator"

---

### User Story 7 - Просмотр использования и статистики (Priority: P3)

Администратор просматривает текущие счётчики использования клиентов — количество отправленных сегментов за период, текущий порог, применённую стратегию. Это позволяет мониторить потребление и прогнозировать затраты.

**Why this priority**: Мониторинг важен, но не блокирует основную функциональность.

**Independent Test**: Отправка нескольких сообщений и проверка корректности отображения счётчиков через admin API.

**Acceptance Scenarios**:

1. **Given** клиент отправил 150 сегментов по тарифному плану с порогами, **When** администратор запрашивает статистику использования, **Then** видит счётчик 150, текущий порог и цену за сегмент
2. **Given** у клиента есть использование по нескольким тарифным планам (разные операторы), **When** запрашивается список, **Then** отображаются все счётчики с группировкой по тарифному плану

---

### Edge Cases

- Что происходит, если сообщение из нескольких сегментов пересекает границу порога (часть сегментов по одной цене, часть по другой)?
- Что происходит при одновременной отправке двух сообщений одним клиентом по одному тарифному плану (конкурентный доступ к счётчику)?
- Что происходит, если администратор изменяет пороги тарифного плана посреди активного периода?
- Что происходит, если период тарифов выходит за границы периода уровней (нарушение вложенности)?
- Что происходит при пересчёте, если клиент уже потратил возвращённые средства до завершения Saga?
- Что происходит при повторной обработке одного и того же сообщения (идемпотентность)?

## Requirements *(mandatory)*

### Functional Requirements

**Справочники (routing-service)**

- **FR-001**: Система MUST позволять создавать, редактировать и деактивировать страны с указанием ISO-кода, телефонного кода и валюты
- **FR-002**: Система MUST позволять создавать, редактировать и деактивировать операторов с привязкой к стране и указанием поддерживаемых типов регистрации имён
- **FR-003**: Система MUST позволять привязывать к оператору номерные префиксы с приоритетами
- **FR-004**: Система MUST определять оператора по номеру получателя — сначала по префиксам, затем через MNP (если доступен)
- **FR-005**: Система MUST обогащать сообщение идентификаторами оператора и страны при маршрутизации

**Регистрация имён (tarification-service)**

- **FR-006**: Система MUST позволять регистрировать имя отправителя (Sender ID) для конкретного клиента у конкретного оператора с указанием типа (платное / бесплатное)
- **FR-007**: Система MUST валидировать, что оператор поддерживает указанный тип регистрации
- **FR-008**: Система MUST определять категорию имени отправителя при тарификации: "shared" (нет регистрации), "paid_registered" или "free_registered"

**Тарифные планы (tarification-service)**

- **FR-009**: Система MUST позволять создавать тарифный план для комбинации оператор + категория имени с выбором одной из 4 стратегий
- **FR-010**: Система MUST обеспечивать уникальность активного тарифного плана для комбинации оператор + категория имени
- **FR-011**: Система MUST поддерживать 4 стратегии тарификации: фиксированная цена, пороги, пороги с пересчётом, предоплата с порогами

**Периоды и пороги (tarification-service)**

- **FR-012**: Система MUST позволять задавать произвольные тарифные периоды (дата начала — дата окончания) без пересечений внутри одного плана
- **FR-013**: Система MUST позволять задавать пороги (от количества сегментов → цена за сегмент) внутри тарифного периода
- **FR-014**: Система MUST позволять задавать ценовые периоды (pricing periods), которые полностью вложены в один тарифный период
- **FR-015**: Система MUST отклонять создание ценового периода, если он выходит за границы тарифного периода

**Тарификация (tarification-service)**

- **FR-016**: Система MUST тарифицировать каждое сообщение по стратегии, определённой для оператора + категории имени
- **FR-017**: Система MUST учитывать каждый сегмент сообщения как отдельную единицу для подсчёта порогов
- **FR-018**: Система MUST вести счётчик использования (сегментов) для каждого клиента в рамках тарифного плана и периода
- **FR-019**: При стратегии "пороги с пересчётом" система MUST пересчитывать все предыдущие сегменты за период по новой цене при переходе порога
- **FR-020**: При стратегии "предоплата + пороги" система MUST списывать абонентскую плату в начале периода; остаток не возвращается
- **FR-021**: Система MUST обеспечивать идемпотентность тарификации через уникальный ключ

**Взаимодействие с billing-service**

- **FR-022**: Система MUST инициировать списание (charge) через billing-service при тарификации сообщения
- **FR-023**: Система MUST инициировать возврат (refund) или доначисление (charge) через billing-service при пересчёте
- **FR-024**: При неуспешном списании/возврате система MUST использовать Saga с компенсирующими транзакциями
- **FR-025**: Система MUST отклонять отправку сообщения при недостаточном балансе
- **FR-026**: При невозможности доначисления после пересчёта система MUST фиксировать задолженность и блокировать последующие отправки

**Валюта**

- **FR-027**: Валюта тарификации MUST определяться по стране оператора

### Key Entities

- **Country**: Страна с ISO-кодом, телефонным кодом и валютой. Привязана к операторам
- **Operator**: Мобильный оператор, принадлежит стране. Определяет поддержку типов регистрации имён (платная/бесплатная)
- **OperatorPrefix**: Телефонный префикс, привязанный к оператору. Используется для определения оператора по номеру
- **SenderRegistration**: Регистрация имени отправителя для клиента у оператора. Имеет тип (платное/бесплатное) и статус
- **TariffPlan**: Тарифный план — связка оператора, категории имени и стратегии тарификации. Уникален для пары оператор + категория
- **TariffPeriod**: Временной период действия порогов внутри тарифного плана. Не пересекается с другими периодами того же плана
- **TariffTier**: Порог — определяет цену за сегмент начиная с определённого количества отправленных сегментов
- **PricingPeriod**: Период действия цен, полностью вложен в один TariffPeriod
- **PrepaidFee**: Абонентская плата за период для стратегии "предоплата + пороги"
- **UsageCounter**: Счётчик отправленных сегментов клиентом в рамках тарифного плана и периода
- **TarificationLog**: Аудит-запись каждой операции тарификации с ключом идемпотентности

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Каждое отправляемое сообщение тарифицируется корректно по настроенной стратегии в 100% случаев (при наличии активного тарифного плана и достаточного баланса)
- **SC-002**: Пересчёт при переходе порога (стратегия 3) завершается с корректной корректировкой баланса для всех ранее отправленных сообщений за период
- **SC-003**: Тарификация одного сообщения не замедляет общий поток отправки — обработка укладывается в существующие SLA системы
- **SC-004**: Конкурентная отправка нескольких сообщений одним клиентом не приводит к некорректному подсчёту порогов или двойному списанию
- **SC-005**: Предоплата (стратегия 4) списывается автоматически при наступлении нового периода без ручного вмешательства
- **SC-006**: Администратор может настроить полный тарифный план (стратегия + периоды + пороги) за одну рабочую сессию
- **SC-007**: При сбое Saga (списание/возврат) система восстанавливается автоматически без потери средств клиента
