# Admin Panel — Design Spec

**Дата:** 2026-03-27
**Подход:** Единое приложение (portal-frontend) с role-based routing

## Контекст

### Текущее состояние
- **Admin Gateway** (Go) — 72 полностью реализованных REST-эндпоинта (`/admin/v1/*`), gRPC-интеграция с 10+ микросервисами. Auth middleware отключен (критическая проблема).
- **Portal Frontend** (React 19 + TS + Vite) — клиентский портал, 10+ страниц, нет UI-библиотеки (inline CSS), нет общих компонентов.
- **Админского UI не существует** — вся администрация только через API.

### Требования
- Полный контроль над дизайном — админка как часть продукта
- 5-10 пользователей смешанного технического уровня
- Функции: CRUD клиентов/провайдеров, мониторинг, биллинг, тарификация, аналитика

### Решение
Расширить portal-frontend, добавив админские роуты с role-based доступом. Единая кодовая база, единый деплой, общая компонентная система.

---

## 1. Архитектура и роутинг

### Разделение по ролям

Расширяем `AuthContext` полем `role: 'client' | 'admin' | 'superadmin'`, которое приходит с бэкенда при логине.

### Структура роутов

```
/login                    — общий логин (роль определяется по токену)
/dashboard                — клиентский портал (существующие страницы)
/admin                    — админские страницы (lazy-loaded)
  /admin/clients          — управление клиентами
  /admin/providers        — управление провайдерами
  /admin/routes           — маршрутизация
  /admin/billing          — биллинг и тарификация
  /admin/analytics        — расширенная аналитика
  /admin/monitoring       — мониторинг в реальном времени
  /admin/templates        — шаблоны
  /admin/webhooks         — вебхуки (глобальные)
  /admin/hlr              — HLR-провайдеры
  /admin/countries        — страны и операторы
  /admin/audit            — аудит-лог (расширенный)
```

### Code splitting

Все `/admin/*` роуты — один lazy chunk. Клиентский портал не грузит админский код:

```tsx
const AdminLayout = lazy(() => import('./pages/admin/AdminLayout'))
```

### Защита роутов

```tsx
<Route path="/admin/*" element={
  <RequireRole role="admin">
    <AdminLayout />
  </RequireRole>
} />
```

`RequireRole` проверяет роль из контекста. Несоответствие → редирект на `/dashboard`.

### API-слой

Существующий `api/client.ts` вызывает `/portal/v1/*`. Добавляем `api/admin.ts` для `/admin/v1/*`. Общий `apiFetch()` переиспользуется.

## 2. Компонентная система

### UI-стек

**Tailwind CSS** для стилей + **Radix UI** для поведения (модалки, дропдауны, табы). Полный контроль над внешним видом, без Material UI.

### Базовые компоненты

| Компонент | Назначение | Расположение |
|-----------|-----------|-------------|
| `Button` | Кнопки с вариантами (primary, danger, ghost) | `components/ui/` |
| `Input` | Текстовые поля с лейблами и ошибками | `components/ui/` |
| `Badge` / `StatusBadge` | Статусы: active/inactive, delivered/failed | `components/ui/` |
| `Modal` | Модальное окно (Radix + `useFocusTrap`) | `components/ui/` |
| `Toast` | Уведомления об успехе/ошибке | `components/ui/` |
| `DataTable` | Таблица с сортировкой, пагинацией, выбором строк | `components/data/` |
| `FilterBar` | Горизонтальная панель фильтров | `components/data/` |
| `StatCard` | Карточка метрики для дашбордов | `components/data/` |
| `Sidebar` | Навигация (отдельная для портала и админки) | `components/layout/` |
| `PageHeader` | Заголовок страницы + breadcrumbs + actions | `components/layout/` |
| `ConfirmDialog` | Подтверждение опасных действий | `components/layout/` |
| `Form` / `FormField` | Обёртка над формами с валидацией | `components/ui/` |

### Структура проекта

```
src/
  components/
    ui/           — базовые: Button, Input, Badge, Modal, Toast, Form
    data/         — DataTable, FilterBar, StatCard
    layout/       — Sidebar, PageHeader, ConfirmDialog
  pages/
    portal/       — существующие страницы (постепенный рефакторинг)
    admin/        — новые админские страницы
  api/
    client.ts     — портальный API (существующий)
    admin.ts      — админский API (новый)
  contexts/
    AuthContext.tsx — расширенный (+ role)
```

### Миграция портала

Не переписываем портал сразу. По мере создания shared-компонентов — постепенно заменяем inline-код в портальных страницах. Новые компоненты создаются для админки, затем мигрируют в портал.

## 3. Админские страницы

### Управление клиентами (`/admin/clients`)
- Таблица клиентов с поиском, фильтрами (статус, дата регистрации)
- Детальная карточка клиента: инфо, баланс, rate limits, API-ключи, статистика отправок
- Действия: создать, заблокировать/разблокировать, изменить лимиты, пополнить баланс

### Управление провайдерами (`/admin/providers`)
- Список провайдеров с индикаторами здоровья (health status)
- Карточка провайдера: конфигурация, текущая нагрузка, success rate
- Действия: добавить, отключить, изменить приоритет

### Маршрутизация (`/admin/routes`)
- Табличное представление правил: страна → оператор → провайдер(ы) с весами
- Группировка по странам, раскрываемые строки с деталями
- Действия: создать правило, изменить веса, отключить маршрут

### Биллинг и тарификация (`/admin/billing`)
- Балансы клиентов с возможностью ручного пополнения
- Транзакции с фильтрами (тип, клиент, период)
- Тарифные планы: CRUD, привязка к клиентам
- Ценовые тиры по странам/операторам

### Мониторинг (`/admin/monitoring`)
- Throughput в реальном времени (msg/sec, доставлено/ошибки)
- Статусы провайдеров — health checks
- Очереди Kafka — lag по топикам
- Auto-refresh каждые 10 секунд (polling, без WebSocket на первом этапе)

### Расширенная аналитика (`/admin/analytics`)
- Агрегация по всем клиентам (в отличие от портальной — только свои)
- Breakdown по провайдерам, странам, операторам
- Графики: объёмы, delivery rate, latency (recharts)

### Шаблоны (`/admin/templates`)
- Модерация шаблонов: approve/reject с комментарием

### Вебхуки (`/admin/webhooks`)
- Глобальные вебхуки, управление подписками по клиентам

### HLR (`/admin/hlr`)
- HLR-провайдеры, веса маршрутов, health checks

### Страны и операторы (`/admin/countries`)
- Справочник стран и операторов, префиксы

### Аудит-лог (`/admin/audit`)
- Расширенный: все пользователи, все действия, фильтры по действию/пользователю/дате

## 4. Аутентификация и авторизация

### Единый логин

Одна форма `/login` для всех. Бэкенд возвращает роль в ответе на аутентификацию. Фронтенд перенаправляет:
- `client` → `/dashboard`
- `admin` / `superadmin` → `/admin`

### Роли

| Роль | Доступ |
|------|--------|
| `client` | Только `/portal/v1/*` — свои данные |
| `admin` | `/admin/v1/*` — полный CRUD, кроме: удаление клиентов, управление админами |
| `superadmin` | Всё без ограничений, включая управление другими админами и удаление клиентов |

### Защита на двух уровнях

1. **Фронтенд** — `RequireRole` компонент, скрытие UI-элементов по роли. Только UX, не безопасность.
2. **Бэкенд** — Admin Gateway проверяет JWT + role claim на каждом запросе. Сейчас отключено — нужно включить.

### Сессии

Текущий подход (cookie + CSRF) сохраняется. Добавляется:
- `role` в auth-контекст
- Refresh token для длинных сессий админов
- Автоматический logout при бездействии (30 мин для админов)

### Бэкенд: включение auth middleware

Admin Gateway auth middleware нужно переключить с dummy-режима на реальный:
- Валидация JWT через Auth Service (gRPC)
- Проверка role claim (`admin` / `superadmin`)
- Маппинг gRPC ошибок: `Unauthenticated` → 401, `PermissionDenied` → 403

## 5. Обработка ошибок и UX-паттерны

### Обработка ошибок

- **API ошибки** — расширенный `ApiError`. Toast с описанием. 401 → auto logout. 403 → "Недостаточно прав". 503 → "Сервис недоступен".
- **Опасные действия** — `ConfirmDialog` перед удалением, блокировкой, изменением тарифов. Для критических операций (superadmin) — повторный ввод пароля.
- **Формы** — inline-валидация на фронте + серверная валидация. Ошибки у конкретных полей.

### Загрузка данных

- Skeleton-лоадеры вместо текстовых "Loading..."
- Optimistic updates для toggle-операций (вкл/выкл провайдера)
- Retry-кнопка при сетевых ошибках

### Мониторинг — auto-refresh

- Polling каждые 10 секунд для `/admin/monitoring`
- Индикатор "последнее обновление: X сек назад"
- Возможность паузы
- При потере связи — предупреждение без спама

### Таблицы

- Состояние фильтров и пагинации в URL query params (`?page=2&status=active`)
- Возможность поделиться ссылкой на отфильтрованный вид
- Экспорт в CSV для аналитики и биллинга

---

## Вне скоупа (на будущее)

- WebSocket для real-time мониторинга (первая версия — polling)
- Гранулярные permissions (`billing.write`, `clients.delete`) — сейчас ролевая модель
- Drag-and-drop для маршрутизации
- Dark mode
- i18n / мультиязычность
