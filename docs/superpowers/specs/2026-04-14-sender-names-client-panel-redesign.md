# Редизайн панели клиента: Имена отправителей

**Дата:** 2026-04-14
**Статус:** Approved
**Область:** Frontend — клиентский портал (`portal-frontend`)

---

## Обзор

Редизайн флоу «Регистрация у оператора» в разделе «Имена отправителей» клиентского портала.

**Проблема:** регистрация у оператора требовала ввода UUID оператора вручную и была спрятана в модальном окне деталей — неудобно и непонятно.

**Решение:** три отдельных страницы с единым паттерном навигации. Модальное окно деталей заменяется страницей; регистрация у операторов выносится на отдельную страницу с таблицей операторов и выпадающими списками типов.

---

## Маршруты

| Маршрут | Страница | Изменение |
|---------|----------|-----------|
| `/sender-names` | Список имён | Минимальное — убрать модал деталей |
| `/sender-names/:id` | Детали имени | **Новая** — заменяет модал |
| `/sender-names/:id/operators` | Регистрация у операторов | **Новая** |

---

## Страница 1: Список имён (`/sender-names`)

Изменения минимальны:
- Убрать весь state и JSX модального окна деталей (`selected`, `showEdit`, `showHistory`, `showRegister` и связанные обработчики)
- Клик по строке и кнопка «Подробнее» → `navigate('/sender-names/:id')`
- Всё остальное (таблица, пагинация, модал создания) остаётся без изменений

---

## Страница 2: Детали имени (`/sender-names/:id`)

### Компоненты

**Шапка:**
- Имя отправителя (моноширинный шрифт, крупно) + бейдж статуса
- Ссылка «← Имена отправителей»

**Метаданные:**
- Дата создания
- Дата одобрения / отклонения (если есть)

**Блок: статус `approved`**
- Виджет «Регистрация у операторов»: список пилюль — зелёные (зарегистрировано) и серые (не зарегистрировано)
- Кнопка «Зарегистрировать у операторов →» → переход на `/sender-names/:id/operators`

**Блок: статус `rejected`**
- Красный блок с причиной отклонения
- Инлайн-форма: поле ввода нового имени + кнопка «Отправить на повторное рассмотрение»

**Блок: статус `pending`**
- Информационный текст «Имя на модерации»

**Сворачиваемая история статусов** (во всех случаях):
- «▸ Показать историю статусов» → разворачивает список переходов

### API-вызовы
- `GET /portal/v1/sender-names/:id` — данные имени
- `GET /portal/v1/sender-names/:id/history` — история (при раскрытии)
- `POST /portal/v1/sender-names/:id/resubmit` — повторная отправка (при rejected)
- `GET /portal/v1/sender-names/:id/operator-registrations` — статусы регистраций у операторов (для пилюль)

## Страница 3: Регистрация у операторов (`/sender-names/:id/operators`)

### Хлебные крошки
```
Имена отправителей › [name] › Регистрация у операторов
```

### Таблица операторов

Колонки:
| Колонка | Описание |
|---------|----------|
| Чекбокс | Выбор оператора для регистрации |
| Оператор | Название + slug |
| Тип регистрации | `<select>` или прочерк (см. логику ниже) |
| Стоимость | Цена/мес при платном типе, иначе «—» |
| Статус | «Зарегистрировано» (зелёный) / «Не зарегистрировано» (жёлтый) |

**Логика колонки «Тип регистрации»:**

| Доступные типы у оператора | Элемент | Значение по умолчанию |
|---------------------------|---------|----------------------|
| Только бесплатная | `<select>` с одним пунктом | Бесплатная |
| Только платная | `<select>` с одним пунктом | Платная |
| Оба типа | `<select>` с двумя пунктами | Бесплатная |
| Нет типов | Прочерк «—», чекбокс задизейблен | — |

Список типов в `<select>` расширяем — новые типы добавляются без изменения компонента.

**Состояния строк:**
- **Уже зарегистрировано** → строка задизейблена (серый фон), чекбокс недоступен, тип и стоимость «—», статус зелёный
- **Нет типов** → чекбокс задизейблен, строка активна визуально, но недоступна для выбора
- **Не зарегистрировано** → чекбокс активен

### Футер

```
[Зарегистрировать у выбранных (N)]   [Отмена]          Уже зарегистрировано: X, Y
```

- Кнопка «Зарегистрировать» задизейблена, пока не выбран хотя бы один оператор
- Счётчик `(N)` обновляется при изменении выбора
- «Отмена» → назад на `/sender-names/:id`
- После успешной регистрации → редирект на `/sender-names/:id` с toast «Регистрация отправлена»

### API-вызовы
- `GET /portal/v1/operators` — список всех операторов с доступными типами регистрации
- `GET /portal/v1/sender-names/:id/operator-registrations` — текущие регистрации имени
- `POST /portal/v1/sender-names/:id/operator-registrations` — создать регистрации (bulk: массив `{operator_id, type}`)

## Изменения в API

Новые эндпоинты на бэкенде:

### Связь с существующим `senderTariffApi.createRegistration`

Существующий метод `senderTariffApi.createRegistration({ operator_id, sender_name, type })` создаёт одиночную регистрацию. Новый `POST /portal/v1/sender-names/:id/operator-registrations` — bulk-вариант того же действия, scoped по sender name. Старый метод остаётся (используется в других местах), новый добавляется рядом.

### `GET /portal/v1/operators`
Возвращает список операторов с доступными типами регистрации.

Поле `registration_types` читается из колонки `registration_types text[]` таблицы `operators` (существующая таблица). Если колонки нет — добавить миграцией: `ALTER TABLE operators ADD COLUMN registration_types text[] NOT NULL DEFAULT '{}'`.

```json
{
  "operators": [
    {
      "id": "uuid",
      "name": "МТС",
      "slug": "mts",
      "registration_types": ["paid"]
    },
    {
      "id": "uuid",
      "name": "Билайн",
      "slug": "beeline",
      "registration_types": ["free", "paid"]
    }
  ]
}
```

### `GET /portal/v1/sender-names/:id/operator-registrations`
Возвращает статус регистрации имени у каждого оператора.

```json
{
  "registrations": [
    {
      "operator_id": "uuid",
      "operator_name": "МегаФон",
      "type": "free",
      "status": "active"
    }
  ]
}
```

### `POST /portal/v1/sender-names/:id/operator-registrations`
Bulk-создание регистраций.

```json
{
  "registrations": [
    { "operator_id": "uuid", "type": "paid" },
    { "operator_id": "uuid", "type": "free" }
  ]
}
```
