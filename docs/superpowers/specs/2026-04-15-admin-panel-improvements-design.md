# Admin Panel Improvements — Design Spec

**Date:** 2026-04-15  
**Approach:** Incremental (A) — каждый этап самодостаточен и полезен  
**Scope:** Frontend (React/TypeScript) + Backend (Go) изменения

---

## Контекст и мотивация

Текущая админ-панель содержит 30+ страниц и покрывает большую часть операций. Выявлено три проблемы:

1. **Смешение ролей** — технические (провайдеры, маршруты) и бизнес-задачи (клиенты, биллинг) перемешаны в одной навигации. Разные люди выполняют разные роли, и каждый вынужден видеть чужие разделы.
2. **Пробелы функциональности** — кампании клиентов нельзя контролировать из админки; расписания маршрутов и симулятор маршрутизации отсутствуют; клиентские домены и default sender names не управляемы из UI.
3. **Слабая кросс-навигация** — переход между связанными сущностями (клиент → его кампании, маршрут → его расписания) требует ручного поиска.

---

## Этапы реализации

### Этап 1: Переключатель режимов

**Что делаем:** В шапке сайдбара добавляем toggle-свитчер с двумя режимами: "Технический" и "Бизнес". Выбранный режим сохраняется в `localStorage`. При переключении сайдбар фильтрует пункты меню.

**Разделение разделов:**

| Технический режим | Бизнес режим | Общий (оба режима) |
|---|---|---|
| Провайдеры | Клиенты | Дашборд |
| SMPP-соединения | Биллинг | Аналитика |
| Платформенные маршруты | Тарификация | Детализация |
| Индивидуальные маршруты | Индивидуальные тарифы | Аудит |
| Каналы доставки | Шаблоны | Мониторинг |
| Стратегии доставки | Sender Names | |
| HLR | Operator Templates | |
| Страны / Операторы | Юр. лица | |
| Вебхуки | Договоры | |
| Системные настройки | Компании | |
| Расписания маршрутов (новое) | Пользователи / Роли | |
| Симулятор маршрутов (новое) | Кампании (новое) | |

**Поведение по ролям:**
- Пользователь с полными правами (`admin`) видит свитчер и переключается свободно
- Пользователь без прав на технические разделы — свитчер скрыт, отображается только бизнес-режим (существующая логика `hasPermission` уже это поддерживает)
- URL не меняется при переключении режима

**Файлы для изменения:**
- `portal-frontend/src/components/AdminSidebar.tsx` — добавить свитчер, логику фильтрации
- `portal-frontend/src/hooks/useAdminMode.ts` — новый хук для хранения состояния режима в localStorage
- Никаких изменений backend не требуется

### Этап 2: Управление кампаниями (`/admin/campaigns`)

**Что делаем:** Новый раздел в бизнес-режиме для полного контроля над кампаниями всех клиентов.

#### Страница списка `/admin/campaigns`

- Таблица всех кампаний всех клиентов
- Колонки: название, клиент, статус, прогресс (X/Y получателей), sent/delivered/failed, дата запуска, действия
- Фильтры: по клиенту, статусу (`draft` / `running` / `paused` / `completed` / `failed`), дате, типу
- Действия из строки: Пауза, Возобновить, Остановить (с диалогом подтверждения)

#### Детальная страница `/admin/campaigns/:id`

**Блоки:**
1. **Заголовок** — название, клиент (ссылка), статус badge, кнопки управления (пауза/возобновить/остановить)
2. **Параметры кампании** — тип, шаблон (ссылка), sender name (ссылка), канал доставки, расписание, батч-размер
3. **Статистика** — карточки: всего получателей, отправлено, доставлено, прочитано, ошибки, CTR
4. **Получатели** — пагинированная таблица записей campaign_recipients с их статусом
5. **История статусов** — таблица переходов с временными метками

**Редактирование (ограниченный набор полей):**
- Расписание отправки (cron-выражение или datetime)
- Размер батча (batch_size)
- Интервал между батчами (batch_interval)
- Контент кампании, список получателей и тип — не редактируются

**Кросс-навигация:** ссылки на клиента, шаблон, sender name в блоке "Related" в шапке страницы.

#### Backend

Новые endpoint'ы в `/internal/gateway/admin/router/router.go`:
```
GET  /admin/v1/campaigns              — список всех кампаний (с фильтрами)
GET  /admin/v1/campaigns/:id          — детали кампании
POST /admin/v1/campaigns/:id/pause    — пауза
POST /admin/v1/campaigns/:id/resume   — возобновление
POST /admin/v1/campaigns/:id/stop     — остановка
PUT  /admin/v1/campaigns/:id          — обновление (только schedule, batch_size, batch_interval)
```

Обращаются к существующему campaign service через gRPC или напрямую к БД через существующий репозиторий кампаний.

### Этап 3: Расписания маршрутов (`/admin/routes/schedules`)

**Что делаем:** Новый раздел в техническом режиме для управления временными расписаниями маршрутов.

#### Концепция

Расписание позволяет автоматически переключать активного провайдера для маршрута в зависимости от времени суток и дня недели. Например: в рабочее время — основной провайдер, ночью и в выходные — резервный.

#### Страница списка `/admin/routes/schedules`

- Таблица: название, маршрут/провайдер, тип (ежедневное/недельное/разовое), статус (активно/приостановлено), ближайшее срабатывание
- Действия: включить/выключить, редактировать, удалить

#### Создание/редактирование расписания

Форма в два шага:

**Шаг 1 — Маршрут:**
- Выбор маршрута (платформенный или клиентский)

**Шаг 2 — Временные правила:**
- Визуальная сетка 7×24 (дни недели × часы суток)
- Каждая ячейка — активный провайдер в это время
- Выделение диапазона + назначение провайдера через dropdown
- Цветовая легенда провайдеров
- Дополнительно: разовые переопределения для конкретных дат (праздники)

**Валидация:**
- Предупреждение если расписание конфликтует с другим на том же маршруте
- Обязательное покрытие всех 168 часов (или явное "использовать default провайдер")

**История срабатываний:** последние 20 переключений провайдера по расписанию.

#### Backend

Новая таблица `route_schedules` (если не существует) или использование существующей структуры.

Новые endpoint'ы:
```
GET    /admin/v1/route-schedules           — список
POST   /admin/v1/route-schedules           — создать
GET    /admin/v1/route-schedules/:id       — получить
PUT    /admin/v1/route-schedules/:id       — обновить
DELETE /admin/v1/route-schedules/:id       — удалить
POST   /admin/v1/route-schedules/:id/enable  — включить
POST   /admin/v1/route-schedules/:id/disable — выключить
GET    /admin/v1/route-schedules/:id/history — история срабатываний
```

### Этап 4: Симулятор маршрутизации (`/admin/routes/simulator`)

**Что делаем:** Инструмент для отладки и проверки конфигурации маршрутизации без реальной отправки.

#### Страница симулятора

**Форма входных параметров:**
- Номер получателя (MSISDN) — автоматически определяет страну и оператора
- Клиент — выбор из списка (применяются его индивидуальные маршруты)
- Sender Name — для маршрутов с ограничением по типу отправителя
- Тип трафика (`transactional` / `promotional` / `OTP`)
- Канал доставки (`sms` / `viber` / `whatsapp`)
- Дата и время — для проверки расписаний (по умолчанию — текущее)

**Результат — пошаговая цепочка решений:**

```
✓ Номер: +79161234567 → МТС, Россия (MCC: 250, MNC: 01)
✓ Клиент: Acme Corp → найден индивидуальный маршрут #42
✓ Расписание маршрута: 14:00 четверг → активен Провайдер A
✓ Провайдер A: доступен, health = OK
→ Итог: сообщение пойдёт через iDigital (приоритет 1)
```

Каждый шаг раскрывается accordion'ом — показывает какие правила были проверены, какие отброшены и почему.

**Режим "что если":**
- Чекбоксы для временного отключения провайдеров/маршрутов в рамках симуляции
- При изменении — автоматический пересчёт результата
- Чётко помечено: "Это симуляция, реальная конфигурация не изменяется"

**Быстрый переход:** кнопка "Открыть симулятор" на детальных страницах маршрутов (с предзаполненными параметрами).

#### Backend

Новый endpoint (read-only, не меняет состояние):
```
POST /admin/v1/routes/simulate
Body: { msisdn, client_id, sender_name, traffic_type, channel, datetime, disabled_providers[] }
Response: { steps[], result: { provider_id, provider_name, route_id } }
```

Логика симулятора реализуется в том же слое, что и реальная маршрутизация, но без side effects.

### Этап 5: Расширение страницы клиента

**Что делаем:** Добавляем три новые вкладки на страницу клиента `/admin/clients/:id`.

#### Вкладка "Домены"

Управление кастомными доменами клиента:
- Таблица: домен, тип (`short-link` / `webhook` / `portal`), статус верификации (`pending` / `verified` / `failed`), дата добавления
- Статус верификации раскрывается — показывает ожидаемые DNS-записи и что обнаружено
- Действия: добавить домен, повторная верификация, удалить (с предупреждением если активен)

#### Вкладка "Sender Names"

Контекстное управление sender names клиента:
- Список всех зарегистрированных sender names этого клиента с их статусом
- Для каждого канала (`sms`, `viber`, `whatsapp`) — dropdown выбора default sender name
- Быстрый переход на детальную страницу sender name для модерации
- Не дублирует `/admin/sender-names` — добавляет клиентский контекст

#### Вкладка "Кампании"

Быстрый список кампаний клиента с переходом на `/admin/campaigns/:id`.

#### Backend

Новые endpoint'ы для доменов:
```
GET    /admin/v1/clients/:id/domains        — список доменов клиента
POST   /admin/v1/clients/:id/domains        — добавить домен
DELETE /admin/v1/clients/:id/domains/:did   — удалить домен
POST   /admin/v1/clients/:id/domains/:did/verify — повторная верификация
```

Для default sender names — расширение существующего `PUT /admin/v1/clients/:id/config`:
```json
{
  "default_sender_names": {
    "sms": "sender_name_id",
    "viber": "sender_name_id"
  }
}
```

### Этап 6: Кросс-навигация (внедряется инкрементально)

**Что делаем:** На детальных страницах ключевых сущностей добавляем блок "Related" — небольшие теги-ссылки на связанные сущности.

**Реализация:** Компонент `<RelatedLinks items={[...]} />` в шапке детальных страниц.

| Страница | Related блок |
|---|---|
| `/admin/clients/:id` | → Кампании (N), → Маршруты (N), → Sender Names (N) |
| `/admin/campaigns/:id` | → Клиент, → Шаблон, → Sender Name |
| `/admin/providers/:id` | → Маршруты (N), → Расписания (N) |
| `/admin/sender-names/:id` | → Клиент, → Оператор, → Биллинг |
| `/admin/routes/:id` | → Провайдер, → Расписания (N), → [Симулятор ↗] |

Related блок не делает дополнительных запросов — данные подгружаются вместе с основным запросом страницы (count полей в ответе API).

## Порядок реализации

1. **Этап 1** — Переключатель режимов (только frontend, низкий риск)
2. **Этап 2** — Управление кампаниями (frontend + backend)
3. **Этап 3** — Расписания маршрутов (frontend + backend + новая таблица)
4. **Этап 4** — Симулятор маршрутизации (frontend + backend read-only)
5. **Этап 5** — Расширение страницы клиента (frontend + backend)
6. **Этап 6** — Кросс-навигация (внедряется параллельно с этапами 2-5)

Каждый этап можно деплоить и использовать независимо.

---

## Что остаётся за рамками данного спека

- Quiet hours, frequency caps, notification settings — не входят в данный спек
- Opt-out списки, API-ключи — отдельная задача
- Переотправка сообщений — отдельная задача
- Изменение существующих разделов (кроме страницы клиента) — не затрагивается
