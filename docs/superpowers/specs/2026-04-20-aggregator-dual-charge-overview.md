# Двойное списание для агрегаторов — обзор для менеджера

**Дата:** 2026-04-20 (обновлено после сверки с реальным состоянием кода)
**Сопутствующий технический документ:** `2026-04-20-aggregator-dual-charge-design.md`

## О чём речь

В системе уже реализована модель "агрегатор + субаккаунты": есть таблицы, репозитории, админский интерфейс, страницы для агрегатора, настройка тарифов и квот. Работа велась с середины апреля 2026.

**Что работает прямо сейчас:**
- Агрегатор может создавать субаккаунты, выставлять им тарифы, видеть аналитику.
- Админ может настраивать квоты и billing-режимы.
- При отправке сообщения субаккаунтом система делает двойное списание: с субаккаунта и с агрегатора, с записью маржи.
- Квоты, пулы сегментов, overage — есть в коде и в БД.

**Что сделано неправильно и требует доработки:**

1. **Двойное списание не атомарно.** Сейчас система списывает сначала с субаккаунта, потом с агрегатора — двумя отдельными вызовами. Если второй упадёт (таймаут, сбой), делается компенсационный возврат первого. Между ними есть окно несогласованности. В редких случаях это приводит к зависшим списаниям или двойным возвратам.
2. **Списание происходит слишком рано.** Сейчас деньги списываются в момент расчёта тарифа, до того как сообщение действительно ушло к оператору. Если провайдер недоступен или сбой случился раньше отправки, деньги всё равно списаны. Это некорректно: экономически мы должны платить только за сообщения, которые действительно ушли к оператору.
3. **Аналитика маржи неполная.** В лог маржи не записывается, сколько сообщений прошло по пакетной цене, а сколько по overage. Агрегатор видит общую маржу, но не может разложить её на эти две категории.
4. **Мелкая техническая правка.** Идентификаторы сообщений используют несортируемый формат UUID, что в будущем затруднит партиционирование логов при росте объёмов.

Этот проект закрывает четыре пункта выше. Новых пользовательских фич не добавляется — это технический долг.

## Что изменится для агрегатора

**Фактически ничего нового не увидит.** Все текущие страницы работают. Отчёты по марже становятся точнее (различают pool и overage). Двойные списания/возвраты в редких случаях перестают происходить.

**Квота продлевается автоматически.** Уже заложено в схему (поле `auto_renew`), но не работало на практике. После этих изменений: если у агрегатора в предыдущем месяце была квота с `auto_renew=true` — на следующий месяц создаётся точно такой же row автоматически при первой отправке. Админ может отключить автопродление на конкретном агрегаторе (через `auto_renew=false`) — тогда следующий месяц нужно настраивать вручную, иначе агрегатор будет заблокирован.

## Что изменится для субаккаунта

Ничего видимого. Единственное различие — если платформа упала раньше отправки сообщения, деньги не будут списаны (сейчас в некоторых случаях списываются). Это положительное, но редкое изменение.

## Что изменится для администратора платформы

**Ручной работы становится меньше.** Раньше предполагалось, что админ каждый месяц настраивает квоту для каждого агрегатора. С автопродлением — достаточно настроить один раз, дальше система продлевает сама с теми же параметрами. Изменения параметров (новый контракт, другая цена) — через админский UI.

**Агрегаторы без настроенной квоты и `auto_renew=false`** — блокируются. Это поведение осталось как было.

**Операции админа не меняются:** страница настройки квот та же, CRUD работает. Меняется только то, что система теперь сама создаёт новые периоды.

## Что изменится финансово

**Ничего не меняется в экономической модели.** Ставки, цены, маржа — всё как настроено. Меняется только **надёжность** списаний:

- Списания и возвраты становятся атомарными: либо оба списания прошли, либо ни одно.
- Списания происходят ровно за те сообщения, которые действительно ушли к оператору. Ни за попытки, которые не дошли до оператора, ни за случаи "платформа упала до отправки".
- Post-submit delivery failures (оператор принял, но потом вернул failed) — списание остаётся. Это индустрийный стандарт.

**Отчётность становится точнее.** В маржа-логе теперь будет видно: столько-то сегментов по пакетной цене, столько-то по overage. Это даёт агрегатору и платформе более детальную картину wholesale-экономики.

## Когда это заработает

Выкатка поэтапная, с фиче-флагом:
1. Миграция БД (добавляет поля для детализации маржи).
2. Деплой новых версий billing-service, tarification-service, pipeline.
3. Включение фиче-флага на одном тестовом агрегаторе, верификация (1-2 дня).
4. Включение для всех агрегаторов.
5. После стабилизации — удаление старой (неатомарной) логики.

На любом этапе можно выключить флаг и вернуть старое поведение. История маржи, созданная при новом флаге, не теряется.

## Чего этот проект не делает

- Новой функциональности для пользователей (ни агрегаторов, ни субаккаунтов, ни админа).
- Уведомлений о приближении к лимиту квоты — поля в схеме есть (`notified_80pct`, `notified_100pct`), но реализация уведомлений — отдельная задача.
- Массовых операций над квотами.
- Перевода инфраструктуры с `is_reseller` на что-то ещё.
- Расширения sharding'а квот для высоконагруженных агрегаторов.

## Риски

- **Миграция БД несовместима с откатом в процессе выкатки.** Добавляются поля с дефолтами — старый код будет просто не использовать их. Риск минимальный.
- **Фиче-флаг выключен по умолчанию.** Если включение покажет проблемы — быстрый откат.
- **Автопродление квот.** Если агрегатор пропустил обновление контракта и `auto_renew=true` — продолжит работать по старым параметрам. Это не баг, а особенность: админ отвечает за своевременное обновление.
