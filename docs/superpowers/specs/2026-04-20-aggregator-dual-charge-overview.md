# Двойное списание и квоты для агрегаторов — обзор для менеджера

**Дата:** 2026-04-20
**Сопутствующий технический документ:** `2026-04-20-aggregator-dual-charge-design.md`

## О чём речь

В системе есть **агрегаторы** — клиенты, которые перепродают трафик платформы дальше своим **субаккаунтам** (например, мелким компаниям). Сейчас этот флоу работает наполовину: субаккаунт платит по тарифу, но платформа не получает свою долю, а агрегатор не фиксирует свою наценку. Маржа агрегатора нигде не считается, отчётов по ней нет.

Этот проект закрывает эту дыру и добавляет механизм контроля объёмов.

## Что изменится для агрегатора

**Экономика становится прозрачной.**
Каждый раз, когда субаккаунт отправляет SMS, в системе происходит два списания:
- С баланса субаккаунта — по цене, которую агрегатор установил субаккаунту.
- С баланса самого агрегатора — по цене, которую платформа установила агрегатору.

Разница между этими двумя ценами — **маржа агрегатора**. Она фиксируется в истории по каждому сообщению. Агрегатор в любой момент может посмотреть, сколько он заработал на конкретном субаккаунте, за день, за месяц, по конкретному направлению.

**Ограничение: квота на месяц.**
Каждому агрегатору администратор платформы назначает месячную квоту — сколько SMS-сегментов агрегатор может прогнать через платформу в текущем месяце по "контрактной" цене. Это соответствует формату wholesale-контрактов в индустрии: "купил миллион сегментов за фикс, дальше — сверху по другой цене".

Пока объём в пределах квоты — агрегатор платит "пакетную" цену. Как только квота исчерпывается — система автоматически переходит на **overage-тариф** (повышенная цена за сегмент сверх пакета). Отправка **не блокируется** при исчерпании пакета, пока на балансе агрегатора есть деньги на overage.

Квота обнуляется 1-го числа каждого месяца (UTC). Админ может заранее настроить квоту на следующий месяц, если планируется изменение условий контракта.

**Отрицательная маржа — разрешена, но видна.**
Если агрегатор случайно настроил субаккаунту цену ниже собственной закупочной, система его не останавливает — субаккаунт получит свою цену, агрегатор потеряет разницу. Но этот факт виден в отчётах и в метриках: платформа покажет админу алерт "у агрегатора X сустейн отрицательная маржа", а сам агрегатор увидит это в дашборде и сможет поднять цену.

## Что изменится для субаккаунта

**Почти ничего.**
Субаккаунт продолжает работать как раньше: видит свой баланс, отправляет SMS, получает свою цену. Никаких новых полей, никакой новой логики в UI субаккаунта.

**Возможные новые ошибки, которые он может увидеть:**
- "Временно недоступно, обратитесь к вашему провайдеру" — если админ платформы забыл настроить квоту на текущий месяц для его агрегатора. Это операционная ошибка со стороны админа, а не бизнеса.
- "Недостаточно средств на балансе агрегатора" — если у агрегатора кончились деньги. Это сигнал субаккаунту связаться с его агрегатором.

## Что изменится для администратора платформы

**Новая ежемесячная задача:** перед началом каждого месяца настроить квоту для каждого активного агрегатора. Два параметра: лимит сегментов и overage-цена за сегмент.

Если квота на месяц не настроена — **агрегатор не сможет отправлять сообщения** до тех пор, пока квота не появится. Пакет не работает молчаливо — это осознанный выбор: контракты между платформой и агрегаторами индивидуальные, дефолтных значений быть не должно.

**Для предотвращения ошибок** в систему встроен мониторинг:
- Алерт, когда появляются агрегаторы без настроенной квоты на текущий месяц.
- Алерт, когда у какого-то агрегатора устойчиво отрицательная маржа (он теряет деньги).
- Алерт, когда производительность списаний падает (намёк на проблемы с нагрузкой).

Админ-интерфейс содержит страницу "Квоты агрегаторов" со списком всех агрегаторов и состоянием их квот. Из неё можно установить квоту на любой будущий месяц. Массовое копирование текущих квот на следующий месяц — в первую версию не входит (добавится позже, если ручная работа окажется обременительной).

## Что изменится финансово

**Платформа начнёт получать свою долю.** Сейчас за трафик субаккаунтов через агрегаторов платформа не списывает ничего с агрегатора. Это прямая потеря — трафик идёт через операторов платформы, платформа платит операторам, но не получает встречного потока от агрегатора. После внедрения: каждое сообщение субаккаунта = списание с баланса агрегатора в пользу платформы.

**Отчётность становится честной.** Маржа агрегатора фиксируется по каждому сообщению с привязкой к (агрегатор, субаккаунт, оператор, направление). Это закрывает потребности:
- Агрегатор может считать свою прибыль по периодам и субаккаунтам.
- Платформа может видеть top-агрегаторов по объёму, top-субаккаунтов, средние маржи по рынку.
- Спорные ситуации решаются ссылкой на конкретную запись в истории.

**Деньги не теряются.** Если сообщение не ушло к оператору (наш сбой, провайдер недоступен) — списания не происходит вообще. Если сообщение ушло к оператору, но дальше было отклонено (неверный номер, заблокированный отправитель) — списание остаётся: оператор всё равно взял с нас за приём. Это индустрийный стандарт "pay per submit, not per delivery".

Повторные ответы системы ("а не послали ли вы уже это сообщение?") не приводят к двойным списаниям — стоит защита по уникальности сообщения.

## Когда это заработает

Выкатка поэтапная:
1. Техническая подготовка — миграция БД, деплой новых сервисов. Для клиентов незаметно.
2. Включение на одном тестовом агрегаторе — проверка, что маржа считается правильно, балансы сходятся, отчёты показывают корректные цифры.
3. Постепенное включение для всех агрегаторов.

На каждом этапе есть возможность быстро выключить новую логику и вернуть старую, если что-то пойдёт не так. Возврат не теряет данные — история двойных списаний остаётся для разбора.

## Чего этот проект не делает

Чтобы не перегружать этот блок работы, **за рамками остались:**
- Массовое копирование квот с одного месяца на следующий для всех агрегаторов (пока только поштучно).
- Возврат денег за сообщения, которые оператор принял, но не доставил (осознанное решение: в SMS такие возвраты — это отдельная услуга, а не правило).
- Переделка "новой" терминологии в интерфейсах (где-то `reseller`, где-то `network`, где-то `aggregator` — это будем чистить отдельно).
- Автоматическое переключение агрегатора между пакетом и overage в реальном времени на дашборде — базовая версия дашборда показывает использование пакета, расширенная — позже.

## Риски

- **Забытая квота блокирует агрегатора.** Решается алертом и дисциплиной админа. В худшем сценарии — агрегатор на час-два теряет возможность отправлять, пока админ не настроит.
- **Агрегатор может уйти в убыток.** Если его тарифы для субаккаунтов ниже закупочных — он будет терять. Система это не запрещает (бизнес-решение агрегатора), но делает видимым.
- **Высокая нагрузка на одном агрегаторе.** Архитектура выдерживает порядка 100 сообщений в секунду от одного агрегатора. Если конкретный агрегатор превысит — есть план масштабирования (не входит в эту работу, но подготовлен).
