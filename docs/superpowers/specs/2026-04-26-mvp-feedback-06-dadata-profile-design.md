# Spec №6: Профиль — автозаполнение реквизитов юр.лица через Dadata

**Дата:** 2026-04-26
**Источник:** MVP-таблица, строка «Настройки → Профиль» (Партнёр)
**Статус:** Не сделано (Dadata в коде отсутствует).

## Контекст

Спека:
> Юр.лицо Партнера (автоматический поиск по ИНН).
> - Dadata API (10к запросов в день): https://dadata.ru/api/find-party/
> - API: <ключ был в спеке открытым текстом — см. отдельное замечание в обратной связи менеджеру>

Аудит:
- Реквизиты юр.лица живут в таблице `companies` ([migrations/000091_create_companies.up.sql](migrations/000091_create_companies.up.sql)): `inn`, `kpp`, `ogrn`, `name`, `full_name`, `legal_address`, `actual_address`, `ceo_name`, `ceo_title`, `bank_*`. Связь `client_companies` — M:N.
- `ProfilePage.tsx` редактирует только `contact_person`, `phone`, 2FA, пароль. Полей юр.лица в форме нет.
- `grep dadata` по репо → пусто. Ни клиента, ни ENV-переменной, ни кеша.

## Решение

### Подход

**Прокси через portal-gateway с Redis-кешем по ИНН.** Прямой вызов с фронта невозможен (ключ Dadata в браузере = утечка квоты + проблемы с CORS). Кеш TTL 7 дней (реквизиты редко меняются). При превышении дневного лимита 10к — 429 пользователю с понятным сообщением.

### Что меняем

**1. Конфигурация**

В `internal/gateway/portal/config/config.go` (или общий `config.yaml`):
```yaml
dadata:
  api_key: ${DADATA_API_KEY}        # ENV
  base_url: https://suggestions.dadata.ru/suggestions/api/4_1/rs
  daily_limit: 10000
  cache_ttl: 168h                    # 7 дней
  request_timeout: 5s
```

Ключ хранится в ENV `DADATA_API_KEY` на сервере, в репо не попадает. **Старый ключ из открытой таблицы перевыпустить** (см. обратную связь менеджеру).

**2. Backend: новый endpoint**

`internal/gateway/portal/handlers/dadata.go`:

```
GET /portal/v1/dadata/party?inn=7707083893
Auth: только аутентифицированные пользователи. Для МVP — все клиенты, не только партнёры. Партнёр-only — позже, если выяснится что злоупотребляют.

Response 200:
{
  "inn": "7707083893",
  "kpp": "773601001",
  "ogrn": "1027700132195",
  "name": "СБЕРБАНК",
  "full_name": "ПУБЛИЧНОЕ АКЦИОНЕРНОЕ ОБЩЕСТВО ...",
  "legal_address": "117997, г Москва, ...",
  "ceo_name": "Греф Герман Оскарович",
  "ceo_title": "ПРЕЗИДЕНТ, ПРЕДСЕДАТЕЛЬ ПРАВЛЕНИЯ",
  "type": "LEGAL",   // или "INDIVIDUAL" для ИП
  "source": "cache" | "live"
}

Response 404: { "error": "not_found" }
Response 429: { "error": "daily_limit_exceeded", "retry_after_seconds": 12345 }
Response 502: { "error": "upstream_unavailable" }
```

Логика:
1. Валидация ИНН (10 или 12 цифр).
2. Lookup в Redis: `dadata:party:{inn}` — если есть, вернуть с `source=cache`.
3. Rate-limit чек: `dadata:counter:{YYYY-MM-DD}` — если ≥ 10000, вернуть 429.
4. Запрос к Dadata: `POST {base_url}/findById/party` с `Authorization: Token <api_key>`, body `{"query":"<inn>"}`.
5. Парс ответа — взять первую запись из `suggestions[]`. Если массив пуст — 404.
6. Маппинг в нашу структуру (поля выше).
7. Запись в кеш (`SETEX dadata:party:{inn} 604800 <json>`).
8. Инкремент счётчика (`INCR dadata:counter:{YYYY-MM-DD}`, `EXPIRE` на 36 часов).
9. Ответ с `source=live`.

**Обработка ИП и юрлиц:** Dadata возвращает разные структуры. Маппинг покрывает оба:
- LEGAL → `name`, `full_name`, `kpp`, `ogrn`, `legal_address`, `ceo_name`, `ceo_title`.
- INDIVIDUAL (ИП) → `name = "ИП Фамилия И.О."`, `kpp=null`, `ogrnip` в поле `ogrn`, `legal_address` (как `data.address.value`), `ceo_name` = ФИО ИП, `ceo_title="Индивидуальный предприниматель"`.

**3. Frontend**

В `ProfilePage.tsx` (или в отдельной форме «Реквизиты юр.лица», если профиль уже перегружен) добавить блок:

```
┌─ Реквизиты юр.лица ─────────────────────┐
│  ИНН: [_____________] [Найти]           │
│                                          │
│  При успехе автозаполнение полей:       │
│  Наименование:    ...                    │
│  Полное наимен.:  ...                    │
│  КПП:             ...                    │
│  ОГРН:            ...                    │
│  Юр. адрес:       ...                    │
│  Руководитель:    ...                    │
│  Должность:       ...                    │
│                                          │
│  [Сохранить как мою компанию]            │
└──────────────────────────────────────────┘
```

Кнопка «Найти» дёргает `GET /portal/v1/dadata/party?inn=...`. После заполнения — пользователь может править вручную. Кнопка «Сохранить» создаёт запись в `companies` (через существующий `companiesApi.create` или новый эндпоинт) и привязывает к клиенту через `client_companies`.

**Обработка ошибок:**
- 404: «Юр.лицо с таким ИНН не найдено. Введите данные вручную или проверьте ИНН.»
- 429: «Сегодня исчерпан лимит автопоиска. Попробуйте завтра или введите данные вручную.» (поля остаются доступны для ручного ввода — fail-soft).
- 502: «Сервис автопоиска временно недоступен. Введите данные вручную.»

### Что НЕ делаем

- **Прямой вызов с фронта.** Ключ нельзя выпускать в браузер.
- **Подсказки на каждое нажатие клавиши** (Dadata Suggestions). Дороже по квоте, выгода для UX небольшая. Если попросят — отдельная фича.
- **Привязка только к роли «Партнёр».** Спека упоминает партнёра, но запрет для клиента не оправдан — клиенты тоже хотят автозаполнение. Открываем всем аутентифицированным. Если злоупотребляют (мониторинг счётчика) — добавим per-role rate-limit.
- **Поддержка иностранных юрлиц.** Dadata только РФ.
- **Кеш в памяти процесса.** Только Redis — у нас несколько инстансов portal-gateway, in-memory был бы дублированной квотой.

## Acceptance criteria

1. ENV `DADATA_API_KEY` обязателен при старте portal-gateway, иначе запуск падает с явной ошибкой (а не молчаливо).
2. `GET /portal/v1/dadata/party?inn=7707083893` отвечает корректным JSON со структурой выше.
3. Повторный запрос на тот же ИНН в течение 7 дней — `source=cache`, в Dadata НЕ ходим (проверить через мок Dadata в тесте).
4. Когда счётчик дня достигает 10000 — следующие запросы возвращают 429 без вызова Dadata.
5. Невалидный ИНН (не 10/12 цифр) — 400 с понятной ошибкой, без вызова Dadata.
6. UI: кнопка «Найти» по ИНН наполняет поля; пользователь может править; «Сохранить как мою компанию» создаёт запись в `companies`.
7. При 429/502 — пользователь видит понятное сообщение и может ввести данные вручную.
