# Spec №9: Кампании-wizard — косметические доводки

**Дата:** 2026-04-26
**Источник:** MVP-таблица, строка «Отправить → Кампании»
**Статус:** Wizard уже 4-шаговый. Закрываем 4 расхождения и скрываем «Повторы» из меню.

## Контекст

Спека описывает упрощённый wizard в 4 этапа: Сообщение / Аудитория / Расписание / Подтверждение. Аудит показал, что [CampaignWizardPage.tsx](portal-frontend/src/pages/campaigns/CampaignWizardPage.tsx) (905 строк) уже соответствует структурно: 4 шага, A/B на шаге 1 раскрытием, диалог отмены, авто-имя `SMS · dd.mm.yyyy · hh:mm`, расчёт стоимости.

Расхождения локальные:
1. Сводка «Исключено: N» в шаге 2 пишет `(фильтры применяются при запуске)` без числа — спека требует явное число.
2. Сводка варианта B на confirm показывает только `abTemplateB?.body`, но не `abMessageTextB` (если пользователь вписал текст вручную в textarea).
3. «Имя отправителя по умолчанию» — берётся первый из списка. Нет поля `is_default`.
4. «Сохранить как черновик» при пустом `contactListId` подставляет первую базу — хак, искажающий UX.
5. В навигации присутствует пункт «Повторы» ([CampaignSchedulesPage.tsx](portal-frontend/src/pages/campaigns/CampaignSchedulesPage.tsx)) — спека просит «убрать навсегда (либо переедет в каскад, не в MVP)».

## Решение

### Что меняем

**1. Сводка «Исключено: N» (шаг 2)**

В [CampaignWizardPage.tsx:584](portal-frontend/src/pages/campaigns/CampaignWizardPage.tsx#L584) заменить заглушку `(фильтры применяются при запуске)` на расчёт:

```
К отправке: <total - excluded> контактов
(Исключено по фильтрам: <excluded>)
```

Где `excluded` считается на бэке: новый эндпоинт `POST /portal/v1/campaigns/audience/preview` принимает `contact_list_id`, `exclude_countries[]`, `exclude_operators[]` и возвращает `{ total: int, excluded: int, target: int }`. Логика — один SQL `COUNT(*) FILTER (...)` по `contacts` с join на `operator`/`country`. Если уже есть похожий API — реиспользовать.

При смене базы или фильтров — debounce 300мс и пересчёт.

**2. Сводка Variant B на confirm (шаг 4)**

В блоке подтверждения A/B показывать оба источника текста:
- Если `abMessageTextB` непуст — показать его как «Текст варианта B» (приоритет над шаблоном).
- Иначе если `abTemplateB` выбран — показать `abTemplateB.body` как «Шаблон варианта B: <name>».

Логика та же что для основного текста (приоритет вручную введённого над шаблоном).

**3. Дефолт-отправитель: использовать `is_default` поле**

Аудит показал, что в БД миграция `default-senders` уже была (видна в недавних коммитах CLAUDE.md: «default-senders security gaps + UX cleanups»). Проверить что в `sender_names` есть колонка `is_default` или отдельная таблица `default_senders` с привязкой к клиенту.

Логика на фронте при инициализации wizard (CampaignWizardPage.tsx:95):
```
const initialSender =
  approvedSenders.find(s => s.is_default)
  ?? approvedSenders[0]
  ?? null;
```

Если `is_default` отсутствует и пользователь его не назначил — оставляем «первый approved» как fallback (не падаем).

**4. «Сохранить как черновик» — без хака с базой**

В [CampaignWizardPage.tsx:244](portal-frontend/src/pages/campaigns/CampaignWizardPage.tsx#L244) убрать подстановку первой базы. Бэкенд должен принимать черновик с `contact_list_id=null`. Если уже не принимает — добавить в схему campaigns: `contact_list_id` стать nullable для `status='draft'`. Валидация требует ненулевой `contact_list_id` только при `status='scheduled'` или `'running'`.

Новая логика «Сохранить как черновик»: сохраняем то, что есть, без додумывания.

**5. Скрыть «Повторы» из меню**

В [UserLayout.tsx](portal-frontend/src/components/layout/UserLayout.tsx) убрать пункт меню, ведущий на `/campaigns/schedules`.

Файлы [CampaignSchedulesPage.tsx](portal-frontend/src/pages/campaigns/CampaignSchedulesPage.tsx) и роут **оставить** в коде — фича рабочая, может вернуться в раздел «Каскады» позже. Прямой URL продолжает работать (закладки не ломаем). Если фича попадёт в каскад-MVP — переместим под `/cascade/schedules`.

### Что НЕ делаем

- **Полную декомпозицию wizard'а на компоненты** (`MessageStep` / `AudienceStep` / ...). 905 строк в одном файле — больно, но рефакторинг не часть этого спека. Отдельная задача после MVP.
- **Переписывание на TanStack Form + zod**. Слишком инвазивно.
- **Удаление кода `CampaignSchedulesPage`**. Только скрываем из меню.
- **Серверный preview-эндпоинт для остальных шагов** — только для шага «Аудитория».

### Открытые вопросы (закрываю сам)

- **Существующие черновики 6-шаговой схемы:** wizard уже 4-шаговый, скорее всего черновиков по старой схеме нет. Если миграция кода была недавняя и черновики есть — они откроются на доступных полях, лишние данные в БД останутся, не падают. Если попадутся проблемные — отдельный hotfix.
- **«Время до выбора победителя» при отправке «Сейчас»:** считаем от момента запуска (т.е. от submit на шаге 4). Это понятнее пользователю.
- **A/B при «Позже»:** время до выбора победителя добавляется к запланированному времени отправки. Окно «доставка→измерение» работает после старта.

## Acceptance criteria

1. Шаг «Аудитория»: при выборе фильтров появляется реальное число «Исключено: N», обновляется при изменении.
2. Шаг «Подтверждение» при включенном A/B показывает оба варианта (A и B) корректно — для каждого либо textarea-текст, либо шаблон.
3. Дефолт-отправитель: если у пользователя есть sender с `is_default=true` — он подставляется. Иначе — первый approved.
4. «Сохранить как черновик» с пустой базой — сохраняет черновик без `contact_list_id`. Открытие черновика обратно — поле «База» пустое, пользователь должен выбрать.
5. Из меню «Повторы» исчезли. Файлы и роут продолжают работать по прямому URL.

## Размер задачи

S (1-2 рабочих дня: 4 точечных правки + один новый эндпоинт `audience/preview` + удаление пункта меню).
