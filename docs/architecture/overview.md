# Обзор архитектуры SMPP сервера

## Введение

SMPP сервер представляет собой микросервисную систему для обработки SMS сообщений, построенную на базе протокола SMPP v3.4. Система обеспечивает высокую доступность, масштабируемость и надежную доставку сообщений.

## Архитектурные принципы

- **Микросервисная архитектура** - разделение на независимые сервисы
- **Асинхронная обработка** - использование Kafka для очередей сообщений
- **Горизонтальное масштабирование** - возможность масштабирования каждого сервиса независимо
- **Высокая доступность** - множественные инстансы сервисов с балансировкой нагрузки
- **Мониторинг и наблюдаемость** - интеграция с Prometheus и Grafana

## Компоненты системы

### API Gateway

**Назначение:** Единая точка входа для клиентов через HTTP и gRPC API.

**Функции:**
- Прием запросов на отправку SMS
- Аутентификация клиентов (API ключи)
- Rate limiting на уровне клиента
- Публикация сообщений в Kafka
- Проверка статуса сообщений
- Получение истории сообщений

**Масштабирование:** Множественные инстансы за HAProxy

**Порты:**
- HTTP: 8080
- gRPC: 9090
- Metrics: 2112

### SMPP Server

**Назначение:** Прием входящих SMPP соединений от клиентов.

**Функции:**
- Прием SMPP соединений (bind_receiver, bind_transmitter, bind_transceiver)
- Обработка submit_sm запросов
- Отправка deliver_sm (DLR) клиентам
- Управление сессиями (enquire_link, unbind)
- Rate limiting на уровне сессии

**Масштабирование:** Один инстанс (можно масштабировать при необходимости)

**Порты:**
- SMPP: 2775
- Metrics: 2112

### Worker

**Назначение:** Обработка очереди сообщений и отправка в SMSC провайдеры.

**Функции:**
- Потребление сообщений из Kafka
- Маршрутизация сообщений к провайдерам
- Управление пулом соединений к SMSC провайдерам
- Обработка DLR от провайдеров
- Retry логика с экспоненциальной задержкой
- Отправка DLR обратно в систему

**Масштабирование:** Множественные инстансы (consumer group)

**Порты:**
- Metrics: 2112

### HAProxy

**Назначение:** Балансировщик нагрузки для API Gateway.

**Функции:**
- Распределение HTTP запросов между инстансами API Gateway
- Распределение gRPC запросов между инстансами API Gateway
- Health checks для бэкендов
- Статистика и мониторинг

**Порты:**
- HTTP: 8080
- gRPC: 9090
- Stats: 8404

## Инфраструктурные компоненты

### Kafka

**Назначение:** Очередь сообщений для асинхронной обработки.

**Topics:**
- `sms.outgoing` - исходящие SMS для отправки
- `sms.dlr` - delivery receipts от провайдеров
- `sms.failed` - сообщения об ошибках (DLQ)

**Особенности:**
- Гарантированная доставка сообщений
- Поддержка consumer groups для масштабирования
- Retention policy для хранения истории

### PostgreSQL

**Назначение:** Основное хранилище данных.

**Таблицы:**
- `messages` - сообщения (партиционирование по датам)
- `providers` - конфигурация SMSC провайдеров
- `routes` - правила маршрутизации
- `clients` - клиенты API
- `dlr_receipts` - delivery receipts
- `audit_log` - аудит операций

**Особенности:**
- Партиционирование таблицы messages по месяцам
- Индексы для оптимизации запросов
- Поддержка транзакций

### Redis

**Назначение:** Кэш и дополнительные структуры данных.

**Использование:**
- Кэширование данных клиентов
- Rate limiting счетчики
- Временное хранение сессий

### Prometheus

**Назначение:** Сбор и хранение метрик.

**Особенности:**
- Сбор метрик со всех сервисов
- Хранение временных рядов
- Интеграция с Grafana

### Grafana

**Назначение:** Визуализация метрик и дашборды.

**Дашборды:**
- Overview - общий обзор системы
- API Gateway - метрики API Gateway
- Worker - метрики Worker
- Provider Health - здоровье провайдеров

## Потоки данных

### Исходящее сообщение (HTTP/gRPC)

1. Клиент отправляет запрос в API Gateway через HAProxy
2. API Gateway аутентифицирует клиента и применяет rate limiting
3. API Gateway сохраняет сообщение в PostgreSQL
4. API Gateway публикует сообщение в Kafka topic `sms.outgoing`
5. API Gateway возвращает ответ клиенту с message_id

### Обработка сообщения Worker

1. Worker потребляет сообщение из Kafka topic `sms.outgoing`
2. Worker определяет провайдера через маршрутизатор
3. Worker получает соединение из пула провайдера
4. Worker отправляет сообщение в SMSC через SMPP
5. Worker обновляет статус сообщения в PostgreSQL
6. При ошибке Worker публикует сообщение в `sms.failed` или повторяет отправку

### Delivery Receipt (DLR)

1. SMSC провайдер отправляет DLR через SMPP соединение Worker
2. Worker публикует DLR в Kafka topic `sms.dlr`
3. Worker обновляет статус сообщения в PostgreSQL
4. Worker отправляет DLR клиенту через SMPP Server (если клиент подключен)

### Исходящее сообщение (SMPP)

1. SMPP клиент подключается к SMPP Server и выполняет bind
2. SMPP клиент отправляет submit_sm
3. SMPP Server сохраняет сообщение в PostgreSQL
4. SMPP Server публикует сообщение в Kafka topic `sms.outgoing`
5. SMPP Server возвращает submit_sm_resp клиенту
6. Дальнейшая обработка аналогична HTTP/gRPC потоку

## Масштабирование

### Горизонтальное масштабирование

- **API Gateway:** Добавление новых инстансов за HAProxy
- **Worker:** Добавление новых инстансов в consumer group
- **SMPP Server:** Добавление новых инстансов (требует настройки балансировки)

### Вертикальное масштабирование

- Увеличение ресурсов контейнеров (CPU, память)
- Настройка пулов соединений к БД и Redis
- Настройка concurrency для Worker

## Безопасность

- Аутентификация через API ключи
- Rate limiting на уровне клиента и сессии
- Изоляция сетей через Docker networks
- SSL/TLS для внешних соединений (опционально)

## Мониторинг

Все сервисы экспортируют метрики в формате Prometheus:
- HTTP/gRPC запросы и latency
- Количество обработанных сообщений
- Ошибки и их типы
- Размер очередей Kafka
- Здоровье соединений к провайдерам

Health checks доступны на всех сервисах:
- `/health` - полная проверка с зависимостями
- `/health/live` - liveness probe
- `/health/ready` - readiness probe
