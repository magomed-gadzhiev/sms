## Batch 1: Step 1 (Сообщение)

### AC-CW-M-01: Wizard открывается на Step 1 по умолчанию

**ДАНО:**

- Страница `/campaigns/new` без query-параметра `?draft=`

### AC-CW-M-02: Sender dropdown загружен и первый одобренный предвыбран

**ДАНО:**
- У тестового клиента есть минимум один sender_name со статусом `approved`

**КОГДА:** Wizard полностью загружен на Step 1

**ТОГДА:**
- Dropdown "Имя отправителя" содержит как минимум одну опцию с названием из sender_names
- Первый одобренный sender выбран по умолчанию (value != пустая строка)
- Нет error-сообщения "Не удалось загрузить имена отправителей"

**Предусловие данных:** в БД для тестового reseller-юзера есть `INSERT INTO sender_names (name, status) VALUES ('TestSender1', 'approved')` или аналогичное.

### AC-CW-M-03: "Далее" disabled когда textarea пустая

**ДАНО:**
- Step 1 активен
- Textarea пустая (строка состоит из нулевой длины или только whitespace)
- Sender name выбран (по AC-CW-M-02)
- A/B toggle выключен

**КОГДА:** пользователь ничего не вводил / стёр текст

**ТОГДА:**
- Кнопка "Далее" имеет attribute `disabled` ИЛИ `aria-disabled="true"`
- Клик по "Далее" не приводит к смене active step в `StepIndicator`

### AC-CW-M-04: "Далее" enabled когда текст введён

**ДАНО:**
- Step 1 активен
- Sender name выбран
- A/B toggle выключен
- Textarea пустая

**КОГДА:** пользователь вводит в textarea "Привет мир" (10 символов)

**ТОГДА:**
- Кнопка "Далее" становится enabled (не имеет `disabled`)
- Счётчик символов обновляется на 10

---

### AC-CW-M-05: CharacterCounter обновляется при вводе

**ДАНО:**
- Step 1 активен, textarea пустая
- Counter отображает `"160 осталось"` (полная квота GSM7 для одного SMS)

**КОГДА:** пользователь вводит "Hello world!" (12 символов, ASCII)

**ТОГДА:**
- Counter обновляется до `"148 осталось"` (160 − 12 = 148)
- Для текстов ≤ 160 символов SMS-segment suffix НЕ отображается

**Примечание:** формат counter — `"N осталось"`, не `"N/max"`, как можно было бы ожидать из спеки. Спека (§Шаг 1) описывает compound-формат "символы + количество частей SMS", реализация показывает "remaining + опционально parts". Расхождение минорное, фиксируется как низкоприоритетный D-03 (см. _DRIFT.md), AC формулируется по реальному выводу.

### AC-CW-M-06: Выбор шаблона заполняет textarea его телом

**ДАНО:**
- Step 1 активен, textarea пустая
- У тестового клиента есть минимум один approved template с body `"Test template body"`

**КОГДА:**
1. Пользователь кликает "Выбрать шаблон"
2. Открывается TemplatePicker
3. Пользователь выбирает шаблон с body `"Test template body"`

**ТОГДА:**
- Textarea содержит `"Test template body"` (spec §"Шаг 1: при выборе шаблона текст подставляется в textarea")
- Counter обновился на 18 (длина строки)
- Кнопка "Далее" стала enabled

**Предусловие данных:** `INSERT INTO templates (body, status) VALUES ('Test template body', 'approved')` для тестового клиента.

**Примечание:** этот AC напрямую противоречит текущему коду (строка 307 очищает textarea при выборе шаблона — см. DRIFT D-02 Путь A). Тест будет красным до фикса кода.

### AC-CW-M-07: A/B toggle раскрывает блок "Вариант B"

**ДАНО:**
- Step 1 активен
- A/B toggle в состоянии OFF
- Блок "Вариант B" не виден в DOM (или hidden)

**КОГДА:** пользователь включает A/B toggle

**ТОГДА:** в DOM появляются все поля Варианта B:
- Textarea для текста варианта B
- Кнопка "Выбрать шаблон" для варианта B
- CharacterCounter для варианта B
- Slider/input "Доля аудитории" с текущим значением 20 (дефолт)
- Select "Время до выбора победителя" с текущим значением 6 (дефолт)
- Radio-group "Метрика победителя" с выбранным `delivery_rate` (дефолт)

### AC-CW-M-08: "Далее" disabled когда A/B on и текст B пуст

**ДАНО:**
- Step 1 активен
- Текст варианта A введён (произвольный, например "Текст A")
- Sender name выбран
- A/B toggle включён (по AC-CW-M-07)
- Textarea варианта B пустая

**КОГДА:** пользователь наблюдает state кнопки "Далее"

**ТОГДА:**
- Кнопка "Далее" имеет `disabled` (текст B — обязательное поле при A/B on, согласно spec §"Валидация Step 1")

**Примечание:** в коде сейчас валидация A/B проверяет `abTemplateIdB`, а не текст B. Тест будет красным до фикса кода (см. DRIFT D-02).

## Seed-free подмножество

| AC | Seed-free? | Комментарий |
|---|---|---|
| AC-CW-M-01 | ✅ | Только UI, ничего не нужно |
| AC-CW-M-02 | ❌ | Требует approved sender в БД |
| AC-CW-M-03 | ❌ | Зависит от AC-M-02 (sender нужен) |
| AC-CW-M-04 | ❌ | Зависит от AC-M-02 |
| AC-CW-M-05 | ❌ | Зависит от AC-M-02 |
| AC-CW-M-06 | ❌ | Требует approved template + sender |
| AC-CW-M-07 | ✅ | Только UI, toggle |
| AC-CW-M-08 | ❌ | Зависит от AC-M-02 |

**Только 2 из 8 seed-free.** Остальные 6 требуют хотя бы одного approved sender_name у тестового клиента.

**Реальность:** тестовый reseller-юзер в sandbox скорее всего уже имеет sender_names (предыдущие тесты создавали). Проверим в процессе — если есть, AC идут без seed. Если нет — нужен seed через API в `beforeEach`.

## Зависимости от кода (DRIFT D-02)

До применения фикса по Пути A:
- **AC-CW-M-03, AC-CW-M-04** — упадут, потому что текущий `canProceed` проверяет `templateId`, а не `messageText`
- **AC-CW-M-06** — упадёт, потому что код очищает textarea при выборе шаблона (строка 307)
- **AC-CW-M-08** — упадёт, потому что A/B валидация проверяет `abTemplateIdB`, а не текст B

**AC-CW-M-01, AC-CW-M-02, AC-CW-M-05, AC-CW-M-07** — должны пройти независимо от фикса D-02 (проверяют поведения, не затрагиваемые drift).

## План тестирования

Два захода:
1. **Сейчас:** реализую все 8 тестов. Ожидаемо: 4 passed / 4 failed (см. выше).
2. **После фикса D-02 + deploy:** повторный прогон. Ожидаемо: 8 passed.

Красные тесты на этапе 1 — доказательство того, что они реально тестируют drift D-02, а не "заглушки". Это **feature, не bug**.

## Batch 2: Step 3 (Расписание) — Phase A (без timezone checkbox)

**Скоуп:** только режим "Сейчас / Позже" и валидация даты/времени.
**Отложено в Phase B:** checkbox "По часовому поясу абонента" (см. [_DRIFT.md D-04](_DRIFT.md)).

### Условные предусловия для всего batch

- Тестовый клиент имеет минимум 1 approved sender_name
- Тестовый клиент имеет минимум 1 контактную базу с любым именем
- Если seed отсутствует — тесты skipнутся с явным сообщением

### AC-CW-S-01: Step 3 открывается с режимом "Сейчас" по умолчанию

**ДАНО:** пользователь прошёл Step 1 и Step 2, активен Step 3 "Расписание"

**КОГДА:** Step 3 полностью отрендерился

**ТОГДА:**
- Radio `input[name="sendMode"][value="now"]` имеет `:checked`
- Radio `input[name="sendMode"][value="later"]` НЕ :checked
- Поля "Дата" и "Время" НЕ видны в DOM

### AC-CW-S-02: Выбор "Позже" раскрывает date/time picker'ы

**ДАНО:** Step 3, режим "Сейчас", date/time скрыты

**КОГДА:** пользователь кликает radio "Позже"

**ТОГДА:**
- Radio "Позже" :checked, "Сейчас" не :checked
- В DOM появляется `<input type="date">` с label "Дата"
- В DOM появляется `<input type="time">` с label "Время"

### AC-CW-S-03: Возврат к "Сейчас" скрывает date/time

**ДАНО:** Step 3, "Позже" активен, date/time видны

**КОГДА:** пользователь кликает radio "Сейчас"

**ТОГДА:**
- Radio "Сейчас" :checked
- `<input type="date">` и `<input type="time">` исчезают из DOM

### AC-CW-S-04: Date picker имеет `min` = сегодня

**ДАНО:** Step 3, режим "Позже"

**КОГДА:** date picker отрендерен

**ТОГДА:**
- `input[type="date"]` имеет attribute `min` = `YYYY-MM-DD` сегодняшней даты

### AC-CW-S-05: Inline-ошибка при времени < now + 5 минут

**ДАНО:** Step 3, режим "Позже"

**КОГДА:**
- Date = сегодня (в локальном времени)
- Time = `00:00` (заведомо в прошлом в любое время суток, кроме exact 00:00:00 тика)

**ТОГДА:**
- Отображается красный текст: `"Время отправки должно быть не менее чем через 5 минут от текущего момента."`
- Текст виден сразу (inline, без клика "Далее")

### AC-CW-S-06: "Позже" с валидным будущим временем — переход на Step 4

**ДАНО:**
- Step 3, режим "Позже"
- Date = сегодня (или завтра, если за 30 мин уже следующий день)
- Time = (текущее время + 30 минут)

**КОГДА:** пользователь кликает "Далее"

**ТОГДА:**
- Активный step становится "Подтверждение"
- Inline-ошибка НЕ отображается

### AC-CW-S-07: "Позже" с пустыми полями блокирует Next

**ДАНО:** Step 3, режим "Позже", date и time пусты

**КОГДА:** пользователь кликает "Далее"

**ТОГДА:**
- Остаётся на Step 3 "Расписание"
- Появляется текст: `"Укажите корректную дату и время отправки."`

### AC-CW-S-08: "Сейчас" — Next работает без доп. полей

**ДАНО:** Step 3, режим "Сейчас"

**КОГДА:** пользователь кликает "Далее"

**ТОГДА:**
- Активный step становится "Подтверждение"
- Никаких ошибок валидации

## Batch 2: Step 3 (Расписание) — Phase B (timezone checkbox + backend)

**Скоуп:** активация checkbox "По часовому поясу абонента" в UI + полная backend-поддержка (миграция + proto + domain + repo + handler).

**Закрывает drift:** D-01 (backend без поля), D-04 (UI checkbox disabled).

### AC-CW-S-09: Checkbox не рендерится в DOM при mode = "Сейчас"

**ДАНО:** пользователь на Step 3, default mode "Сейчас"

**КОГДА:** страница отрендерена

**ТОГДА:**
- Checkbox "По часовому поясу абонента" отсутствует в DOM (блок внутри `{sendMode === 'later' && ...}`)
- Label "По часовому поясу абонента" не виден пользователю

### AC-CW-S-10: Checkbox появляется и enabled при mode = "Позже"

**ДАНО:** Step 3, mode = "Сейчас" (checkbox скрыт)

**КОГДА:** пользователь переключает на "Позже"

**ТОГДА:**
- Checkbox появляется в DOM с label "По часовому поясу абонента"
- Checkbox **НЕ disabled** (не имеет attribute `disabled`)
- Checkbox по умолчанию НЕ checked

### AC-CW-S-11: Клик по checkbox + создание → POST содержит use_subscriber_timezone=true

**ДАНО:**
- Step 3 с "Позже", checkbox виден и unchecked
- Заполнены валидная date+time
- Пользователь проходит на Step 4 и нажимает "Запланировать"

**КОГДА:** до клика "Запланировать" — пользователь ставит галочку на checkbox

**ТОГДА:**
- POST /portal/v1/campaigns содержит в body `"use_subscriber_timezone": true`
- Ответ сервера HTTP 201

### AC-CW-S-12: Без галочки → POST содержит use_subscriber_timezone=false

**ДАНО:**
- Step 3 с "Позже", checkbox unchecked
- Заполнены валидная date+time
- Пользователь проходит на Step 4 и нажимает "Запланировать"

**КОГДА:** отправка без включения checkbox

**ТОГДА:**
- POST /portal/v1/campaigns содержит `"use_subscriber_timezone": false`

### AC-CW-S-13: Переключение "Позже" → "Сейчас" сбрасывает state

**ДАНО:**
- Step 3 с "Позже", checkbox checked
- Пользователь включил timezone

**КОГДА:** пользователь кликает radio "Сейчас"

**ТОГДА:**
- Checkbox исчезает из DOM
- Внутреннее `useSubscriberTimezone` state установлено в false (onChange handler радио "now")
- Следующий переход обратно на "Позже": checkbox unchecked (не restored из предыдущего состояния)

### AC-CW-S-14 (API round-trip): Backend сохраняет и возвращает флаг

**ДАНО:** валидный reseller/client auth, доступ к Portal API

**КОГДА:**
1. POST /portal/v1/campaigns с body, содержащим `use_subscriber_timezone: true` + все обязательные поля + `scheduled_at` в будущем
2. Сервер возвращает HTTP 201 с `{id, ...}`
3. GET /portal/v1/campaigns/{id}
4. DELETE /portal/v1/campaigns/{id} (cleanup)

**ТОГДА:**
- Ответ step 2: `use_subscriber_timezone == true`
- Ответ step 3: `use_subscriber_timezone == true`
- Ответ step 4: HTTP 204 (удаление успешно)

**Обоснование:** закрывает D-01. Без этого AC backend-изменение не верифицируется.

- **Seed:** тот же что в Phase A (sender + contact list). API round-trip дополнительно создаёт и удаляет тестовую кампанию.
- **Drift:** D-01 и D-04 закрываются этим batch'ем.
